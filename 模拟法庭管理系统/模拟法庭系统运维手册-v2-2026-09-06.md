### 1.5 剧本数据模型（改案/建案照这个填）

控制中台状态对象 `S` 结构（来自 `DEMO` + `normalize` 默认值）：

```js
{
  meta:    { caseNo, cause, court, domain, red, blue },   // 案号/案由/法院/案由域/红方摘要/蓝方摘要
  roles:   [ {id,name,role,side,seat} ],                  // side: red=原告 / blue=被告 / neutral=中立
  stageIdx:1,                                             // 庭审阶段 0~5
  speaker: "plain",                                       // 当前发言席位 id
  advantage:5,                                            // 红蓝优势条，±100（正=红方占优）
  view:    "observer",                                    // observer/red/blue/judge
  transcript:[                                           // 推演时间轴
    {t:0,  k:"stage", stage:1, text:"▶ 进入【法庭调查】阶段"},   // 阶段标记
    {t:8,  role:"judge", type:"say", text:"……"},                // 发言
    {t:70, role:"pagent", type:"atk", text:"⚔️ 进攻：……"},        // 进攻
    {t:96, role:"dagent", type:"def", text:"🛡️ 防守：……"}         // 防守
  ],
  evidence:[                                              // ⚠️ 证据墙条目（见 §1.5b）
    { id:"E1", name:"…", by:"plain", status:1, purpose:"证明原告主体适格" }
  ],
  verdict: "",                                            // 评议宣判结论
  startedAt: null                                         // 计时起点时间戳
}
```

- **transcript 条目类型**：`k:"stage"`（阶段标记）+ `type:"say"|"atk"|"def"`（陈述/进攻/防守）。
- **evidence.status 枚举**：`0 未出示 / 1 已出示 / 2 已质证 / 3 已采纳 / 4 未采纳`（对应 `EVI_STATUS`）。
- **evidence.purpose**：证明目的字段（v1 漏记，v2 补入）。是证据墙「证明目的」一行的数据来源。

> 改案最小动作：复制 `DEMO`，改 `meta`（尤其 `domain` 决定法官心智默认域）、`roles`、`transcript`、`evidence`，导出 JSON 或直接改 `DEMO` 常量后刷新页面。

### 1.5b 证据墙条目化（v2 新增 · Request G 落地）

证据墙把双方证据按「提交方阵营」分列，每张证据**独立成卡**，可读出「谁提交 / 名称 / 证明目的 / 当前质证状态」。

**布局**（中台 HTML 结构，已实测）：
- 左列 **红方·原告证据墙**（`#eviRed`）= `role.side==="red"` 的证据。
- 右列 **蓝方·被告证据墙**（`#eviBlue`）= `role.side==="blue"`（含中立 `neutral` 归蓝方）的证据。

**卡片结构**（`renderEvidence()` 渲染，每行含）：
```
┌─ 证据 E1          [状态徽标]        ← .evi-h：证据id + EVI_STATUS[e.status]
│  证据名称                       ← .evi-name
│  【证明目的】证明原告主体适格     ← .evi-pur：固定前缀"证明目的" + purpose 字段
│  提交：原告                       ← .evi-by：roleById(e.by).name
└─────────────────────────────
```

**配色规则（红蓝方向纠正 + 质证状态）**：
| 状态 | status 值 | 卡片配色 | 含义 |
|---|---|---|---|
| 未质证（红） | 0 未出示 / 1 已出示 / 4 未采纳 | `.evi.unexam` 左边框红 + 红底 | 尚未走完质证，风险提示 |
| 已质证（绿） | 2 已质证 / 3 已采纳 | `.evi.exam` 左边框绿 + 绿底 | 质证完成，可作定案参考 |

> 判定逻辑（源码）：`exam = e.status>=2 && e.status<=3`（已质证/已采纳=绿；未出示/已出示/未采纳=红）。
> 实战用法：推演中每完成一轮质证，把对应证据 `status` 由 1→2，卡片即由红转绿，态势一眼可见。

**证据墙维护要点**：
- 加证据 = 往 `S.evidence` 数组追加对象，**必带 `by`（角色id，决定落红列还是蓝列）与 `purpose`**。
- `by` 指向 `roles[].id`；`by` 找不到角色时按 `neutral` 处理（归蓝列）。
- 改完刷新页面，红蓝列与红绿配色自动重算。

## 4. 双看板自动化刷新（v2 新增 · Request J 落地）
