## 🔌 通道故障处置规范（2026-08-06 确立）

1. **IMA 故障分型**（诊断入口 `03-连接/scripts/fix_ima_connector.py`；状态文件真实路径 `~/.workbuddy/connectors/75c7265a-5f11-4420-9e71-be28329d68fd/connector-states.v3.json`）：
   - **配置态故障**：`userDisabled['ima-mcp']=true` 或不在 `enabled` 列表 → 执行 `--apply` 翻转 + 重启 WorkBuddy。
   - **运行态掉线**：配置全部健康（enabled ✓ / userDisabled=False / everConnected=True / 凭证已注入）但工具不在索引 → **属会话级，不执行 `--apply`**，等待恢复即可。
2. **摄入中断铁律**：IMA 取全文失败时**绝不回写 `ingested`**，仅在 `ima_intake_state.json` 写 `b_pending_backfill` 节点（`candidates_selected` / `consume_priority=next_run_first` / `occupies_new_quota=false`）。否则去重表被污染，候选会被误判为已摄入而永久丢失。
3. **QQ 邮箱推送兜底**：`qq-mail` MCP 发信工具不在索引时，改走 `~/.workbuddy/skills/qq-email/scripts/send.js --stdin`（SMTP smtp.qq.com:465，凭证读 `QQ_EMAIL_ACCOUNT`/`QQ_EMAIL_AUTH_CODE` 环境变量，已配置）。**不再降级为「响应正文替代推送」或写 QQ 补发摘要文件。**（2026-08-14 补充：`send.js` 参数为**位置参数** `<收件人> <主题> --stdin`，非 `--to` 形式；且 `qq-mail` MCP 的 confirmation_token 有效期极短（约 2 分钟），自动化无人值守场景下 MCP 需人工确认时**直接切 SMTP 脚本**，勿等待确认。）
4. **案例源降级标记**：法随案例库 MCP 不可用时用 WebSearch 采集，采集文件必须标 `pending_source_upgrade`，待 MCP 恢复回源补全案号与全文说理。
5. **可用性判据（2026-08-07 新增）**：连接器面板的 `connected/disconnected` 是**滞后快照，不可作判据**。判断 MCP 通道是否可用，一律以 `ToolSearch` 工具索引 + `DeferExecuteTool` 实调为准。08-07 面板显示 ima-mcp disconnected，实测 15 篇全部 fetch 成功。
6. **IMA media_id 构造规律（2026-08-07 确立，防 220030 假失败）**：
   `media_id = "wechatarticle_62fe55a7567bc291dfbbee29900b27c3_" + <32位十六进制 rawid> + <knowledge_base_id>`
   rawid **必须取全 32 位**。8 位截断会使 `fetch_media_content` 返回 **220030**，该错误码此前被误归因为"IMA 运行态掉线"，实为构造错误。遇 220030 先核 media_id 长度，再判通道。
7. **降级笔记不覆盖原则（2026-08-07 确立）**：公开源降级笔记与后续 IMA 真源笔记若**主题不重叠**，降级笔记属独立有效资产，只消解 `ima_source_pending: true→false` 并加 `resolved_note`，**不删除、不覆盖**。

## 🔎 裁判规则库回填与在线对账铁律（2026-08-29 确立）

8. **华宇元典查询一律不得传 `type` 参数**：`yuandian_rh_case_details` 的 `type`（`ptal`=普通 / `qwal`=权威）不传则不筛选。历史对账一直传 `type:"qwal"`，**把整个普通案例库排除**，造成大量假阴性（误记为"库内未收录"）。去掉后普通案例大量命中，如 `(2021)鲁民终913号` 由误记 miss 转 hit。除非明确只要权威案例，否则**禁止传 type**。
9. **共现笔记锚点污染（写入型任务通用）**：连接层把其他笔记文件名写进卡片末尾 `## 关联…`（595 张）/ `## 相关笔记`（425 张）区块与 `related_links`（607 张）字段，其中常含案号但**非本卡源案例**。实测误挂 14 张——`R-PI-145`（工伤认定）被挂 `(2021)最高法民再145号`（房屋租赁案）、`R-PI-142` 被挂 `(2023)最高法民终142号`（纯编号数字巧合）。**任何"从卡片提取元数据"的任务，锚点只从本体内容提取**：frontmatter 剔除 `related_*` 字段，正文截断至首个「关联/相关笔记/共现笔记」标题前。宁可少挂不可错挂。
10. **vault 严格 YAML 不可解析（354/612 张）**：title 里的 wikilink、`连接枢纽-` 裸条目等导致 `yaml.safe_load` 失败，但 Obsidian 容忍。**批量改 frontmatter 必须逐行编辑，禁止 yaml 往返序列化**，否则会毁掉这 354 张。校验"零损坏"的正确做法是**与写前基线备份比对失败集是否一致**，而非看绝对失败数。
11. **存在并发写入进程**：回填后 `updated` 时间戳被别的进程改动、行内列表被重序列化为块式列表，导致幂等性不收敛（写-改-写循环）。**派生数据（可从正文重新提取的）不要写进 frontmatter**，只写主锚点与判定结果。幂等性验收标准：连续 3 次 dry-run 需改写文件 = 0。
12. **回填脚本**：`03-连接/scripts/backfill_yuandian_ids.py` v1.2（dry-run 默认 / --apply 落盘 / 写前整目录备份 + 文件数断言 / 幂等）。待实证队列 `03-连接/yuandian_verify_queue.json`（100 个案号）；单次查询返回约 1.5 万字符，宜分批消费、只回写命中台账。当前覆盖率 96/612 = 15.7%，516 张无案号锚点诚实挂起 `yuandian_source_pending`（源自公众号/学习笔记/法条解读，本就不对应裁判文书，**不得伪造案号**）。

## 🛠 IMA 漏窗回补实战补遗（2026-08-11）

- **前序会话 fetch 全文的缓存在本会话会丢失**：IMA `fetch_media_content` 的原始响应缓存在 `.workbuddy/projects/<session>/tool-results/`（`mcp-connector-proxy-ima-mcp_fetch_media_content-*.txt` 为 XML/JSON 全文；`chatcmpl-tool-*.txt` 为模型工具输出）。该目录**会被主动轮转**——本会话的新工具调用会顶掉旧文件（实测 994a1b9…txt 在一次 grep 到 ls 之间即消失）。故跨会话回补时，若需复用前序 fetch 内容，须**第一时间 cp 到工作区安全目录**再解析，否则内容随轮转丢失、且 IMA 不可用时无法重取。
- **状态↔磁盘 desync 是漏窗回补的常态**：KB 构建期已落盘的笔记往往未登记 `ima_intake_state.json` 的 `ingested` 列表。回补前务必先磁盘扫描确认笔记存在（互链不重复建文件），仅对真正缺失者新建；已存在者增强 frontmatter（补 `media_id/window/ima_true/occupies_new_quota`）即可。
- **摄入中断铁律的边界**：未完整取回全文→绝不回写 `ingested`。但若笔记已落盘（desync 或前序 fetch 缓存恢复），内容安全，注册 `ingested` 仅为补 dedup 表、绝不污染去重（参考 `w_2026-08-07` consumed 先例"仅补登状态文件"）。
