# 快照 / 备份与版本库规范

> 从 `MEMORY.md` 拆出的独立章节（2026-08-30，用户拍板），**信息一条不丢**。
> 主文件索引：[[MEMORY]] →「🧹 快照/备份与版本库」索引指针。
> 确立日期：2026-08-29（6110 个快照漏进版本库事故后总结）。

---

## 1. `.gitignore` 对已跟踪文件无效

加规则只能阻止「未来新增」。已入库的历史副本必须 `git rm -r --cached` 才停止跟踪（本地文件保留）；且**即使如此 `.git` 体积也不降**（历史 blob 仍在），真瘦身须重写历史（改全部 commit hash + `--force` 强推，风险高）。

任何「加了 gitignore 就该变小」的预期都是错的，**交付前须先向用户讲清**。

## 2. `*.bak` 只匹配文件，匹配不到目录

`*.bak` 只匹配以 `.bak` 结尾的「文件」，匹配不到 `xxx.bak-时间戳` 形式的「目录」——这正是 08-29 发现 **6110 个快照漏进版本库的根因**。

写忽略规则时须区分文件/目录语义，**目录规则要带尾斜杠**。

## 3. 写入型批处理任务的快照策略

脚本每次跑都生成整目录副本（如 `裁判规则库.bak-<时间戳>`）会指数级膨胀——单次回填任务即产生 5 个 ×619 文件 ≈ **3086 个冗余副本**。

应当：
1. 快照只保留「最早基线 + 最新一次」两份；
2. 或写库外目录（`~/WorkBuddy/Backups/`、`/tmp/`）；
3. 库内临时备份文件命名须以 `*.bak` 结尾才能被现有规则兜住。

## 4. 批量改忽略规则前必须做全量误伤验证

```
git ls-files -z | git check-ignore -z --stdin --no-index -v
```

对全部已跟踪文件跑一遍，逐条判定命中项是否落在目标范围内。

⚠️ 注意 `-z` 模式下 `-v` 输出是 **NUL 分隔四元组**（source/line/pattern/path），不是制表符分隔——按 `\t` 解析会得到「命中 0」的**假阴性**结论。

## 5. 快照/副本的新旧排序绝不能用 mtime

Obsidian 索引进程（及各类扫描）会**批量刷新目录与文件的 mtime**。实测 5 个快照目录的 mtime 被刷成同一时刻，按 `os.path.getmtime()` 排序会把最新基线误判为最旧、**险些误删**（2026-08-29 真实事故，被 dry-run 拦下）。

**正确做法**：从目录名内嵌的 `YYYYMMDD-HHMMSS` 时间戳提取排序键（正则 `(\d{8}-\d{6})`），无时间戳者降级用 mtime 并当最旧。适用于一切「按时间保留最近 N 份」的清理脚本。

**同类坑**：`shutil.rmtree` 在 Obsidian 索引进程占用目录时，能删光文件却**不报错地留下空目录壳**（实测残留 0 文件的 `裁判规则库.bak-20260829-162931` + 空的 `合规/` 子目录），导致 prune 后目录数与预期不符——**删完必须校验 `os.path.exists()`**，否则回退清理空目录链。

## 6. `.gitignore` 白名单（`!` 规则）是保留特定副本的正解

批量忽略 `xxx.bak-*/` 后，对仍需受版本控制的少量基线用 `!具体目录/` 开白名单，顺序为「**先忽略、后例外**」。

**限制**：若某文件的**父目录**被排除，则无法用 `!` 重新纳入。
