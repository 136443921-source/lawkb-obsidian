# IMA 漏窗根治方案

## 一、结论先行

**IMA 从来没有"断线"。** 它是被 WorkBuddy 客户端标记为**用户手动禁用**，因此其 MCP 工具从未被注册进会话工具索引。既往 4 天里 A0 自检把这个**配置态问题**误判为**网络态问题**，于是每天忠实登记漏窗、却从不触碰真正的病灶，形成"记录—空转—再记录"的死循环。

| 判断项 | 既往认知 | 实测事实 |
|--------|----------|----------|
| 故障性质 | 会话级工具索引冻结 / 网络断线 | 连接器被置于 `userDisabled` |
| 凭证状态 | 疑似过期 | **完好**（`headerOverrides` 含 ima-mcp） |
| 历史连接 | 不确定 | **成功连过**（`everConnected` 含 ima-mcp） |
| 修复手段 | 等待重连 / 重启 | 翻转两个配置字段 + 重启 |
| 能否自愈 | 否（只能等） | **能**（脚本 10 秒完成） |

---

## 二、根因证据链

### 2.1 决定性证据

配置文件 `~/.workbuddy/connectors/75c7265a-5f11-4420-9e71-be28329d68fd/connector-states.v3.json`：

```json
{
  "enabled": ["kdocs","github","qcc-company","yuandian-mcp","tencent-docs","qq-mail"],
  "userDisabled": { "tencent-docs": false, "qq-mail": false, "ima-mcp": true },
  "everConnected": ["github","kdocs","qcc-company","yuandian-mcp","tencent-docs","qq-mail","ima-mcp"],
  "headerOverrides": ["kdocs","github","tencent-docs","ima-mcp"]
}
```

三点直接指向根因：

1. `enabled` **不含** `ima-mcp` → 客户端不加载其工具，`ToolSearch` 必然搜不到。
2. `userDisabled["ima-mcp"] = true`，而同表中 `tencent-docs`、`qq-mail` 均为 `false` → **仅 IMA 一个被禁**，排除"整体故障"。
3. `everConnected` 与 `headerOverrides` 均含 `ima-mcp` → 授权与凭证完好，**无需重新扫码**。

### 2.2 时间线（历史备份佐证）

| 备份文件 | 时刻 | `enabled` 是否含 ima-mcp |
|---------|------|----------------------|
| `.bak-20260802083212` | 08-02 08:32 | ✗ |
| `.bak-20260802083510` | 08-02 08:35 | ✓（曾短暂启用） |
| `.bak-20260803-1145` | 08-03 11:45 | ✗（位置被 `tencent-docs` 顶替） |
| 当前 | 08-05 | ✗ |

`enabled` 长度长期稳定在 6–7，且 08-03 启用 `tencent-docs` 的同时 `ima-mcp` 消失，高度疑似**启用名额挤占**：新启用连接器时挤掉了最早的一个，并被写入 `userDisabled`。

### 2.3 流程漏洞（为何 4 天没被发现）

自动化 v1.10 的变更记录里其实已写明治本方向：

> 治本＝翻转 connector-states 中 userDisabled + 加回 enabled

但 **A0 的执行步骤（A0.1 自检 / A0.2 回补 / A0.3 登记）从未落地这个动作**。认知写进了变更日志，却没写进流程。这是本次事故的真正制度性原因。

## 三、次生问题（一并修复）

### P2 状态文件路径漂移 + schema 不符

| 项 | 自动化 A1.1 声明 | 磁盘实际 |
|----|-----------------|---------|
| 路径 | `知识飞轮系统/IMA-Inbox/ima_intake_state.json` | `知识飞轮系统/ima_intake_state.json` |
| schema | `{version, last_run_ts_ms, libraries{ingested}}` | `{schema, pending_windows[], totals}` |

**后果（严重）**：即使 IMA 明天恢复，`SELECT_3` 也读不到 `libraries[].ingested` 集合 → **去重完全失效 → 重复摄入已有文章**，污染飞轮。必须在回补**之前**修好。

### P3 回补量爆炸

漏窗 08-02 08:30 → 08-05，跨 4 个自然日，理论满额 `4 天 × 5 库 × 3 篇 = 60 篇`。单次会话不可能完成，且 A0.2 现行写法"对每个窗口逐库补摄"会在两个窗口上叠加成 30 篇，仍然过载。需要**合并窗口 + 限流分批**。

---

## 四、修复方案（四阶段）

### 阶段 1 · 恢复连接（约 5 分钟，需重启）

**路径 A —— 图形界面（推荐，最安全）**

1. 打开 WorkBuddy 连接器管理页面
2. 找到「ima知识库（ima-mcp）」，点击**启用 / 重新连接**
3. 若提示授权已失效再扫码；否则直接生效
4. 重启 WorkBuddy

**路径 B —— 脚本修复（UI 找不到入口时备选）**

```bash
cd ~/Documents/LawKB/知识飞轮系统/03-连接/scripts
python3 fix_ima_connector.py            # 诊断，不写盘
python3 fix_ima_connector.py --apply    # 执行修复（自动备份）
# 出问题时回滚：
python3 fix_ima_connector.py --rollback <备份文件路径>
```

脚本安全约束：默认 dry-run；写盘前自动备份 `connector-states.v3.json.bak-<时间戳>`；**仅**改 `enabled` / `userDisabled` 两键；兼容 `userDisabled` 的 dict / list 两种形态（**已实测本机为 dict，误当 list 处理会损坏配置**）；全程不读取、不打印任何 token。

**验证**：重启后新开会话，`ToolSearch` 搜 `mcp__ima-mcp__` ——出现 7 个工具即成功。

> ⚠ 若启用后 IMA 调用报 401，说明 accessToken 已过期，需在 UI 断开并重新授权，凭证会自动重新注入。

### 阶段 2 · 修正状态文件（回补前必须完成）

1. 将 `pending_windows` 与 `libraries[].ingested` **合并进同一份文件**，统一保留在 `知识飞轮系统/ima_intake_state.json`；
2. 同步修改自动化 prompt 中 A1.1 的路径声明，与磁盘实际对齐（**改声明，不搬文件**，避免历史脚本失效）；
3. 补齐 5 个库的 `libraries` 骨架，`ingested` 初始为空、`last_run_ts_ms` 设为漏窗起点 `2026-08-02T08:30`。

### 阶段 3 · 分批回补（限流）

**窗口合并**：`w1`(08-02 08:30→08-03 11:32) + `w2`(08-03 11:32→08-04 10:00) + 08-04~08-05 缺口 → 合并为单一窗口 `W = [2026-08-02T08:30, 恢复时点]`，避免同一批文章被两个窗口重复计数。

**限流规则**：单次运行**每库 ≤3 篇、全局 ≤15 篇**（即 1 个日常配额），剩余顺延至次日 A0.2 继续，直至 `pending_windows` 清空。

**优先级**：窗口内 `new_pool` 按 `SELECT_3` 价值评分降序；同分取 `create_time` 较早者，保证覆盖不跳跃。

**两种节奏（择一）**：

| 节奏 | 做法 | 补齐耗时 | 适用 |
|------|------|---------|------|
| 保守（推荐） | 融入每日 08:30 自动化，每天补 15 篇 | 视真实新增量，通常 1–4 天 | 无需人工干预，不撑爆单次会话 |
| 集中 | 恢复当天手动连跑 2–4 轮 | 当天补完 | 急需 IMA 知识立即入库 |

> 实际回补量取决于窗口内**真实新增数**，而非理论满额 60 篇。安静日新增少时，1 天即可补完。

### 阶段 4 · 加固（防复发，A0 升级 v1.12）

在 A0.1 之前插入 **A0.0「连接器启用态自检与自愈」**：

1. 读取 `connector-states.v3.json`，检查 `ima-mcp` 是否在 `enabled` 且 `userDisabled` 为假；
2. 若否 → 自动备份并翻转两字段，在报告中标注 `已自愈-连接器启用态-<日期>`，提示"下次运行生效（需重启）"；
3. 若 `everConnected` 不含 ima-mcp → 判定为**从未授权**，此类无法脚本自愈，直接在 QQ 摘要中**标红告警**要求人工扫码；
4. **告警升级**：`pending_windows` 连续 ≥2 天未清空时，QQ 摘要主题加前缀 `【⚠IMA漏窗N天】`，避免再次静默积压 4 天。

## 六、经验沉淀

1. **状态类故障优先查配置，而非查网络。** `connected` / `disconnected` 的表面状态不足以定位问题，必须直接读 `connector-states.v3.json` 的 `enabled` / `userDisabled`。
2. **变更日志里的"治本方向"必须落到执行步骤。** v1.10 已识别根因却未固化为 A0 动作，导致认知与流程脱节，空转 4 天。
3. **自愈动作要有告警升级阶梯。** 只登记不升级的告警等同于没有告警——连续 N 天未解决必须提高可见度。
4. **改配置文件前先探测数据类型。** 本机 `userDisabled` 为 dict，按 list 处理会静默损坏结构（本方案脚本已在首轮 dry-run 中捕获并修复该缺陷）。
