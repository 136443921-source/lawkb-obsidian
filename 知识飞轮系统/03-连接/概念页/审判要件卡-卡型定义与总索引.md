# 审判要件卡（Trial Element Card）· 卡型定义与总索引

> **一句话**：审判要件卡回答**「该怎么判」**（正向裁判规则）；要件映射卡回答**「有没有引错」**（负向涵摄拦截）。**这是两套东西，不可互相替代。**

---

## 一、为什么必须新增这一卡型（关键区分）

| 维度 | 要件映射卡（已有） | **审判要件卡（本卡型）** |
|------|------------------|------------------------|
| 载体 | `lti_element_cards.json` + `lti_semantic_rules.json` | 知识飞轮规则卡 `R-PI-*` / `R-PR-*` |
| 回答的问题 | 「引用错了吗？」 | **「该怎么判？」** |
| 推理方向 | **负向拦截**（涵摄断裂检测） | **正向裁判**（审理思路→裁判结论） |
| 触发时机 | 文书生成**后**校验 | 庭审推演**中**引导推理 |
| 典型输出 | 「1165 不是无过错责任，请区分 1166」 | 「先查四要件，再按顺位比对，支持/不予支持分别是……」 |
| 消费方 | LTI 文本监控器（闸门） | **模拟法庭 `judge_reviewer`（法官心智）** |

> **结论**：把审判要件内容硬塞进 `lti_element_cards.json` 会破坏其负向拦截的语义纯度；反之，用负向拦截规则指导裁判则会陷入「只知不能怎么判、不知该怎么判」的困境。**必须物理隔离、双轨并行。**

## 二、字段规范（v1.0）

沿用《规则卡编号体系规范 v1.0.0》的编号与 frontmatter 骨架，**新增审判要件特有字段**：

```yaml
rule_id: R-PI-215              # 强制，白名单域码 + 三位补零
card_type: 审判要件卡           # 【新增强制】用于与要件映射卡物理区分
review_step: 第七部分 第三节一(一)   # 【新增】审理环节定位
elements:                      # 保留（与现有卡同构，可复用三元闸门）
  - id: E1
    name: 要件名
    desc: 涵摄内容
ruling:                        # 【新增·核心】正向裁判规则
  support: 支持的条件与结论
  reject: 不予支持/驳回的条件与结论
burden_of_proof: 举证责任分配   # 【新增】
geo_scope: 贵州省（…）          # 【新增】地域效力标注
negative_sample: true          # 保留（负向兼容）
negative_note: 翻车标本
```

**正文八段结构**（固定）：
1. 裁判规则（正向 · 该怎么判）—— 支持 / 不予支持
2. 审查要点（审理思路）
3. 构成要件与举证（elements 表 + 举证责任）
4. **法条依据（权威源回填，非凭记忆）**
5. 抗辩与但书
6. 翻车标本（负向拦截 · HIR）
7. 来源与地域效力
8. 关联（知识飞轮连接层）

## 三、铁律（建卡与使用均须遵守）

1. **法条正文回填铁律**：卡内 `elements` 仅描述要件，**绝不内嵌法条正文**；法条正文必须从本地权威源（`Documents/LawKB/法律法规库/`）或北大法宝/华宇元典核填，并标注来源与「现行有效」状态。
2. **铁律 R2（机器仅候选）**：审判要件卡给出的裁判结论是**候选推理**，不是自动裁判。法官/律师须结合个案证据人工拍板。
3. **地域效力标注铁律**：本书系贵州省高级人民法院组织编写的**裁判尺度统一指引，非全国统一司法解释**，跨省援引须核实当地口径。
4. **编号铁律**：域码只能用白名单 14 域（本次用 `PI` / `PR`），序号实地查库取最大值 +1，禁止凭记忆取号。

## 五、消费方式：法官心智四步推理链（judge_reviewer）

模拟法庭 `judge_reviewer`（Reviewer & Procedural Commander）在实质审查阶段消费本卡型，按四步推进：

1. **定位审理环节** → 用 `review_step` 确定当前处于「原告诉请审查 / 被告抗辩审查 / 争议裁判规则」哪一环；
2. **逐项涵摄** → 用 `elements` 逐项比对本案事实是否落入要件；
3. **举证校验** → 用 `burden_of_proof` 判断哪一方未完成举证；
4. **裁判预判 + 但书提醒** → 用 `ruling.support` / `ruling.reject` 给出**候选结论**，并同时触发 `negative_note` 提示翻车风险。

> 输出仍须遵守 **铁律 R2**：机器只给候选，法官人工拍板。
