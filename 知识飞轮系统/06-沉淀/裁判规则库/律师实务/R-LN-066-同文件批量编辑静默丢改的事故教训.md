# 回显成功 ≠ 落盘成功：同文件批量编辑静默丢改的事故教训

> **卡型**：工程事故卡（AI 协作·文件编辑通道）｜**编号**：`R-LN-066`｜**建卡日期**：2026-09-08
> **事故等级**：P1（卡片**正文 0 处错误**，但**同消息同文件多 Edit 仅首条落盘**，总索引 3 处 + 编号规范 3 处共 **6 处挂载修改静默丢失**，险致六层挂载不一致）
> **一句话**：**工具回显「Successfully edited」只代表请求被受理，不代表所有变更都已持久化。** 一条消息对**同一文件**发多个 Edit，后到的写请求会基于原始快照覆盖先到的——于是除首条外全部静默蒸发，而你还以为都改好了。

## 一、事故概述（发生了什么）

2026-09-07/08 序5 抚养纠纷（36 张卡，R-HY-056~091）六层挂载收尾。主卡已落盘，需把挂载信息同步进枢纽文件。

**收尾时（踩坑）**：在**同一条消息**内，对**同一文件**发出多个 Edit 调用——

| 目标文件 | 本消息内 Edit 数 | 实际落盘 | 静默丢失 |
|---|---|---|---|
| `03-连接/概念页/审判要件卡-卡型定义与总索引.md` | 4（frontmatter version / 共227→263 / §4.10 整块 / 1.8.0 changelog） | **仅第 1 个**（frontmatter） | **3 处** |
| `06-沉淀/裁判规则库/_规则卡编号体系规范.md` | 6（frontmatter / §2 HY 在库 55→91 / §7 基线 055→091 / §8 第八批块 / 变更记录 / …） | **仅第 1 个**（frontmatter） | **3 处** |

**每个 Edit 均回显「Successfully edited」**，于是我判定挂载完成，继续推进。

**复验时（暴露）**：因跨文件引用对不上，触发 `Grep` 复验，发现——
- 总索引**仍是「共 227 张」**、**无 §4.10**、**无 1.8.0 changelog**；
- 编号规范 HY 基线**仍是 055**、在库**仍是 55**。

→ 确认：**同消息同文件多 Edit 仅首条生效，其余虽回显成功却被静默丢弃**。

**根因一句话**：同文件并发写——多个 Edit 请求针对同一文件，底层以「读原快照→改→写」而非「增量链式」执行，后写者用原始快照覆盖先写者，最终仅首条（或最后基准态）可见；回显层与落盘层不一致，失败静默无报错。

## 二、根因分析（三层，逐层往下挖）

**第一层·直接原因**：同文件并发写覆盖。一条消息内的多个 Edit 并非串行链式合并，而是各自基于消息发起时的文件快照计算 diff 并写回；当目标为同一文件时，后完成的写请求用**旧快照**覆盖了先完成的写请求的结果，造成除一个基准态外全部丢失。回显「Successfully edited」仅表示「该次请求已被处理」，**不表示它在最终文件里可见**。

**第二层·流程缺陷（真正致命的一层）**：**缺少「改后 Grep 复验」作为写后门禁**。
交付校验器只查卡片**内部**一致性（YAML、字段、八段、法条块、死链），**完全不查枢纽文件的挂载是否真的写进去了**。回显成功给了我虚假的安心感，于是**跳过了「改完用 Grep 实地核一遍落盘」这一步**。

**第三层·认知盲区（最隐蔽的一层）**：**「省消息」冲动压倒「一处一改」纪律**。
把多改压进一条消息看似高效，实则违反了工程上「一次只改一件事、改完即验」的基本原则。批量编辑的「省」是以「不可见的丢失风险」为代价的——而这恰恰是静默失败最爱走的门。

## 三、误判传导链（错一步如何滚成一串）

```
① 一条消息对总索引发 4 个 Edit → 仅 frontmatter 落盘
      ↓ 4 条均回显 Successfully edited，误以为全改好
② 同消息对编号规范发 6 个 Edit → 仅 frontmatter 落盘
      ↓ 同样回显成功，未起疑
③ 推进跨文件引用（消费方 / LOG / 入库索引）基于"已挂载"的假设
      ↓ 引用目标实际不存在（总索引无 §4.10、规范无 §8 第八批块）
④ 跨文件对不上 → 触发 Grep 复验
      ↓ 发现总索引仍 227、规范 HY 仍 055
⑤ 认清静默丢改 → 把 3 + 3 = 6 处漏改逐条拆成单独消息重发
      ↓ 每条消息仅含该文件一个 Edit，全部落盘
⑥ Grep 复验 → 六层挂载一致；顺手去重总索引重复 1.8.0 changelog 行
```

**关键**：链条上**每一步单看都合理**（批量编辑本就是常见操作），且**没有任何一步报错**。静默失败的可怕之处正在于此——它不报警，只蒸发。

## 四、代价清单（量化）

| 项 | 数值 |
|---|---|
| 受影响枢纽文件 | 2 份（总索引 / 编号规范） |
| 静默丢失修改 | **6 处**（总索引 3 + 编号规范 3） |
| 卡片正文错误 | **0 处**（主卡本身完好，问题在挂载层） |
| 险致后果 | 六层挂载两文件不一致、跨文件引用错位；若未复验直接交付，校验器 ERROR 0 仍会通过（校验器不查挂载完整性） |
| 关联残留 | 总索引出现**重复 1.8.0 changelog 行**（本卡已顺手去重） |
| 修复方式 | 6 处漏改逐条拆成单独消息重发 + Grep 复验 |
| 修复总耗时 | 约 25 分钟（复验 + 拆消息补 Edit + 重校验） |

**六处静默丢失的具体内容**：

| # | 文件 | 丢失的修改 | 为何危险 |
|---|---|---|---|
| 1 | 总索引 | 「共 227 张」→「共 263 张」未生效 | 索引总数失真，后续取号基线漂移 |
| 2 | 总索引 | §4.10 抚养纠纷整块未插入 | 消费方/调用方找不到第八批索引锚点 |
| 3 | 总索引 | 1.8.0 changelog 行未追加 | 版本追溯断点（且后续补发时造成重复行） |
| 4 | 编号规范 | §2 HY 在库 55→91 未生效 | 域容量统计失真 |
| 5 | 编号规范 | §7 HY 基线 055→091 未生效 | **取号铁律物理基线错误**，下一可用号算错 |
| 6 | 编号规范 | §8 第八批块未登记 | 批次溯源缺失 |

**共同特征**：六处都是「看起来改完了」的静默丢失，**只有 Grep 实地核才拦得住**。

## 五、正确做法（SOP：同文件编辑三铁律，不许跳步）

**铁律一 · 同文件多处修改，必须分多条消息逐个 Edit**
- ✅ 一条消息**只含该文件的一个 Edit**；N 处修改 = N 条消息。
- ❌ 不在一条消息内对**同一文件**发多个 Edit。
- 理由：同文件并发写会以旧快照互相覆盖，仅首条可见，其余静默蒸发。

**铁律二 · 跨文件批量可并行，但同文件仍须拆**
- ✅ 一条消息可对**多个不同文件**各发**一个** Edit（跨文件互不影响，安全）。
- ❌ 即使一条消息里对 A 文件发 2 个、对 B 文件发 2 个，A/B 各自的 2 个仍会各自静默丢改。
- 口诀：**「跨文件并行安全，同文件必拆单条」**。

**铁律三 · 批量写后必须 Grep 复验落盘，不只看回显**
1. 全部 Edit 发完之后；
2. 用 `Grep` / `Read` **实地核一遍关键落盘点**（数量变更、新增章节、changelog 行）；
3. 回显「Successfully edited」**不等于落盘**——以复验结果为准；
4. 跑通用死链/一致性自检脚本（`_check_deadlinks.py`），确认零死链、跨文件引用对齐。

**判定「挂载是否真写好」的完整流程**：① 逐文件单条 Edit → ② 每条发完即 Grep 核该处落盘 → ③ 全量跑死链自检 → ④ 不一致立即拆消息补 Edit。本卡是 R-LN-055 / R-LN-059 的**编辑通道补丁**——R-LN-055 解决「查不到 ≠ 不存在」，R-LN-059 解决「此刻不存在 ≠ 永远不存在」，**本卡解决「回显成功 ≠ 落盘成功」**。

## 六、翻车标本（负向拦截·同类错误清单）

1. ❌ 一条消息对同一文件发 4 个 Edit → ✅ 拆成 4 条消息逐个 Edit
2. ❌ 把工具回显「Successfully edited」当落盘证明 → ✅ 改后必 Grep 复验
3. ❌ 为省消息把多改压进一条 → ✅ 一处一改，用消息数换安全性
4. ❌ 认为「批量 = 快」→ ✅ 同文件批量 = 风险，跨文件批量 = 安全
5. ❌ 交付校验 ERROR 0 就以为挂载全齐 → ✅ 校验器不查挂载完整性，须人工 Grep 复验
6. ❌ 一条消息对两文件各发多 Edit → ✅ 同文件多 Edit 仍须拆；跨文件各一 Edit 可并行
7. ❌ 依赖「看起来合理」判断落盘 → ✅ **凡不进校验器的东西，就一定会被写错**（与坑 16「强判断表述不受 E9 约束」、坑 17「门禁静默降级」同源）
