# 迁移清令牌 → 批量假连接：MCP 安全迁移批量清令牌的根因指纹与一次性根治

> **卡型**：连接诊断卡（AI 协作·连接器根因）｜**编号**：`R-LN-113`｜**建卡日期**：2026-09-16
> **事故等级**：P0（多个主源连接器集体掉线，法条核验主链路中断；叠加业务层错误被误判为"单点反复坏"才显反复）
> **一句话**：**`connector-status` 全绿、调用全挂，且多个受管 MCP 同一时间一起掉——这不是三个独立故障，是平台级 MCP 安全迁移（v3→v4）批量清了所有 Bearer 令牌这一个事件"被依次发现"。判定式：落盘三标志全 True + 多个 `enabled=true` 却无令牌 = 迁移清令牌；处置 = 一次性全部重新授权，别逐个修。**

## 一、现象（老强一周内的真实体感）

2026-09-09 至 09-16，连接器"依次出问题"：先是 ima，再是华宇元典，现在是北大法宝，"都存在问题、修不完"。

**实测真相（2026-09-16 只读诊断 `~/.workbuddy/connectors/75c7265a-5f11-4420-9e71-be28329d68fd/connector-states.json`）**：

| 连接器 | enabled | bound | headerOverrides 有令牌? | 判定 |
|---|---|---|---|---|
| pkulaw | true | — | ❌ 无 | **亚型B 假连接** |
| yuandian-mcp | true | — | ❌ 无 | **亚型B 假连接** |
| gongyi-open-mcp | true | — | ❌ 无 | **亚型B 假连接** |
| qq-mail | true | — | ❌ 无 | **亚型B 假连接** |
| tencent-weiyun | true | — | ❌ 无 | **亚型B 假连接** |
| qcc-legal | true | — | ❌ 无 | **亚型B 假连接** |
| ima-mcp | false→09-16 翻 true | true | ✅ 有 | 亚型A（更早旧问题，已修） |
| kdocs / github / tencent-docs | false | — | ✅ 有 | 废弃条目（仅存的令牌在此） |
| ima-mcp-oa | ❌ 条目缺失 | — | — | 亚型C（司内版，UI 无注册入口） |

**关键体感矛盾**：UI 显示这些连接器 `connected`（因为 `enabled=true` 进了已连接列表），但一调用就 `未连接 / 401 Bearer missing`。——这正是"假连接"的招牌表现。

## 二、根因指纹（决定性，一眼区分"迁移清令牌"vs"单点随机坏"）

**迁移事件落盘三标志同时为真**（在 `connector-states.json` 顶层）：
- `mcpSecurityMigrated = true`
- `headerOverridesBearerStripped = true`
- `staleManagedAuthHeadersPurged = true`

→ 这是 WorkBuddy 在 **2026-09-09 前后平台级 MCP 安全迁移（connector-states schema v3→v4）** 时，**批量剥离了 `headerOverrides` 里所有 Bearer 令牌**的落盘铁证。

**为什么能断定是"批量清令牌"而非"随机损坏"（fingerprint）**：
- 迁移后，6 个 `enabled=true` 的在用受管 MCP **令牌全被清**（沦为亚型B 假连接）；
- 而**仅存的 4 个还带令牌的连接器，恰好全是 `enabled=false` 的废弃条目**（kdocs / github / tencent-docs）——它们是"关着的"所以没被重新授权流程覆盖，令牌残留。
- **这个"在用全清、废弃全留"的分布，是迁移清令牌的专属 fingerprint，随机损坏绝不会长这样。**

**判定公式（速判）**：
```
connector-states.json 顶层三标志全 True
  AND 多个 enabled=true 连接器在 headerOverrides 无令牌
  ⇒ 安全迁移批量清令牌（子类：批量亚型B 假连接）
  ⇒ 按"一次性批量重新授权"处置，勿逐个当独立故障排查
```

## 三、为什么感觉"一个一个坏、修不完"（误判传导链）

```
① 9-9 迁移清令牌（单点事件，同一时间戳批量发生）
      ↓ 但用户不是同时发现
② 先发现 ima 断 → 修 ima（翻 enabled，实则 ima 是更早的亚型A，叠加混淆）
      ↓ 几天后
③ 发现元典调不通 → 重连 → 仍 402（元典积分不足，业务层D-2，重连无效）
      ↓ 误读"元典又坏了"
④ 发现 pkulaw 调不通 → 重连 → 仍 90001（法宝点数校验失败，业务层D-1，重连无效）
      ↓ 误读"法宝又断了"
⑤ 体感：ima / 元典 / 法宝"依次坏、修不完"
      ✗ 真相：清令牌是一次性事件，被"依次发现" + 业务层错误(402/90001)被误读为"又断线"共同造成反复错觉
```

**最隐蔽的一环**：②③ 的 `402` / `90001` 是**业务层配额错误（亚型D）**，重连/重启/点连接**全都无效**——却因为"刚重连完还报错"被误判成"连接没修好"，于是反复重连、白耗精力。详见 [[R-LN-055-工具调用失败不等于服务不可用的MCP误判事故教训]] 与亚型D 判定（错误体带 `requestId`/`timestamp` = 服务端已处理 = 业务层，非断线）。

## 四、与"单点 OAuth 过期"的区分（别再误判）

| 维度 | 迁移清令牌（本卡） | 单点 OAuth 过期 |
|---|---|---|
| 发生时间 | **同一时间戳、多个受管 MCP 同时掉** | 零散、只坏一个、时间不相关 |
| config 标志 | 带 v4 迁移三标志全 True | 无迁移标志 |
| 令牌分布 | 在用全清、废弃全留（fingerprint） | 仅该连接器令牌失效 |
| 处置 | **一次性批量重新授权全部受管 MCP** | 只修那一个 |
| 业务层叠加 | 常叠加 402/90001 被误读为"又断" | 一般无 |

→ 据此一眼区分根因，避免把批量事件误判为单点反复修（这正是老强这周白耗的坑）。

## 五、正确处置（SOP：一次性根治，不许逐个修）

**铁律一 · 先读 config 确诊，再动手**
- 定位活跃 config：`find ~/.workbuddy/connectors -name connector-states.json`，取 mtime 最新的 UUID 目录那份（version 4）。
- 只读三件套判定：`python3` 读 `connectors{id:{enabled,bound}}` 与 `headerOverrides{id:加密令牌}`；`enabled && id∉headerOverrides` = 假连接。
- **红线**：AI 不代点 UI、不注入令牌、不静默翻 enabled（老强硬性规则）。

**铁律二 · 受管 HTTP MCP 缺令牌 = UI「解绑后重新连接」一次性点亮**
- 实际 UI 按钮名为**「解绑后重新连接」**（= 技能文档早期写的「重新授权 / 信任」，同一动作，按钮名因版本而异）；**别因找不到"重新授权"按钮而绕路**。
- 对这 6 个一次性全部重连（用各自账号走 OAuth，令牌写回 `headerOverrides`）：
  `pkulaw` ｜ `yuandian-mcp` ｜ `gongyi-open-mcp` ｜ `qq-mail` ｜ `tencent-weiyun` ｜ `qcc-legal`
- ⚠️ pkulaw 重连时务必登录**已充值的那个北大法宝账号**（个人版/平台版混淆坑）；连完仍 `90001` = 法宝侧点数问题，重连治不了，去查点数/核对账号绑定。
- ⚠️ 元典连完若 `402` = 积分不足，先 `yuandian_get_user_balance` 查 `pointBalance`（免费），别 `top_k=50` 猛烧。

**铁律三 · 连完必须重启 WorkBuddy + 开新对话验证**
- 旧会话工具索引**不热加载**：中途重连后，当前对话的 `ToolSearch`/`DeferExecuteTool` 仍报 `not found`，纯属会话级假象，**开新对话即可**，别在旧会话空转重连。
- 重启后复验 `connector-states`：确认 `enabled=true` + 有令牌（应用可能后台回写 `enabled=false`，需再翻）。

**铁律四 · 亚型C 条目缺失（ima-mcp-oa 类）UI 无注册入口则忽略**
- 连接器页面只有「解绑后重新连接」、**没有完整注册入口**；个人版（ima-mcp）已健康，司内版用不到就直接忽略，别硬找按钮。

**铁律五 · 业务层与连接层分治（见亚型D）**
- `402` / `90001` / `403` 是配额/权限，**重连/重启无效** → 去充值或核对账号，不并入"连接修复"反复操作。

## 六、翻车标本（负向拦截·同类错误清单）

1. ❌ 看到 ima / 元典 / 法宝"依次坏"就当三个独立故障逐个修 → ✅ 先读 config 看迁移三标志，判"批量清令牌"一次性处置。
2. ❌ 重连后还 `90001`/`402` 就以为"连接没修好"反复重连 → ✅ 那是业务层配额错误（亚型D），重连无效，去查点数/积分。
3. ❌ 在 UI 找"重新授权/信任"按钮找不到而绕路 → ✅ 实际按钮是「解绑后重新连接」，等价动作。
4. ❌ 旧会话里调不到工具就判"没修好" → ✅ 会话工具索引不热加载，开新对话验证。
5. ❌ 只看 `connector-status` 显示 connected 就信"能用" → ✅ status=connected 仅代表配置生效，**不代表 upstream API 鉴权通过**（90001 期间 status 一直绿）。
6. ❌ 逐个受管 MCP 等到用才修 → ✅ 迁移清令牌后一次性全部重新授权，配每日守卫主动播报。
