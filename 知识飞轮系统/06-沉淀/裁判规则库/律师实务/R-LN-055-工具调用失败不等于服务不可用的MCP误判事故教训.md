# 工具调用失败 ≠ 服务不可用：ToolSearch 拼错名误判 MCP 断线的事故教训

> **卡型**：工程事故卡（AI 协作·法条回填通道）｜**编号**：`R-LN-055`｜**建卡日期**：2026-09-06
> **事故等级**：P1（未污染法条正文，但导致法源降级 + 漏引现行新规）
> **一句话**：**「我查不到」和「它不存在」是两回事。** 把检索失败直接当成服务不可用，会在无人报错的情况下让整批成果降级——且**降级本身是静默的**。

## 一、事故概述（发生了什么）

2026-09-06 拆《贵州法院类案审判要件指南（第二卷）》第四部分·新就业形态劳动争议（36 张卡，R-LD-010~045）。建卡需回填法条正文，按铁律须走权威源。

我先后用 ToolSearch 查了 `yuandian_law_vector_search`、`mcp__yuandian__yuandian_law_vector_search` 等名字，**均返回查不到**，遂在日志、汇报、记忆里三处写下：「**元典与北大法宝 MCP 本会话均不可用**」，并据此**降级**走公开网页源（gov.cn / mohrss.gov.cn 等）逐条核填 12 部 46 条。

**真相（老强追问后实地复核）**：两个 MCP **全程可用**——

| 证据 | 结果 |
|---|---|
| `~/.workbuddy/connectors/75c7265a-.../connector-states.json` | `pkulaw: enabled=True`、`yuandian-mcp: enabled=True` |
| 华宇元典 `yuandian_law_vector_search` 真调用 | 成功，返回劳动合同法第 82 条原文 |
| 北大法宝 `get_article`（劳动合同法·第七条）真调用 | 成功，返回原文 + `timeliness: 现行有效` |

**根因一句话**：连接器命名空间是 `yuandian-`**`mcp`**（带连字符），我凭语感写成 `yuandian`，且裸名不带 `mcp__` 前缀根本不在工具表里。

## 二、根因分析（三层，逐层往下挖）

**第一层·直接原因**：工具名拼错。

| 我查的（❌） | 正确全名（✅） |
|---|---|
| `yuandian_law_vector_search`（裸名，无 `mcp__` 前缀） | `mcp__yuandian-mcp__yuandian_law_vector_search` |
| `mcp__yuandian__yuandian_law_vector_search`（**漏 `-mcp`**） | `mcp__yuandian-mcp__yuandian_law_vector_search` |
| （法宝名未正确拼出） | `mcp__pkulaw__mcp-law-search-service.get_article` / `.search_article` |

**第二层·方法论错误（真正致命的一层）**：以「检索失败」推断「服务不可用」，**跳过了真调用验证**。
ToolSearch 只是**查工具表**，查不到只能证明「这个名字不在表里」，**证明不了服务断线**。二者之间隔着一整个验证环节，我一步跨过去了。

**第三层·认知错误**：用 `~/.workbuddy/mcp.json` 判断连接器是否配置。
✅ 事实：**pkulaw / yuandian / ima 等是内置连接器**，配置在 `~/.workbuddy/connectors/<uuid>/`，**不在 mcp.json**（该文件当前只有 `fasui-caselibrary`、`obsidian`）。
→ 我拿一份**不完整的清单**去证否，是典型的**以偏概全**。

## 三、误判传导链（错一步如何滚成一串）

```
① ToolSearch 拼错名 → 查不到
      ↓ 未做真调用验证
② 误判「MCP 不可用」
      ↓ 顺手找了个"证据"加强错觉
③ 发现 mcp.json 没有 → 坐实「没配」（实为不完整清单，是伪证）
      ↓ 据此决策
④ 46 条法条降级走公开网页源（慢、且检索面窄）
      ↓ 隐性代价，无人报错
⑤ 漏掉法释〔2025〕12号劳动争议解释（二）第六、七条
      ↓ 传导到成果
⑥ R-LD-024（二倍工资三类除外）未引现行新规，埋下适用争议
      ↓ 写进记忆
⑦ 错误结论入自动化记忆 → 若无人纠正，下一批（序 4）会**继续走降级通道**
```

**最危险的是 ⑦**：错误一旦写进记忆/技能，会**跨会话自我复制**。这才是 P1 而非 P2 的原因。

## 四、代价清单（量化）

| 代价项 | 量化 |
|---|---|
| 法条降级 | 12 部 / 46 条由元典/法宝降为公开网页源 |
| **实质遗漏** | **法释〔2025〕12号《劳动争议解释（二）》第六、七条全文未引**（2025-09-01 施行） |
| 受影响卡 | **R-LD-024**（二倍工资三类除外）；劳动报酬组 R-LD-022 起应补第六条计算规则 |
| 标注被迫降级 | 卡内统一改标「权威源核填」（不能虚标「元典核填」） |
| 校验器被污染 | 为适配降级通道，把 E8 校验口径扩到接受「权威源核填」——**校验器被错误结论带着改** |
| 时间成本 | 46 条逐条翻网页，远慢于一次语义检索 |
| 好的一面 | 事后回源复核：**第十一条与元典逐字一致**，公开源核填质量本身**合格**，未产出错误法条 |

## 五、正确做法（SOP：判定「MCP 不可用」六步，不许跳步）

1. **精确查全名**：`ToolSearch(tool_names=["mcp__<connector>__<tool>"])`，名字**照抄** `available_deferred_tools` 列表，**不凭语感拼**；
2. **模糊兜底**：查不到 → 改 `ToolSearch(queries=["关键词"])`；
3. **查门禁**：读 `~/.workbuddy/connectors/<uuid>/connector-states.json` 看 `enabled`（**活跃 workspace = mtime 最新的 UUID 目录**）；
4. 🔴 **真调用一次**（关键步骤）：`DeferExecuteTool` 实跑一次看真实报错——**ToolSearch 查不到 ≠ 服务不可用**；
5. **别用 mcp.json 证否**：内置连接器不在其中；
6. **才允许降级**，且降级须**留痕 + 事后回补**：卡内标注写「**权威源核填**」（绝不虚标「元典核填」），并在日志登记「待回源复核」。

**配套铁律两条**：
- **降级通道不得反向修改校验器口径**——本批为迁就降级改了 E8，等于让校验器为错误结论背书。正确做法：校验器保持严格，降级卡单独标记待复核。
- **错误结论不入记忆**；若已写入，**下一轮必须回头订正**（本卡即为该动作的产物）。

## 六、翻车标本（负向拦截·同类错误清单）

> ⚠️ **翻车一·以检索失败证否存在**：`A 查不到` 推不出 `A 不存在`。检索工具的失败原因有 N 种（名字错、命名空间错、未加载、权限），"服务断线"只是其中之一。
> ⚠️ **翻车二·用不完整清单做全称判断**：拿 `mcp.json` 里"没有"推出"没配"，忽略内置连接器目录。**先确认清单是否完备，再判断成员有无。**
> ⚠️ **翻车三·跳过真调用验证**：这是本次事故的分水岭。**一次 3 秒的实跑就能戳破整个误判。**
> ⚠️ **翻车四·为迁就临时降级而改校验口径**：把质量闸门降低以适配次优路径，是最隐蔽的一类污染。
> ⚠️ **翻车五·错误结论跨会话复制**：写进 automation memory 后，下一批自动沿用。**订正必须回头改源文件，不能只在口头说一句。**
> ⚠️ **翻车六·把"降级"当成"完成"**：降级是权宜，不是交付标准。46 条降级后未登记回补计划，直到老强追问才暴露遗漏。
