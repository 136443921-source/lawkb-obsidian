# 工具事故卡：监控驾驶舱僵尸进程与 socket 残留骗过健康检查

> **事故回放**：错值 + 真值 + 复测命令（O2 信条 2：无复测命令不建卡）
> 复测命令 1：`ps -ax -o pid,command | grep -i "lti-gate" | grep -v grep`
> 实测值 1：`NO_LTI_GATE_PROC`（进程已死，仅 `/tmp/lti-gate.sock` 残留）
> 复测命令 2（初误判）：`socket.connect + send(json) 无换行` → recv 超时
> 复测命令 3（修正）：`send((json+'\n'))` → `PONG {"pong": true, "ts": "2026-09-18T09:26:21"}`
> 错值：`cockpit_data.json` 报 `"daemon_running": true` / `"daemon_status": "✅ 运行中"` / 门禁运行度 60
> 真值：门禁守护进程在会话间已死亡，驾驶舱显示的是**过时/失真健康态**

## 一、事故概述（发生了什么）
- 触发场景：9655 单机驾驶舱交付前核验，门户 `http://127.0.0.1:9655/` 返回 200，误以为整套系统健康。
- 表象现象：驾驶舱「门禁运行度 60 / ✅ 运行中 / daemon_running=true」，看板一片绿。
- 损失/影响面：若直接交付，驾驶舱第一项核心指标就是**假阳性**——一个以"监控健康度"为使命的面板，自己先报了假健康。诚实性破产。

## 二、根因分析（三层，逐层往下挖）
- 第一层（直接原因）：门禁守护进程（lti-gate-daemon）在两次对话会话之间被回收/死亡，仅残留 `/tmp/lti-gate.sock` 文件；而早期误判检测逻辑可能依赖"socket 文件存在"判定存活。
- 第二层（机制原因）：监控类驾驶舱的健康检查**没有统一"探活进程/探真实响应"的硬标准**；本次 `scan_gate` 实际用 `pgrep -f` 探进程（可靠），但进程确实死过，数据曾反映过时状态，且缺"交付前实探真实状态"闭环。
- 第三层（系统原因）：后台守护进程以裸 `run_in_background` 启动，**无保活（launchctl/KeepAlive）**，跨会话必死；部署/交付流程缺"交付前实探真实状态"的强制门禁。

## 三、误判传导链（错一步如何滚成一串）
| 步 | 我的误判 | 实际 |
|---|---|---|
| 1 | 门户 HTTP 200 = 全系统健康 | 只证明 http.server 在，不代表门禁 daemon 在 |
| 2 | `cockpit_data.json` 写 daemon_running=true = 现在在跑 | 那是 09:15 扫描时的快照，进程之后已死 |
| 3 | 初测 socket ping 超时 = 守护进程逻辑有 bug | 实际是我客户端漏了 `\n`（行分隔协议），误伤判断 |
| 4 | 补 `\n` 后 PONG 通 = 一直没问题 | 真正问题是"之前死过、且交付前没人实探" |

## 四、代价清单（量化）
- 时间成本：约 2 轮对话 + 多轮 ps/socket 复测才定位，约 30 分钟。
- 数据风险：若未复测直接交付，驾驶舱假阳性会反向污染老强对系统真实健康度的判断。
- 下游影响：9655 驾驶舱公信力受损；若作为"监控面板"范本推广，同类假阳性会复制。

## 五、正确做法（SOP：N 铁律，不许跳步）
1. **探活不探文件**：健康检查必须探"活进程 / 真实响应（PONG/HTTP 200 on the actual service）"，绝不用"socket 文件存在""端口可连"当存活证据。
2. **交付前实探闭环**：任何监控驾驶舱交付前，必须逐项实地复测数据文件中的状态字段与真实进程/服务一致，不一致即标红而非美化。
3. **后台进程必保活**：守护进程走 `launchctl load` + `KeepAlive`（plist 已就位），或至少是带自动重启的 supervisor，禁止裸跑跨会话死。
4. **客户端对齐协议**：行分隔（JSONL）服务的测试客户端必须发 `\n`，否则 recv 阻塞误判——写进测试脚本固化。

## 六、翻车标本（负向拦截·同类错误清单）
- [ ] 把"门户可达"当"子系统全健康"
- [ ] 用"socket 文件存在"判定进程存活
- [ ] 拿历史扫描快照当"当前真实状态"交付
- [ ] 测试客户端漏协议分隔符导致 recv 超时，误判服务有 bug
