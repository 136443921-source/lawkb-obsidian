# LTI 文本监控器 · 防法律幻觉能力【再评估】

> **目的**：三轮终评（2026-08-30）给出「80.6% 检出率 / 0% 误报 / 两条硬边界」画像，并把 P2 在线核验标为「待决策，理论上可逼近 95%+」。
> 但 SKILL.md v4.8.0（08-26）变更日志已声明「元典在线核验封装落地（P0/P1/P2）」，且 `yuandian_verify_cache.json` 实测已回填 7 条。
> **本评估用实跑代码的方式，核对 P2 到底把能力推到了哪**。结论可能让「P2 逼近 95%」的预期降温。

## 一、结论先行（修订版）

| 项目 | 三轮终评（08-30） | 本再评估（08-31 实测） | 变化 |
|---|---|---|---|
| 总检出率 | 80.6%（29/36） | **维持 80.6%**（硬边界未突破） | 无变化 |
| 误报率 | 0%（0/18） | **维持 0%**（P2 仅附注不阻断，不引入误报） | 无变化 |
| 细节编造（条号对+内容改） | 0/4 | **0%（实跑用例5 静默放行，复现）** | 无变化，P2 未补 |

> **一句话**：v4.8.0 的 P2 把"元典核验缓存"机制落了地，但**只落地了"时效状态附注"，没有落地"条文内容相似度比对"**。所以两条硬边界（细节编造 / 案例存在性）在当前实现下**依然 100% 漏检**。三轮终评预期中"P2 理论上可逼近 95%+"的增量，**在当前代码中并未兑现**。

## 二、v4.8.0 P2 机制实测（读代码 + 跑缓存）

### 2.1 缓存现状（08-30 22:22 最后回填）
`provision_index/yuandian_verify_cache.json` 共 **7 条**，覆盖 **4 部法**：
- 公司法（16条 current / 999条 not_found）
- 慈善法（58条 / 60条 current）
- 劳动合同法（47条 current）
- 民诉法（122条 current）
- 金融稳定法（12条 not_found，草案）

**覆盖度极低**：12 部 R101 表外法律仅 4 部有缓存，且每条多只核验 1 条；高频法（刑法/民法典/刑诉/行诉/工伤/道交）**零缓存**。

### 2.2 `build_annotation` 真相（核心发现）
```python
def build_annotation(text, cache):
    for 每个引用 in 文本:
        v = verdict_for(raw, art_raw, cache)   # 只查缓存返回 state
        if v["state"] != "unknown":
            notes.append({"state":..., "note": v["note"]})
```
- `verdict_for` 只返回 **state**（current/obsolete/not_found/unknown）+ 一条"XX法第N条现行有效/查无此条"的**文本附注**。
- **它完全不读文本中"该条的内容主张"，也不与元典返回的 `content` 做任何相似度比对**。
- 即：**元典 content（条文原文）被取回、被缓存，但 LTI 当前只用它的 `sxx`（时效字段），不比对其正文**。

### 2.3 生效条件（"代码落地 ≠ 能力生效"）
- `wrap_output(..., yuandian_verify=cache)` —— **必须调用方主动传缓存参数**，否则 `yv_notes=[]`，P2 完全静默不生效（`main.py:824` `if yuandian_verify:` 才触发）。
- 默认调用（不传参）下，P2 贡献 = 0。
- 即便传了缓存，P2 **只附注、不 REJECT**（不进自动阻断链，SKILL.md 明确"避免外部网络依赖影响确定性"）。

## 三、实证 5 用例结果

| 用例 | 构造 | 实测结果 | 谁拦的 / 谁没拦 |
|---|---|---|---|
| G1 慈善法60条"管理费用10%" | 条号对、主题词挂错（管理费用≠60条） | `[R102] 管理费用应对应第61条` + 元典附注 current | **R102 主题词错配拦截**（非P2） |
| G1b 劳动合同47条"半个月工资" | 条号对、主题词挂错（经济补偿≠47条） | `[R102] 经济补偿应对应第46条` + 元典附注 current | **R102 主题词错配拦截**（非P2） |
| H0 公司法999条"股东会每季度" | 越界条号 | `REJECT [R101] 第999条超出约266条` | **R101 本地阻断**（P2 not_found 没机会发挥） |
| CTRL 慈善法60条正确引用 | 正确 | 仅元典附注 current，无告警 | 正确放行 ✅ |
| **CTRL 民法典586条"30%"** | **条号对+主题对+只改数字（真细节编造）** | **完全静默放行，零提示** | **R109/R102/P2 全部漏检** ❌ |

### 设计教训（诚实校准）
- G1/G1b 看似"内容篡改"，实为**"主题词挂错条号"**——这是 R102 的主题词↔条号映射能力，与"同一条号内数值/措辞篡改"是**两回事**。R102 能拦前者，P2 与 R102 都拦不住后者。
- 真正复现三轮终评"细节编造 0/4"的是 **CTRL 用例（民法典586条30%）**：条号 586 正确、主题"定金"正确（R102 静默）、数值 20%→30% 被改——**LTI 全模块静默**，P2 缓存无民法典586条故不触发。
- 此用例 1:1 复现三轮终评 G1（民法典586条定金20%→30%），**实锤 P2 未补该边界**。

## 六、真正打通硬边界需要什么

1. **内容相似度比对层（缺失的核心）**：在 `build_annotation` 中，对命中缓存的引用，将「文本中该条的内容主张」与「元典 `content`」做语义/关键词比对，差异超阈值 → WARNING（如"586条主张30%，元典原文为20%"）。这是 P2 方案的原意，但当前未实现。
2. **缓存自动填充**：调用方交文书时自动 `extract_verify_requests` → 调元典 → `record_verification` 回填，而非依赖人工/AI 手工三步（否则缓存永远 7 条）。
3. **默认启用**：`wrap_output` 内部自动 `load_cache()` 消费本地缓存（无需调用方传参），让 P2 默认生效（保留"掉线/无缓存→静默"降级）。
4. **高频法本地建索引扩面**：R109 仅覆盖刑法/民法典，应扩至公司/慈善/劳动等高频法，使"同条号内容篡改"至少在这几部法内被本地 R109 抓到（不依赖元典）。

---

## 七、一句话结论

**LTI 仍是「形式层严密 + 局部内容层精准 + 时效实证有背书」的校验器，且始终零误报；v4.8.0 的 P2 把元典数据通道打通了，但只用了"时效字段"这一角，条文正文比对这最关键的一跳没做。所以"引用是否越界"它判得干脆，"引用是否真实（内容被改/案例伪造）"它依然判不了——这条硬边界，代码层面尚未被 P2 打通。**
