# IMA 摄入量衰减诊断报告（修订版 v2）
> **🗂️ 相关笔记**：[[IMA候选池开采规程-v1.18|本诊断的修复方案已落地为该规程]] · [[华宇元典MCP评估与优化建议-2026-08-30|同日志：元典 MCP 评估]] · [[连接枢纽-运维过程|领域枢纽]]


> **提问**：以前每日能从 IMA 摄取 15 篇，最近几天只有几篇，什么原因？
>
> **v2 结论（修正）**：主因不是「不展开文件夹」，而是 **候选池只取首页 50 条、且未摄入不足 3 篇时未按 S1 规则翻页**。合同库根目录实测 1644 篇文章，摄入脚本只看得到其中第 10~50 条，**第 51 条之后的 1603 篇从未进入候选池**。

> ⚠️ **v1 报告的主因判断有误，已修正**。v1 依据「根目录前 20 条多为文件夹」推断根目录文章稀少；v2 用 `total_size − Σ(顶层文件夹 file_number)` 反推，证实根目录文章量极大。结论以本版为准。

## 二、四重真因（按贡献度排序 · v2 修正）

### 🔴 主因：首页 50 条之后不翻页（v2 新增，贡献最大）

- prompt S1 明文要求：「首页候选不足 3 且库较大时**用 offset 翻页补足**」。
- 但实测：合同库首页 41 篇可见文章里未摄入仅 1~2 篇（远不足 3），**并未触发翻页**，当日就此止步。
- 机制：投喂速度 ≈1~2 篇/天/库，摄入速度 3 篇/天/库。早期首页存量充足 → 15 篇/日；存量吃完后，首页只剩当天新投喂的 1~2 篇 → **跌到 3~6 篇/日**，而第 51 条之后的 1603 篇无人问津。

### 🟠 次因：文件夹混入候选，白占配额

- `select_3()`（`intake_runner.py:533-559`）仅判断 `media_id in ingested_set`，**不检查 `media_type`**。
- 文件夹名命中高价值关键词（"合同协议范本"→合同+范本、"指导性案例"→案例），**评分反而最高、被优先选中**，随后 `can_fetch_content: false` 取文失败 → 白吃 3 篇配额。
- 合同库首页 50 条中 9 条是文件夹，律师库 ≥12 条。

### 🟡 三因：文件夹内文章从未被展开

- `intake_runner.py` 全文 `grep "folder|folder_id|media_type|递归|展开"` → **0 命中**，无任何目录递归。
- 实测传 `folder_id` **有效**（"合同协议范本"658 篇可列出，含 3 层嵌套），属可修复项。
- 此项在 v1 被误判为主因；实为第三顺位（文件夹内约 1170 篇 vs 根目录未触及 1603 篇）。

## 四、修复建议（三选一）

### 🅰️ 方案 A：深度翻页 + 文件夹递归（推荐 · P0）

改 `intake_runner.py`：
1. `crawl_candidates()` —— **cursor 深度翻页**，直到凑够 N 篇未摄入候选或 `is_end`；
2. 递归展开 `folder_id` 子树；
3. `select_3()` 前置过滤 `media_type == 99`。

- **收益**：可开采量 292 → 6394（**21 倍**）；15 篇/日可稳跑一年以上；医疗事故 331 + 工伤 349 + 交通事故 220 主矿脉解锁。
- **代价**：首次需翻页若干次；后续可用"已摄入游标"增量续扫。
- **风险**：低。只读，不改 IMA 数据；`folder_id` 与 cursor 翻页均已实测有效。

### 🅱️ 方案 B：只修深度翻页（次优 · P0）

只做第 1 项（翻页）+ 第 3 项（过滤文件夹），不递归文件夹。

- **收益**：改动最小，立即解锁根目录的 1603+ 篇；15 篇/日 可恢复。
- **代价**：文件夹内 1170+ 篇继续沉睡（含医疗事故 331、工伤 349）。

### 🅲️ 方案 C：只过滤文件夹（最小改动 · P1）

仅加 `media_type != 99` 过滤。10 分钟改完，消灭白占配额。

- **代价**：**治标不治本**，很快再次归零。不建议单独立项。

### 我的建议：🅰️，且 B 是 A 的子集

瓶颈从来不是"每天能吃多少"，而是"能看见多少"。A 把可见范围从「最新 41 篇」扩到「全库 6394 篇」。

## 五、关于「逐篇可开采清单」的说明（重要）

老强勾选的待办「首次全量爬库，产出各库真实可开采清单」，实测结论如下：

1. **库级 / 目录级清单**：已完成，见本报告第一节与「主矿脉」表。
2. **逐篇清单（6102 条 media_id + 标题）**：当前**无法在对话内产出**，原因——
   - MCP 工具每条返回都带 `introduction` 全文，逐篇拉取会把上下文撑爆（估算 600 万+ 字符）；
   - 已尝试走 **IMA OpenAPI 脚本直连**（写好了 `03-连接/scripts/ima_library_crawler.py`），但 `~/.config/ima/` 这套凭证对应的是**另一批知识库**（秘书长职业成长、小哲AI学伴、习水县光伏…，ID 为 base64 格式），对每日摄入那 5 个库返回 `220004 invalid knowledge_base_id`，**两套 ID 体系不互通**。
3. **更好的路径**：其实**不需要预先爬清单**。按方案 A 修好后，流水线运行时自带 cursor 翻页 + 递归，**它自己就是全量爬库**——边翻页边选文、边写 `ingested`，不受对话上下文限制。预先存一份 6000 条清单反而会立刻过期。

> 若老强仍想要一份静态快照：请为这 5 个库开通 OpenAPI 权限（拿到 base64 格式 kb_id），现成脚本 `ima_library_crawler.py` 直接可跑，约 145 次请求、1 分钟内出全量 JSON。
