# 决策卡 · 法条唯一主源铁律 FR-MAIN（DEC-2026-FR-MAIN）

## 一、决策事由（问题是什么）

`LawKB/` 下同时存在 **「法条银行」** 与 **「法律法规库」** 两套法条副本，二者定位不清、同步机制缺失，已产生**静默误标**风险。

**2026-09-27 实测取证**（不凭记忆）：

| 事实 | 实测数据 |
|---|---|
| 两库共有文件 | 66 个 |
| 其中字节不同的 | **63 个**（仅 3 个相同）→ 分叉率 95.5% |
| 原材料仓 md 总数 | 74 |
| 正文自称「现行有效」但 frontmatter 无合法 `sxx` 佐证 | **23 张**（本次已批量补 `sxx: 待核验`） |
| `sxx` 取值违规（括号注释 / 非枚举值） | 14 张 |
| 真·无 frontmatter 裸卡 | 4 张 |
| **P0 疑本实例** | `法律法规库/通用法律法规/中华人民共和国网络安全法（主席令第53号）·关键条文回填版.md` |

**P0 实例说明**：该卡正文写「**时效性：现行有效**」，实为 **2016 版**（主席令第53号、2017-06-01 施行）；经 2025-10-28 主席令第61号修正重新公布，**自 2026-01-01 起施行**现行版为 2025 修正版（八章八十一条）。该卡 frontmatter 却仅有 `created` / `updated`，**无任何版本标记字段** —— 一旦被起草方或自动化当作现行有效引用，即构成**静默误标**，可直接导致文书引错法。

**根因**：原材料仓允许「就地直写、就地定级」，而该仓不具备权威核验能力，导致「无版本标记 + 有生效主张」的缺陷卡可被任意写入。

## 二、决策内容（拍板了什么）

> 依老强 2026-09-27 指令，采纳**方案 A：冻结原材料仓**。

**（1）冻结 `LawKB/法律法规库/` 为只读原材料仓**
- 禁止任何自动化批量写入或改写（含批量改 frontmatter、批量打标、就地定级）；
- 仅用于历史沿革查证与人工溯源；
- 确需处置既有问题时，**只补标记、不改内容**，单文件留痕。

**（2）法条银行保持唯一主源 —— 写入铁律**
> **所有自动化法条更新以法条银行为唯一源。**

**（3）P0 卡处置**：不删文件，改字段（`sxx: 已废止` + `superseded_by`），正文表述同步降级。

**（4）批量降级**：23 张「自称现行有效」卡补 `sxx: 待核验`（其中 4 张裸卡补建最小 fm）。

## 七、事故教训（写入记忆的三条）

1. **「防覆盖复检」的基准必须是原文件**。本轮写完脚本时把复检对象写成了「生成后的新内容」，导致 23 张全被误判「已被外部改动」而拒绝写入 —— 逻辑上等价于「要求文件先变成目标态才准写」，必然永假。**教训：复检 = 当前磁盘内容 vs 原稿快照。**
2. **抽验必须抽清单内样本**。本轮随手挑了两个不在清单里的文件名去核查「是否误报」，白折腾一轮并一度得出错误结论。
3. **自动化 prompt 更新是「整段替换」**。本轮 update 只传前半段，导致原文约 80% 被静默截断；发现后须用原全文重建。教训：**改 automation prompt 前先 `view` 备份原文，改完必须 `view` 回验长度/结尾**。
