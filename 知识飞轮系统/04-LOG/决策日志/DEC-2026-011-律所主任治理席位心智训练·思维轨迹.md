# DEC-2026-011 · 律所主任（治理席位）心智训练·思维轨迹

> 记录 2026-09-15，一场「律所主任 / 管理合伙人（治理席位）心智训练」的七轮演进链：从首轮 D3 系统体检 → 监控僵尸去重 → 调度建表 → 错峰执行 → drift 工具固化 → 四类 PAUSED 处置 → 中枢枢纽页成簇。
> 每个节点遵循决策档案契约：**决策点 / 考虑了什么 / 否决了什么 / 推翻信号 / 落点**。
> 本卡是 **RULE-TRAINING-WRITEBACK（训练记录回写铁律）** + **协议第七条** 在「治理席位」技能上的完整应用样例，补齐 PROJ-005 + WF-047 之外的第三件套（思维轨迹），闭环三件套。

## 背景触发

老强给「小强律师数字分身系统」增设治理席位（律所主任 / 管理合伙人），定位系统管理员：七大职责域 D1 战情研判 / D2 档案管理 / D3 系统运维 / D4 红蓝队业务指导 / D5 子自动化研判 / D6 智能体与工作流运行审计 / D7 质量控制。实质是"如何把一个只管机器、不办案、不判庭的治理智能体造出来，并沉淀进中枢"。当夜连下七轮训练指令，落到 6 个监控僵尸处置、11 项错峰、4 个 PAUSED 处置、调度登记表与漂移比对工具搭建、以及中枢成簇挂载。

## 思维轨迹（决策演进链）

### 节点 1 · 先定 G0 边界再动手（双栈模型前置）

- **决策点**：治理席位只管"这台机器转得好不好"，七职责域 D1–D7；红线三条——不代理任何一方、不判任何一场庭审、不推翻 QC 单场裁决。
- **考虑了什么**：从系统管理员视角切入；引入双栈模型（业务栈 L0–L5 ∥ 治理栈 G0–G5），治理席位落在 G 栈；与 QC 划界——QC 出单场战术否决权，治理席位出跨场战略结论，关系"QC 出数据、治理席位出结论"。
- **否决了什么**：否决"治理席位兼做业务裁判 / 介入个案"——越界即破坏 G0 定位，且会与业务智能体重叠导致权责不清。
- **推翻信号**：若老强要求治理席位介入具体个案代理或下业务裁决，则本边界降级，须重划 G 栈与业务栈接口。
- **落点**：D3 系统运维全量体检首轮（成熟度 R1：50 / M3），识别出"系统半盲 + 6 条监控类僵尸自动化"现象。

### 节点 2 · 监控僵尸去重：归因三分法首用，开处方前漏反向实证（踩坑 D）

- **决策点**：6 条监控类僵尸自动化，老强拍板**全选"下线"**（含唯一监控点），而非恢复；本就 PAUSED、无配置改动。
- **考虑了什么**：首轮误判"系统半盲 = 监控暂停该恢复"，拟恢复；但实证发现 4/6 已被活跃 `39c0aee8` 覆盖（重复监控）。
- **否决了什么**：否决"恢复 6 条监控"——会被活跃项重复覆盖，属结构类重复；否决"保留唯一监控点"——老强明确全选下线，且结构已由活跃项兜底。
- **推翻信号**：若实证未发现活跃覆盖项，则原"恢复"判断成立；正是**反向证据（被覆盖）推翻了首判** → 固化为坑 D 铁律：**开处方前必须先查反向证据（是否被覆盖 / 重复 / 有依赖引用），禁止凭现象直接开药**。
- **落点**：6 监控全部 PAUSED 下线去重（R3：66 / M4），去重后存活率上升，监控系统由单一活跃项统一承担。

### 节点 3 · 调度建表：解决周一 9:00 挤 8 个的踩踏

- **决策点**：建《自动化调度登记表》作为单一事实源，把分散的 11+ 自动化按职责域编目、记录触发时刻。
- **考虑了什么**：周一 9:00 集中触发 8 个自动化会资源踩踏、日志淹没、相互覆盖；需要全局视图才能错峰。
- **否决了什么**：否决"逐个人工记忆触发时间"——不可累积、易漏；否决"分散在各自 skill 里记录触发时间"——无全局视图，无法发现撞车。
- **推翻信号**：若 WorkBuddy 平台层提供原生调度编排面板，可迁移，但登记表作为人工审计底稿仍保留（人工审计不可被平台黑盒替代）。
- **落点**：`知识飞轮系统/05-调用/自动化调度登记表.md`（R4：72 / M4），11 项编目就绪。

### 节点 4 · 错峰执行：11 项拍板，识别"改时又关=按关" + cloud 前缀只读（踩坑 E）

- **决策点**：11 项错峰逐条拍板改 rrule 错峰；老强标注 A3 法随证书"既点改时间又写关闭"、B4 红队合同同理 → **按关闭（PAUSED）处理**；改前备份 `/tmp/automation_rrule_backup_20260915_1545.md`。
- **考虑了什么**：周一 9:00 高峰期错峰到 9:02–9:18 分散；A3/B4 双标注语义冲突时取"关闭"语义，避免改了 rrule 又没关反而误激活。
- **否决了什么**：否决"按字面'改时间'优先"——用户同时写了关闭，语义为关闭，按关闭处理；否决"对 `cloud:` 前缀用 delete"——平台托管只读，delete 必失败。
- **推翻信号**：若老强事后明确"改时间优先于关闭"，则 A3/B4 改回 ACTIVE + 新 rrule；若 `cloud:` 前缀改为本地托管则可 delete。→ 固化为坑 E 铁律：**删除类拍板前先 grep ID 前缀区分云端 / 本地托管，云端前缀只给 ACTIVE / PAUSED 两档**。
- **落点**：11 项错峰落地（R5：75 / M4）；坑 E 铁律入 WF-047 坑位表。

### 节点 5 · drift 工具固化：调度分析器 + 周刷新漂移比对

- **决策点**：把 `schedule_conflict_analyzer.py` 挂周一 9:35 周刷新自动化，做基线 vs latest 漂移比对（新增 / 消失 / rrule 变更 / status 变更四类）。
- **考虑了什么**：手动改 rrule 后无人复核是否真的错峰、是否又漂移回踩踏；需要可回归的自动比对，而非"改完即忘"。
- **否决了什么**：否决"改完即忘、靠人工复查"——不可回归；否决"直接改配置做自动修复"——L3 禁区未授权（铁律：满一季度实战验证前不授权自动改配置）。
- **推翻信号**：若治理席位获 L3 授权（满一季度实战验证），可启用 `--apply` 自动重排；当前仅 `--drift` 只读比对，绝不写配置。
- **落点**：周刷新自动化 id `638fd6f7-846a-4d6c-8107-241d1f005180`（R6：77 / M4），只读比对四态漂移。

### 节点 6 · 四类 PAUSED 处置：实证→拍板，闭合 LTI 监控真空

- **决策点**：4 个 PAUSED 自动化走"实证 → 拍板"：`a08c9307` 中台数据源 → ACTIVE；`64d97928` LTI 探活 → ACTIVE（闭合 LTI 监控真空）；`automation-1781950804800` 实习复盘 → delete 成功；`cloud:222929` AI 资讯 → delete 失败维持 PAUSED。
- **考虑了什么**：PAUSED 是"半死不活"，须逐个定夺；LTI 探活 PAUSED 导致 LTI 监控出现真空（危险，监控自己失监）。
- **否决了什么**：否决"PAUSED 一律删除"——其中 2 个有真实用途应 ACTIVE；否决"对 `cloud:222929` 强制 delete"——平台只读失败，维持 PAUSED（坑 E 再验）。
- **推翻信号**：若 LTI 探活有更优替代监控，则 `64d97928` 可下线；若 `cloud:` 前缀改本地托管则可 delete（与节点 4 同源推翻信号）。
- **落点**：PAUSED 10 → 9，存活率 85.5% → 87.1%（R7：80 / M4）。

### 节点 7 · 挂枢纽页成簇：方法论 + 经验卡 + 项目备忘录 + 双工具 在飞轮运维 MOC 闭环

- **决策点**：把 WF-047（方法论）、坑 D/E 独立经验卡（纪律）、PROJ-005（实战成绩单）、`mp_maturity.py` + `schedule_conflict_analyzer.py`（双工具）挂进 `连接枢纽-飞轮运维.md`，并补本 DEC 卡闭环三件套。
- **考虑了什么**：训练成果分散在四处，下次审计难复用；需在中枢层面成簇可搜；对照协议第七条，训练成果须 WF + PROJ + DEC 三件套齐备，此前缺 DEC。
- **否决了什么**：否决"只挂经验卡不挂方法论"——不成体系；否决"把经验卡塞进 `_活跃项目.md`"——那是 PROJ 索引会串类污染项目清单；否决"手敲双链不进中枢"——违反协议第六条，对中枢 git 提交一律走 backfill.py 安全通道。
- **推翻信号**：若连接层 `link_cards_rules.py` 周日重建枢纽页时改变分区结构，则手动挂载段需对齐；当前为即时可搜桥接，周日重建一并固化。
- **落点**：飞轮运维 MOC 四件套成簇（纪律 → 方法 → 实战 → 工具）；DEC 卡补齐三件套（WF-047 + PROJ-005 + DEC-2026-011）；本卡经 backfill.py 推送中枢。

## 收敛结论

一场「训练律所主任治理席位」的诉求，实际走出的是**七步递进**：

```
① 边界前置（G0 双栈模型 + QC 划界）
   → ② 僵尸去重（归因三分法首用，漏反向实证→踩坑D）
      → ③ 调度建表（单一事实源，治周一踩踏）
         → ④ 错峰执行（11 项拍板，识别 cloud 前缀只读→踩坑E）
            → ⑤ drift 固化（只读比对，L3 禁区不越权）
               → ⑥ PAUSED 处置（实证→拍板，闭合 LTI 真空）
                  → ⑦ 枢纽成簇（方法—纪律—实战—工具 四件套闭环）
```

三条可迁移判断：
1. **归因三分法须反向实证**——"现象 → 处方"之间必须插一道"反向证据核查"，否则会被覆盖项打脸（节点 2 → 坑 D）。
2. **先识别 ID 前缀再拍板**——云端托管（`cloud:`）只读、delete 必失败，拍板前先 grep 前缀区分云端 / 本地（节点 4/6 → 坑 E）。
3. **方法论—纪律—实战—工具须成簇闭环**——训练成果散落四处等于没训练，必须在中枢层面聚成一簇可搜可复用（节点 7）。

律所主任成熟度七轮演进：**50（R1/M3）→ 59（R2/M3）→ 66（R3/M4）→ 72（R4/M4）→ 75（R5/M4）→ 77（R6/M4）→ 80（R7/M4）**，详见 `PROJ-005-律所主任治理席位心智训练备忘录.md`。

> ⚠️ 真实能力分提示：仪表盘 P2 产出留痕 + P3 身份留痕双满分（共 40 分属"留痕自证"），真实能力分 = P1 + P4 + P5 ≈ 66%，距 M5 教练级尚远；且作为"中枢管家"尚未正经审计过中枢本身（M7 无健康基线 / M8 埋点 0% / M9 无治理态势看板），属下一阶段 D6 主战任务。

## 推翻信号（整体）

- 老强改口允许治理席位介入个案代理或下业务裁决 → 节点 1 的 G0 边界降级。
