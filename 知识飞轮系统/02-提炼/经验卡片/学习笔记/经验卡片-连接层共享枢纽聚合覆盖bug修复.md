# 连接层共享枢纽聚合覆盖 bug 修复（元级经验）

## 一、问题现象（老强发现）
2026-08-30 将 23 张顶层孤儿卡按案由归位后，重跑 `link_cards_rules.py`。`程序知识/` 下 6 张卡（股东知情权诉讼代理要点、R-GS-001/002/003、R014/R015）的 `related_links` 里明明写着 `连接枢纽-通用程序`，但 `grep` 该枢纽页却**完全找不到**这些成员——它们"连上了却看不见"。

## 二、根因
`GROUPS` 中 `程序知识` 与 `法条解读` 共用同一枢纽文件 `连接枢纽-通用程序.md`：
```python
"程序知识": ("通用", "连接枢纽-通用程序", "通用程序连接枢纽"),
"法条解读": ("通用", "连接枢纽-通用程序", "通用程序连接枢纽"),
```
原枢纽页生成逻辑**按分类逐类 `open(hubfile, "w")`** 覆盖写。两类共享同一文件，`法条解读` 后写，把先写的 `程序知识`（约 64 张卡）整体覆盖掉（last-write-wins）。每卡 `related_links` 是逐卡注入、互不干扰，故看似连通，但 MOC 页只保留了最后写入的分类。

## 三、修复（v3.1.1，2026-08-30）
改为**先按 hubfile 反向聚合再一次性写出**：
```python
hub_to_cats = defaultdict(list)
for cat, (rdomain, hubfile, hubtitle) in EG.items():
    hub_to_cats[hubfile].append(cat)
for hubfile, cats in hub_to_cats.items():
    # 聚合该 hubfile 下全部共享分类的成员（去重）后一次写出
    ...
    # 标题/domain 标注为共享域，如 "程序知识/法条解读"
```
修复后 `连接枢纽-通用程序.md` 同时列出 `程序知识` 与 `法条解读` 成员（`[[股东知情权诉讼代理要点]]`、`[[规则激活卡-R-GS-001]]`、`[[规则激活卡-R014]]` 等均已可见）。

## 四、检测方法论（可复用）
- **双重验证法**：归位/重建后，不仅查每卡 `related_links`，更要 `grep 枢纽页` 确认 MOC 可见性。
- **共享 hubfile 强核查**：凡 `GROUPS` 中多分类映射到同一 `hubfile`，归位到这些分类的卡必须重点验证枢纽页。
- **孤儿预防**：`link_cards_rules.py` 只枚举 `经验卡片/<分类子目录>/*.md`，**不扫顶层**；新卡必须落子目录。

## 五、引申教训
- 连接层"连通"有两层：每卡 `related_links`（细粒度）与枢纽 MOC 页（聚合视图）。任一层失效都算未接入。
- 写入型脚本凡涉及"多源写同一文件"，须聚合后一次写出，避免 last-write-wins。
- 全量快照备份（`.backup_link_YYYYMMDD_HHMMSS`）是批量归位/重跑的回滚基线，每次动手前必做。
