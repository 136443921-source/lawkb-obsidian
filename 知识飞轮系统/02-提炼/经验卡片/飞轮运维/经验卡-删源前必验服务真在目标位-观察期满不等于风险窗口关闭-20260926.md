# 删源批准 ≠ 可删：观察期满必须重验「承载状态」

## 一、事故回放（本次是「拦下了一次事故」，不是已发生的事故）

###  Obs：批准看起来完全成立

老强 2026-09-26 上午拍板：「#20 删源今日 23:59 后批准」。

按方案 §5-C.3 的推理链：`第 5 步双验通过 → 记录 T0 → T0+24h 内每日校齐无异常 → 方可提请删源审批`。

- T0 ＝ 2026-09-25 23:59（第 5 步双验通过时刻）→ **观察期 T0+24h ＝ 2026-09-26 23:59，现已到点**
- 期间每日校齐 `drift_count=0` / `aligned=true` / 退出码 0 → **无异常**
- 副本位 `drift_check_9655.py` 单独跑 → `aligned: true` / `drift_count=0` / **退出码 0**

**四条全部满足，一切手续齐备。**

### 真值：服务从未离开旧目录，删源＝当场打挂

| 检查项 | 实测 | 批准所隐含的前提 |
|---|---|---|
| 端口 9655 持有者 | **PID 97482** | — |
| `lsof -p 97482` 的 cwd | **`/Users/chenyouqiang/WorkBuddy/2026-09-17-16-22-53/outputs/9655-cockpit-v2`** | 应为长期资产位 |
| 副本位 `.9655.pid` 内容 | `83606`（v1.5 那次手工启动的实例号） | 应为当前承载实例 |
| `~/.Library/LaunchAgents/com.xiaoqiang.cockpit9655{,.scan}.plist` | `ProgramArguments`／`WorkingDirectory`／`.launchd.out`／`.launchd.err` **4 类路径全指旧目录** | 应指长期资产位 |
| 若删旧目录的后果 | plist 指向不存在路径 → **服务起不来 → 驾驶舱 9655 断服** | — |

**结论：删的不是"已退役的旧副本"，而是"当前仍在承载服务的运行目录"。**

### 错因（两条，都可复用）

1. **时钟 ≠ 状态。** "观察 24 小时无异常"证明的是「过去 24 小时没出问题」，**证明不了「新路径此刻正在承载流量」**。本次 T0+24h 的 24 小时里，**承载方始终是旧目录**——风险窗口从未关闭过，只是没人去验。观察期是一个**必要不充分条件**，不能当充分条件用。
2. **手工启动 ≠ launchd 承载。** v1.5 那次"切换"是手工 `start_9655.sh` 启动副本位实例；`~/Library/LaunchAgents/` 下两份 plist 自始未改写。手工启动只影响当次进程，**下次 unload/load 或开机，launchd 仍按旧 plist 拉起旧目录**——于是进程被换回旧目录（83606 → 97482）。

## 二、可复用铁律（不可逆动作批准前的固定检查清单）

**规矩：凡"删/销毁"类不可逆动作，批准书下达后、执行前，必须逐条实测并留痕。**

| # | 检查项 | 判定标准 |
|---|---|---|
| 1 | **谁在承载？** `lsof -nP -iTCP:<端口> -sTCP:LISTEN` 取 PID → `lsof -p <PID>` 看 cwd | **cwd 必须等于拟保留位**，否则前提不成立 |
| 2 | **调度指哪？** 读 `~/Library/LaunchAgents/*.plist` 的 `ProgramArguments`／`WorkingDirectory`／日志路径 | **全部指向拟保留位**；有 1 处仍指旧位 ⇒ 删旧位必断服 |
| 3 | **任务都加载了吗？** `launchctl list \| grep <标识>` | 计划内任务**应全部在列**；漏加载要补 |
| 4 | **回滚基线在长期位吗？** 备份是否 `cp` 到 LawKB 等长期资产位 | **`/tmp` 不能作回滚基线**（见下） |

**三句话版本**：`不验承载就不批、不验调度就不删、不验回滚就不动。`

### 副产品：`/tmp` 备份不能当回滚基线（本次实测）

- 现有回滚点 `/tmp/opc_migrate_bak_20260925_195400/` 与源目录 `diff -rq` **已出现 4 处差异**（`flywheel-data.js`／`index.html`／`.workbuddy/memory/.../memory.md`／两份 launchd 日志）→ **不是逐字节快照**；
- 且 `/tmp` 会被 macOS 清理（重启、磁盘紧张）→ **删源前必须先在长期位做一次全量 `cp -R`**，并 `diff -rq` 验到零差异，才可放行删除。

## 三、本次的处置

1. **批准不撤回，改「条件式批准」**：老强的批准写入方案 v1.7，但生效须走完修订执行链第 0–4 步——
   ① 长期位全量备份（零差异） → ② 改 2 份 plist 的 4 类路径 → ③ 补 `load` 漏掉的 `.scan` → ④ `launchctl unload/load` + 双验（新 PID cwd 在长期位／`curl` HTTP 200／副本位 `drift_check` 绿）→ ⑤ **重起 T0**（新 T0 ＝ 第 ④ 步绿灯时刻），观察一轮后再请老强点头执行删除。
2. **执行纪律**：删除建议用 `mv` 到隔离区观察 7 日，不直接 `rm`；沙箱下任何 `mv`/`rm` **必须显式回显退出码并复核状态**（v1.6 `mv` 静默不执行的教训）。
3. **本轮零执行**：未改 plist、未动服务、未删任何文件。

- **批前提被证伪时，要敢拦。** 老强的批准建立在方案陈述之上；执行前的实地核查推翻了它，**正确做法是停下来报告 + 把批准改为条件式，而不是"手续齐备就照办"**。
- 与 09-26 另一张卡**合看**：那张是「迁目录 ≠ 迁调度」（**横向**：文件迁了、调度没迁）；这张是「手工启动 ≠ launchd 承载」（**纵向**：当次进程起来了、托管配置没迁）。**两卡合起来＝迁移类动作的验收必须落到"托管配置 + 进程 cwd"这两个硬指标上。**
