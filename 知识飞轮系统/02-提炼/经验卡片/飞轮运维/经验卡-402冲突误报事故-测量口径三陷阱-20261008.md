# 经验卡片 · 卡库路由注册表「402 冲突」误报事故

> **类别**：correction / best_practice（AI 工作流安全 · 计数口径纪律）
> **触发场景**：生成任何"聚合计数"（挂载率 / 冲突数 / 覆盖率 / 缺口数）并据此下结论、向老强汇报、或写进方案/注册表时
> **一句话**：**"冲突 = 402"这个数字，来源是"全技能聚合"，不是"消费技能归属"——把系统级元技能的引用也算进路由冲突，等于用错了统计边界。计数类断言须先定口径（数什么单位、数哪些对象），否则数得越精确，错得越理直气壮。**
> **关联铁律**：六-B 安全铁律、否定型结论须实测（用户级铁律）、`经验卡-统计口径五连错`（同族·计数单位）、`经验卡-存在性断言须实证`（同族·假阴性）

## 一、事故回放（2026-10-08 · 卡库路由注册表生成）

为落地"卡库统一调度"，我写了 `gen_registry.py`，扫全量活跃卡 2503 张 + 9 个消费技能 SKILL.md，生成 `card_route_registry.yaml`。第一版跑出：

| 指标 | 第一版数值 | 真相（修正后） |
|---|---|---|
| 冲突（同 rid 多技能共存） | **402** | **6** |
| 已挂载 / 未挂载 | 2503 / 0（100%） | 2289 / 214（**91.4%**） |
| skill 字段归因 | 全部标 `skills` | 真实技能名 |

据此我差点向老强汇报"挂载率 100%、但存在 402 处路由冲突需逐一裁决"——这是**重判断**，会推导出"消费技能严重交叉污染、需大规模改接线"的错误路线。

**定位过程（三轮实测，非臆断）**：
1. 抽最大冲突组 `类案检索报告卡族 LC-001~013`，逐一 `in` 比对 `类案检索助手/SKILL.md` → **13/13 命中**，却被判 pending。→ 暴露**陷阱①**：skill 侧 token 抓取写死 `R-[A-Za-z0-9_\-]+`，漏判 `LC-`/`PI-`/`HG-` 等非 R 前缀卡。
2. 看冲突项 `实际=skills` 诡异值 → 查 `os.path.basename(os.path.dirname(root))` 取到的是 `~/.workbuddy/skills` 自身。→ 暴露**陷阱②**：技能目录名取错，全部卡 `skill` 字段错标 `skills`。
3. 修①②后冲突从 402 掉到 6，且 6 冲突的共现组合是 `模拟法庭主控协调器 ⇔ 法律检索助手`（343 对）等 → 查这些"技能"实为**系统级元技能**（编排器/拆卡流水线），它们引用全量卡属正常系统行为。→ 暴露**陷阱③**：元技能引用被计入"路由冲突"。

## 二、根因（三处测量陷阱，均为"口径/边界"病）

| # | 陷阱 | 表现 | 类型 |
|---|---|---|---|
| ① | **R- 前缀正则漏判** | `tok_re=R-[A-Za-z0-9_\-]+` 只认 R- 前缀，漏 `LC-/PI-/HG-` 等非 R 前缀卡 → 误报 pending | A 型（单位未定义）变种 |
| ② | **技能目录名取错** | `basename(dirname(root))` 取到 `~/.workbuddy/skills` 自身，而非技能目录名 → skill 字段全错标 | 路径解析 bug |
| ③ | **元技能引用注水** | 把"模拟法庭主控协调器/拆卡流水线"等系统级技能对全量卡的引用，算作"路由冲突" | **统计边界错（数了不该数的对象）** |
| ④ | **检测器全文件子串匹配** | `found = {r for r in all_rids if r in t}` 把"日志格式示例"等**正文提及**（如 `（如 R001、R-GS-001）`）也算作"该技能挂载了此卡" → 假阳性"双挂载/冲突" | **单位病：把"出现"当"挂载"**（挂载的计量单位应是"卡库接线段内 `\| rid \|` 路由行"，不是"全文子串出现"） |

> ⚠️ **本案最危险处**：陷阱③不是"数错了单位"，是**"数错了对象集合"**——冲突的定义应是"同卡出现在 ≥2 个**消费技能**"，我却数成了"≥2 个**全技能（含元技能）**"。这正踩中 `统计口径五连错` 卡里反复强调的：**"有多少条"取决于你数的是什么单位、什么集合。**

> ⚠️ **陷阱④（2026-10-08 续·Plan B 闭环核验中发现）**：即便边界已收紧到"仅消费技能"，`r in t` 的**子串匹配**仍会把技能正文里的示例提及误判为挂载。例：`非诉文书红蓝复核工作流/SKILL.md`、`诉讼文书红蓝复核工作流/SKILL.md`、`法律检索助手/SKILL.md` 的"调用记录回写"段都有一句 `规则 = 本次交付实际引用的裁判规则编号（如 R001、R-GS-001）`——`R-GS-001` 在这里只是**格式示例文字**，却被子串匹配当成"该技能挂载了 R-GS-001"，与真实挂载它的 `legal-base` 一起构成假阳性"双挂载/冲突"。**计量单位应是"卡库接线段内 `| rid |` 路由行"，而非"全文任意子串出现"**——这是陷阱①（单位未定义）在检测器层的再次发作。修正见 §四-C。

## 三、固化铁律（生成任何聚合计数前必念）

| # | 铁律 | 说明 |
|---|---|---|
| 🔴 1 | **计数前先定义"统计边界"**：数的是哪些对象的集合？ | 路由冲突 = "≥2 个**消费技能**"，不是"≥2 个全技能"。元技能/系统级技能引用不计入业务路由冲突 |
| 🔴 2 | **计数前先定义"单位"**：rid / 条目 / 文件 / token？ | 同卡多前缀（R-/LC-/PI-）须用卡片 rid **全集**做精确匹配，禁用单一前缀正则 |
| 🔴 3 | **"为 0 / 极高 / 极低"的极值，换角度复跑一次再信** | 402 冲突是极值；应先问"这个数含哪些对象"，而非直接汇报 |
| 🟢 4 | **聚合脚本的路径解析须 `basename(root)` 取真实实体名** | 取父目录名会拿到容器而非实体，导致归因全错（陷阱②） |
| 🟢 5 | **否定/冲突类结论，先抽样实证再落笔** | 抽 1–2 个样本 `in` 比对真源，5 分钟能拦下 402 这种虚高 |

### 四-B、持久机制：技能角色注册表 SSOT（根治元技能注水·2026-10-08 追加）

> 陷阱③（元技能注水）的本质是「**路由统计边界靠脚本硬编码**」——`gen_registry.py` 用 `CONS = set(DEDICATED.values()) | {UNIVERSAL}` 被动排除元技能，一旦有人把元技能加进映射或未来扩展，虚高必然复现。故须把边界**固化成显式 SSOT**，使注水「不可发生」而非「靠人记」。

**机制文件**：`小强律师数字分身系统/00-系统总览与运维中心/skill_role_registry.yaml`（卡库路由统计边界 SSOT）

**核心设计**：
| 要素 | 内容 | 防复发作用 |
|---|---|---|
| `consumption_skills` | 显式列出 9 个消费技能（路由统计唯一真源） | 脚本只读此列表，元技能天然不在集合内 |
| `default_role: meta` | 未声明技能一律按 meta 处理 | 新技能默认排除，**漏声明→欠计（安全方向，永不虚高）** |
| `meta_excluded_audit` | 存档已审计的系统级 meta 技能（编排器/拆卡流水线/资产运维官等） | 排除依据可审计、可追溯 |
| `governance.fallback_policy` | 注册表缺失即 `SystemExit` 硬失败 | **不静默回退到硬编码**，断绝虚高根 |
| `governance.review_cadence` | 每次路由重算前人工复核 consumption_skills | 边界变更走显式决策，不靠记忆 |

**脚本落实**（删除硬编码边界）：
- `gen_registry.py`：删除 `CONS = set(DEDICATED.values()) | {UNIVERSAL}`，改为 `CONS = load_consumption(ROLE_REG)`；注册表缺失即硬失败。
- `registry_consistency_check.py`：同样改读角色注册表，删除硬编码 9 字符串列表。

**机制牙齿（meta_inflation_guard）**：一致性校验脚本新增「元技能注水自检」——扫描**全部**技能，把引用了卡片 rid 的非消费技能暴露进 `registry_drift_report.json`。**实测**：77 个 meta 技能命中全量卡（模拟法庭主控协调器 346、审判要件卡拆卡流水线 136、ai-mock-court-judge 41…），**全部被强制排除、未计入冲突**——证明边界生效，并暴露未来新增注水风险。

**实证结论（轻量全链路验证）**：消费技能边界 = 9（SSOT）｜挂载 2290/2504 = **91.5%**｜冲突 = **6**（非 402）｜错挂 = 9｜77 meta 技能引用卡被排除未注水。

> 🔴 **本机制对应铁律①升级**：「计数前先定义统计边界」从「人工记」升级为「SSOT 强制」——边界错不再依赖 AI 自律，而由 `skill_role_registry.yaml` 结构性阻断。
