# 经验卡片 · 归因处方前先「反向实证」再验 + cloud: 前缀云端只读——治理席位审计双坑

> **类别**：correction / best_practice（AI 工作流安全 · 处置纪律 / 资源权限）
> **触发场景**：① 对自动化/系统做「恢复 / 下线 / 改造」类处置处方前；② 对带 ID 的云端资源做删除操作前
> **一句话**：**归因三分法开处方前必须先做「反向实证」再验（防凭现象直接开药）；`cloud:` 前缀自动化 = 云端托管只读，delete 必失败，拍板前先识别 ID 前缀。**
> **关联铁律**：六-B 安全铁律、cp 备份铁律、清理前引用预检铁律（同源·动刀前先确认）

## 一、事故回放（2026-09-15 · 治理席位首轮审计，双坑同日暴露）

### 坑 D：「监控类半盲 → 恢复」误判，实被活跃项覆盖

- **我下的处方**：首轮全量体检，把「6 条监控类自动化被暂停」直接归类为「监控类半盲 → 处方：恢复」，准备逐一复活。
- **真相（实证推翻）**：其中 **4/6 的功能已被活跃自动化（如 `39c0aee8`）覆盖**——本质不是「缺失功能」，而是**结构类重复**（同功能双份，一份活跃一份暂停）。
- **正确处方**：**下线去重**（删掉暂停的那份重复），而非「恢复」。6 条最终全选下线（本就 PAUSED，无配置改动）。
- **误判根因**：只做「现象（暂停）→ 归类（半盲）」就开处方，**漏了「归类 → 处方」之间的反向实证闸门**——把「暂停」直接等同「功能缺失」，没先查「这功能是不是已被别处承担」。

### 坑 E：`cloud:222929` delete 失败，平台云端只读

- **我下的操作**：拍板对 `cloud:222929`（AI 资讯自动化）执行 delete，清理僵尸。
- **真相**：平台返回「云端只读」失败，**无删除权限，只能维持 PAUSED**。
- **根因**：带 `cloud:` 前缀的自动化 ID 由**平台云端托管**，WorkBuddy 工具侧只读；与本地 uuid 格式自动化权限不同，未识别前缀直接 delete 必白跑一轮。
- **正确处置**：标记「平台托管 · 仅可 PAUSED，禁止 delete」，处置选项只留 `ACTIVE / PAUSED` 两档。

### 共性

> 两坑同源于「**动手前少了一道确认闸**」：坑 D 是处置逻辑上没反向实证，坑 E 是资源权限上没识别前缀。都是「想当然 → 白跑 / 开错药」。

## 二、根因

1. **归因三分法缺「再验闸门」**：原方法论只有「现象 → 归类 → 处方」三段，归类落定即开处方，没有「开处方前先查反向证据」这道强制关卡。
2. **把「暂停」等同「缺失」**：暂停只是状态，不等于功能不存在；未先确认「是否已被活跃项覆盖 / 是否重复建设」。
3. **资源 ID 前缀与权限未绑定认知**：不同前缀（云端 `cloud:` vs 本地 uuid）后端权限不同，拍板前未 `grep` 区分即调用删除。
4. **未执行「先实证再落刀」闸**：坑 D 动手前若先确认「这 6 个监控功能是否已被别处承担」，坑 E 拍板前若先 `grep` ID 前缀，两坑都能当场规避。

| 🔴 1 | **归因三分法开处方前先做「反向实证」再验** | 能力 / 结构 / 数据 任一归类落定后，先查反向证据（是否被活跃项覆盖 / 是否重复 / 是否仍有依赖引用），再定处方；禁止「凭现象直接开药」 |
| 🔴 2 | **判「恢复 / 结构改造」前，先确认「是不是已被替代」** | 坑 D：6 监控暂停误判为半盲需恢复，实 4/6 被活跃 `39c0aee8` 覆盖 → 应为下线去重 |
