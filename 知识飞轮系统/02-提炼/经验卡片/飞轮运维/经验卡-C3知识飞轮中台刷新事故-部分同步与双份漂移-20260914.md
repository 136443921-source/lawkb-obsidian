# 经验卡片 · C3 知识飞轮中台刷新事故——只刷主块的部分同步陷阱与双份部署漂移

> **类别**：correction / best_practice（AI 工作流安全 · 飞轮运维 · 同步校验）
> **触发场景**：对任何「仪表盘 / 看板 / 快照 / 中台」类产物执行「刷新 / 同步 / 更新」操作时
> **一句话**：刷新脚本只重写 DATA 的「主块」（kg/intake/autos）而漏掉其余写死块，且本地 + 公网双份部署各走各的——「刷新成功」的错觉来自只验了主块；任何同步操作须**全字段校验 + 单一真源双写/重部署闭环**。
> **关联铁律**：六-B 安全铁律、cp 备份铁律、单一真源教训（代码复述权威源必漂移）、外部快照勿轻判死（先搜本地生成链）

---

## 一、事故回放（2026-09-12 ~ 09-14 · C3-REFRESH-INCIDENT）

- **09-12 意图**：用户令「立即刷新 C3 知识飞轮中台数据」。我跑了 `refresh_live.py`，只在 `index.html` 重写了 `kg / intake / autos` 三块，报告「刷新完成」。
- **09-14 第一次暴露**：用户在 `127.0.0.1:8139` 发现「数据更新」仍是 09-12。核查发现两处漂移：
  1. **双份部署**：本地 `cockpit-hub-ops/subapps/flywheel/index.html` 是**另一份独立内嵌 DATA 的文件**，公网刷新根本没覆盖到；
  2. **脚本部分性**：刷新脚本只刷 `kg/autos/intake`，漏掉 `kpi / cardGrowth / metrics / layerInc / rules` 五块——它们自初版起就写死 09-12。
- **09-14 第二次暴露**：用户复查发现「经验卡片增长曲线」仍是 09-12。复盘确认 `cardGrowth` 等 5 块**从未被刷新脚本碰过**，连已刷新的公网那份页面顶部「数据更新」标签也因漏刷 `updated` 字段一直显示 09-12。

**真值对比（写死旧值 vs 今天实测真值，来源：LawKB 实扫 + git）：**

| DATA 字段 | 写死旧值(09-12) | 今天真值(09-14) | 来源 |
|---|---|---|---|
| 经验卡片 `experienceCards` | 408 | **409** | 经验卡片目录实扫 |
| 规则库文件 `rules.total` | 1815 | **1878**（规范卡 1846 / 合规率 98.3%） | 裁判规则库实扫 |
| 六层合计 `sixLayerTotal` | 4522 | **4749** | 六层实扫求和 |
| 思维轨迹卡 | 9 | **10** | 思维轨迹目录实扫 |
| 增长曲线末点 `cardGrowth` | 09-12 / 408 | **09-14 / 409**（14 个历史点） | git 净增重建 |
| `layerInc` 06-沉淀 | 1819（写死） | **1914**（实时） | 与 `kg.dirs` 一致但自相矛盾 |

## 二、根因

1. **刷新逻辑「部分性」缺陷**：`refresh_live.py` 初版只重写 3 块，其余 5 块是初版写死的静态快照，脚本从不触碰——「刷新」名不副实，留下 5 颗漂移雷。
2. **双份部署无单一真源（早期）**：公网 `feilun-refresh/index.html` 与本地 `cockpit-hub-ops/subapps/flywheel/index.html` 各自内嵌一份 DATA，刷新只动公网那份，本地被遗忘。
3. **「只验主块」的验收盲区**：我每次都用「`kg.generated` 已更新」证明刷新成功，没做**全字段核验**——主块通过 ≠ 全字段通过。
4. **`updated` 字段被漏刷**：页面顶部「数据更新」标签依赖 `updated` 字段，脚本初版未覆盖，连公网那份也一直显示 09-12。
5. **git 命令 macOS 兼容陷阱**：增长曲线初版用 `git log --diff-filter=A` 推演历史，在 macOS 上**失灵返回空**——这条路径早该重建，却因返回空被误当「无历史」。
6. **已部署快照未重部署**：即便本地 + 公网已统一为单一真源 `flywheel-data.js`，公网已部署的线上副本仍是旧内联版，须**重部署**才同步——卡在跨 workspace appId 决策（旧 appId 不被当前 workspace 识别）。
7. **sandbox I/O 慢致前台超时**：刷新脚本前台跑 9449 文件扫描必被 120s SIGTERM 杀掉，须后台运行。

## 三、固化铁律（每次「同步/刷新」操作前必念）

| # | 铁律 | 说明 |
|---|---|---|
| 🔴 1 | **同步操作全字段核验** | 报告「刷新完成」前，逐项核对产物**全部**动态字段（含时间序列、文案、衍生块），不只验主块 |
| 🔴 2 | **刷新脚本须「全字段派生」** | 脚本重写逻辑必须覆盖产物全部动态字段；初版写死的静态块必须改为实时派生或显式更新——遗留写死块 = 定时炸弹 |
| 🔴 3 | **双份/多份部署必须单一真源或双写** | 本地 + 公网/预览多份产物时，要么抽单一数据源 + symlink，要么刷新脚本显式双写；否则必漂移 |
| 🔴 4 | **已部署快照须重部署才生效** | 磁盘改了 ≠ 线上更新；改完产物须触发重部署/硬刷新，并**验证线上副本**而非仅本地文件 |
| 🟢 5 | **git 历史推演用 `--name-status` 而非 `--diff-filter=A`** | macOS 上 `--diff-filter=A` 对部分路径失灵返回空；用 `--name-status` 反向统计净增更稳 |
| 🟢 6 | **大目录扫描脚本走后台** | sandbox I/O 慢，9449 文件扫描前台必 120s 超时(SIGTERM)；一律 `run_in_background` |
| 🟢 7 | **时间序列字段单列校验** | 增长曲线/累计类字段是「动态中的动态」，刷新逻辑须显式覆盖并校验末点与点数，不能并入主块一带而过 |

## 四、本次修复后的正确执行流（已落盘根治）

1. **单一真源化**：抽 `feilun-refresh/flywheel-data.js`（`const DATA` 整块，含 `cardFamily`）；公网 `index.html` 用 `./flywheel-data.js`、本地用 `/flywheel-data.js` + 根目录 symlink，刷新脚本只写这一个文件。
2. **全字段派生**：`refresh_live.py` 升级为重写**全部 9 个** DATA 字段（kg/autos/intake/kpi/cardGrowth/metrics/layerInc/rules + `updated`）；kpi/规则库/六层/思维轨迹全部实扫或 git 派生，`cardGrowth` 改用 `git --name-status` 净增重建。
3. **标题语义修正**：`layerInc` 区块「近 7 日增量」→「近 7 日活跃（改动文件数）」——因 09-07~09-12 全量基线导入致改动文件数 ≈ 各层总量（甚至含「改后删除」路径使 02-提炼 1361 > 1352），标「增量」误导。
4. **端到端核验**：`curl` 本地 `/flywheel-data.js` 核对全字段 + `node --check` 语法校验 + symlink 解析校验；实测 `updated 09-14`、经验卡片 409、合规率 98.3、增长曲线 14 点末点 09-14/409、`total_notes 9468`。
5. **待办（挂起·跨 workspace A/B 决策）**：公网 `xq-feilun-hub-2026` 重部署（让线上快照同步单一真源）；每周一自动化 `d06e443d` 改 `createNewApp` 新前缀或回原 workspace（`2026-09-12-01-29-05`）运行，否则下次触发 `unknown_app` 失败。

## 五、复盘金句

> **「『刷新成功』的错觉，来自只验了主块。同步操作的验收标准不是『主块动了』，而是『全字段都对了』；多份部署的真相不是『我改了源文件』，而是『线上副本也更新了』。」**
> 安全感只能来自**全字段核验 + 单一真源 + 已验证的线上副本**，不能来自一条「主块已更新」的局部信号。
