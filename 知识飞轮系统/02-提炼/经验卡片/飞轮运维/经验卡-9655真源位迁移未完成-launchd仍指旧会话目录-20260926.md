# 9655 真源位"迁移"未完成——launchd 仍指向旧一次性会话目录

## 一、事故回放（错值 / 真值 / 错因）

### 表象：日报恒绿，一切正常

| 项 | 实测值 | 判读 |
|---|---|---|
| `drift_check_9655.py` 退出码 | `0` | ✅ 健康 |
| `baseline_manual_version` | `v1.5` | ✅ 与新基线位一致 |
| `drift_count` / `aligned` | `0` / `true` | ✅ 无口径漂移 |
| `health_count` | `0` | ✅ 无运行健康告警 |
| 基线屏数 vs 实车屏数 | `19` vs `19` | ✅ 19 屏齐 |
| 屏校齐率 | `100%`（19/19） | ✅ 达标（≥95%） |
| 真源位 `scorecard_data.json` `generated_at` | `2026-09-25 19:37:11` | ⚠️ 冻结 |
| 真源位 `fresh_h` | `13.44h` | ✅ 当日 <26h，判绿 |

按 §5.10.4 门禁口径，当日应判**全绿**。**这个判定是假绿。**

### 真值：服务与扫描任务根本不在长期资产位

| 检查项 | 实测 | 应为 |
|---|---|---|
| `com.xiaoqiang.cockpit9655`（服务）plist 指向 | `/Users/chenyouqiang/WorkBuddy/2026-09-17-16-22-53/outputs/9655-cockpit-v2/serve_nocache.py` | 长期资产位 |
| `com.xiaoqiang.cockpit9655.scan`（扫描）plist 指向 | `.../2026-09-17-16-22-53/outputs/9655-cockpit-v2/scan_9655.py` | 长期资产位 |
| `launchctl list` 中是否有 `.scan` 任务 | **无该条目**（仅 `com.xiaoqiang.cockpit9655`） | 应存在且 `RunAtLoad` |
| 长期资产位 `scorecard_data.json` md5 | `9bcea099e101e5b20884dc997d32bd61` | — |
| 旧会话目录 `scorecard_data.json` md5 | `c26ad337bae3c2230cafd5e728da0333` | — |
| 旧会话目录 `generated_at` / `fresh_h` | `2026-09-26 06:50:45` / `2.22h` | — |

**两份 `scorecard_data.json` 内容不同，心跳相差 6h13m。旧目录在刷新，长期资产位在冻结。**

### 错因（三条叠加，可复用）

1. **"迁目录" ≠ "迁调度"。** 2026-09-25 把文件 `cp` 到长期资产位，但 `~/Library/LaunchAgents/*.plist` 里的 `ProgramArguments` / `WorkingDirectory` / `StandardOutPath` 四项全部还是旧路径——**服务与扫描任务仍在旧目录自刷**。
2. **扫描任务压根没加载。** `launchctl list` 查无 `com.xiaoqiang.cockpit9655.scan`，说明 9-25 迁移时只 unload 了服务、漏了扫描任务；长期资产位的那份 scorecard 是人工顺手拷过去的，不是扫描产出的。
3. **`drift_check` 抓不到这个错位。** 它比对的是「基线 vs 它自己读到的三个文件」，三个文件在同一目录内自洽 → `drift_count` 恒 0。**换目录跑一遍比对，`drift_check` 一样会给绿。** 这是同态自检，只能证"三方一致"，证不了"产出链挂在了哪个目录"。

### 后果推演（数字带口径）

- 真源位 `generated_at` 冻结于 `2026-09-25 19:37:11`，当前 `fresh_h=13.44h`，阈值 `26h`；
- 按每日校齐节奏，**2026-09-27（明日）该位 `fresh_h` 必然 >26h** → 判 **③断流**，优先级置顶，连续 3 日 → 升 P1 故障；
- 而 cockpit 服务（旧目录）照常 9655 端口 LISTEN 自刷，**驾驶舱大屏看起来永远是活的数据**——这正是"恒绿的最大盲区"。

## 二、可复用铁律（下次照着做的检查清单）

> 通用表述：**「迁移一个会定时产出数据的服务，必须同时迁调度，并验证产出物时间戳在变。」**

1. **迁目录四件套必查**（缺一即视为未完成迁移）：
   `ProgramArguments` / `WorkingDirectory` / `StandardOutPath` / `StandardErrorPath`。
2. **调度侧验收**：`launchctl list | grep <label>` 必须同时能看到**服务**与**扫描/产出**两个任务；只有服务没有 scan ⇒ 数据链已断。
3. **产出物验收（最关键）**：迁完后**隔 30 分钟再取一次产出物的 `generated_at` / mtime**，数字变了才算迁完。只看"文件在、脚本在"不算。
4. **真源位与产出位必须 md5 对齐**：`md5 -q 两处 <file>`，不同 ⇒ 存在双源，先定哪一份是准的再谈校齐。
5. **每日校齐强制单列 `fresh_h`**，不得并入 `drift_count`（本卡 §一 表格「表象 vs 真值」即反例）。
6. **读到的每一个"绿"，都要回答一句：这个绿是**谁**在他的哪个目录里算出来的？**

## 三、处置建议（责任席位：可视化监控运维官 / 集群-服务运维）

| 序 | 动作 | 风险 | 建议 |
|---|---|---|---|
| ① | `cp -p` 备份两个 plist 到 `/tmp/9655_mig_$(date +%Y%m%d_%H%M%S)/` | 无 | 先备份（六-B） |
| ② | 编辑两处 plist 四项路径 → 长期资产位 | 低 | 只改路径，不动其他键 |
| ③ | `launchctl unload` 旧 → `launchctl load` 新 → `launchctl list` 复核 | 中（服务短暂中断） | **须老强确认后执行，本次校齐不自行处置** |
| ④ | 与旧会话目录 `scorecard_data.json` 做一次 md5 对齐或明确"旧目录降为只读归档" | 无 | 删源未批，观察期未满，暂留 |
| ⑤ | 明日校齐重点复验真源位 `fresh_h` 是否回落 | 无 | 若仍 >26h ⇒ ③断流建卡 |

> ⚠️ **本次为每日只读校齐，按红线未做任何写入（未跑 `scan_9655.py`、未改展示层、未动 plist）。** 上述处置动作待老强拍板后另轮执行；如执行，须先 `cp -p` 备份 + `launchctl unload/load` 前确认服务可短暂中断。
