## 一、问题演进
起点是一个连接器根因问题：2026-09-09 至 09-16 ima/元典/法宝"依次坏、修不完"，下一步该怎么判定是单点还是批量？
只读诊断（读 config 而非凭记忆）把问题收敛：

| 轮次 | 老强/事实的追问 | 逼到的位置 |
|---|---|---|
| 1 | "为什么 UI 显示 connected 却调不通？" | connector-states 三标志全 True=迁移清令牌 |
| 2 | "重连后还 90001/402 是不是又断了？" | 那是业务层配额错误(亚型D)，重连无效 |
| 3 | "彻底重启还 Unauthorized？" | OAuth 握手层失败(loopback 未起)，重启无效 |

**收敛到的问题**：多个连接器一起掉，是三个独立故障还是一次批量事件？——答案：读 config 三标志，判"迁移清令牌"一次性处置。

## 二、思维逻辑链

### 1. 现象层：先不各自修，先找同源性
| # | 表象 | 实际 |
|---|---|---|
| 1 | UI 显示 connected | 仅代表 enabled=True 配置生效，≠ upstream 鉴权通过 |
| 2 | ima/元典/法宝依次坏 | 同一时间戳批量清令牌，被"依次发现" |

### 2. 归因层：一个根因，几种形态
- 直接原因：平台级 MCP 安全迁移(v3→v4)批量剥离 `headerOverrides` 所有 Bearer 令牌。
- 业务层混淆：402/90001 是配额错误，重连/重启无效，却被误读为"又断线"。
- 握手层（第四判定）：OAuth loopback 回调未起，重连+重启仍 Unauthorized。

### 3. 拦截层：找到真正的盲区（最有价值）
"在用全清、废弃全留"的令牌分布是迁移清令牌的**专属 fingerprint**——随机损坏绝不会长这样。connector-status 绿≠令牌在，是这类假连接最隐蔽的招牌。

### 4. 固化层：把「人肉警觉」换成「机器门禁」
R-LN-113 与 R-LN-055/059 并列构成「连接器故障判定四件套」（工具索引层 / 时间戳层 / 根因层 / 握手层），互补不重叠；并落 `workbuddy-connector-enabled-gate` 技能 v4.1.1 + 每日守卫自动化主动播报"待重新授权清单"。

## 三、事实思考方向（核查清单）
| # | 核查项 | 动作 | 分级 |
|---|---|---|---|
| 1 | 迁移标志 | 读 config 顶层三标志是否全 True | A |
| 2 | 假连接判定 | enabled && id∉headerOverrides | A |
| 3 | 业务层区分 | 错误体带 requestId/timestamp=业务层，重连无效 | A |
| 4 | 握手层区分 | 日志含 OAuth loopback callback server is not started | A |

**证据分级**：A 级＝config 字段＋真调用返回；B 级＝UI 状态显示；C 级＝"感觉又坏了"推断不得作事实断言。

## 四、分歧与纠偏（如有老强纠正）
本卡为事后重建，无实时纠偏记录。原事故卡结论经老强 2026-09-16 确认（见 R-LN-113 第七节）。

## 五、收敛结论
1. **连接全绿 ≠ 令牌在**：enabled=true 无令牌 = 亚型B 假连接。
2. 多个受管 MCP 同时间掉 = 读 config 三标志，判"迁移清令牌"一次性批量重连。
3. 业务层 402/90001 与握手层 Unauthorized 各是独立亚型，重连/重启无效，须分治。
