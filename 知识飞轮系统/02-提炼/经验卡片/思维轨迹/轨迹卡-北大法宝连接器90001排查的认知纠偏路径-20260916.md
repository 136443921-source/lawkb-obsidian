# 思维轨迹卡：北大法宝(pkulaw)连接器 90001 排查的认知纠偏路径

> 域：知识工程（AI协作·连接器运维诊断）｜类型：反复排查类咨询轨迹（9 轮追问/纠偏）｜关联技能：`workbuddy-connector-enabled-gate`
> 一句话结论：**pkulaw 调用异常的根因不是账号、不是连接层，而是"本会话工具索引对话级定型、中途点连接不热加载"；UI 显示 connected 绿 ≠ upstream API 真能调通。**

## 一、背景与触发
- 任务链：LTI `case_verify_cache.json` 缺口回填（T502 案例存在性硬边界）→ 走 pkulaw 权威核验。
- 现象：调用 `anhao_recognition` 稳定报 `code:90001 Unclassified Authentication Failure`（description: `checking remaining points for user: a4204ed9-3bf5-4340-b392-589ca82dd3a7`）。
- 用户动作序列：网页充值 → 解绑重连 → 重启客户端 → 点连接 → 让我查账号（确认同账号无错配）。
- 全程 UI `connector-status` 一直显示 pkulaw connected（绿），但调用仍失败。

## 二、问题演化链（逐轮误判 → 纠正）
| 轮次 | 当时判断 | 证据/动作 | 后续修正 |
|---|---|---|---|
| 1 | 双通道均不可用（pkulaw鉴权失败+元典余额0）→ 物理阻塞，固化为 backlog | 实测两源 | 正确，backlog 120 条固化 |
| 2 | "解绑重连只刷配置、运行进程持旧会话"→ 让用户重启 server | 误以为有独立重启按钮 | **撤回**：托管 HTTP connector 无重启按钮，架构不成立 |
| 3 | bridge.log `[90001]`=北法宝错误码；curl 60121/ 得 502=后端故障 | 误读日志 + 错路径 | **撤回**：`[90001]` 是进程 PID（同文件 `[40502][15022]` 佐证）；502 是路径错（应 `/<uuid>/mcp`） |
| 4 | 上一实例"点连接仍 90001"→ 坐死账号侧点数/绑定异常（亚型D-1） | 上一对话实例实测 | **校正**：那是旧实例曾加载 pkulaw 时实测；当前实例工具列表无它，调不到，无法验证 90001 是否还在 |

| 9 | 沉淀进 `workbuddy-connector-enabled-gate` 亚型D-1 补遗 | 技能更新 | 防下次重复误判 |

## 三、三层证据闭环法（本卡核心可复用方法论）
排查连接器异常，禁止单凭 UI 表象（connected 绿）下结论，必须分三层取证：

| 维度 | 查什么 | 本例结论 | 取证手段 |
|---|---|---|---|
| **账号层** | 充值账号与连接器绑定账号是否同一 | ✅ 用户确认同账号已充值 | 用户核对 + 90001 文案含 user UUID（请求已抵北法宝） |
| **连接/后端层** | proxy 是否真连通北法宝 | ✅ 通 | 读 `mcp-aluris-proxy/bridge.log`：`Connected to remote server https://aluris.top/mcp` + `Proxy established successfully`；进程 PID 在跑 |
| **本会话工具索引层** | 当前会话能否真调到该工具 | ❌ 未加载 | `ToolSearch` 无 + `connector-status` 无 + 直接调报 `not found in deferred tools index` |

> 🔑 **杠杆点**：三层任一维度都不能单凭 UI 表象判定。connected 绿只代表 WorkBuddy 连接配置生效（enabled + 令牌注入），不代表 upstream API 鉴权通过。

## 四、三次自我纠偏（本课最大思维价值）
1. **"运行进程持旧会话需重启 server"** → 错。pkulaw 是经本地 `connector-proxy(127.0.0.1:60121)` 转发的托管 HTTP MCP，宿主管、无独立重启按钮；UI 解绑重连只刷 OAuth 配置，动不了云端点数。
2. **"bridge.log 行首 [90001] 是北法宝错误码"** → 错。那是**进程 PID**（同文件还有 `[40502]` `[15022]` 相互佐证）；日志真实含义是"连接成功、STDIO 代理已建"。
3. **"curl 60121/ 得 502 = 后端故障"** → 错。是**路径错**（正确路径 `/<uuid>/mcp`），proxy 本身是活的，根路径无路由才 502。
4. **（隐含第4次）"点连接仍 90001 坐死账号侧"** → 需校正。那是**上一个对话实例**曾加载 pkulaw 时实测；当前对话实例工具列表根本没它，物理上调不到，谈不上验证 90001 是否还在。

## 五、根因定论与处置
- **根因**：宿主工具索引**对话级定型**——用户在当前对话中途点连接，工具列表在对话开启时已定型、不热加载。这是架构限制，不是操作错。
- **账号/连接层**：均正常（用户同账号已充值 + bridge.log 证 proxy established）。
- **唯一确定动作**：**开新对话**，pkulaw 自动加载后，我做两件事——
  - 若仍 `90001`：坐实 aluris.top 网关 ↔ 北法宝账号 `a4204ed9` 点数/绑定问题，拿 UUID 找 WorkBuddy/北法宝支持核（那时错误体最明确）；
  - 若通：直接消费 `case_verify_backlog.json`（**120 条高频缺口已就绪**），逐批 15 条核验注入 + 跑 T502 回归，缓存 45→165 条。

## 六、可复用排查 SOP（落 `workbuddy-connector-enabled-gate` 亚型D-1 补遗）
1. 遇连接器调用异常，**先查本会话工具索引是否真含该工具**（`ToolSearch` + 直接调），不在则开新对话重测，而非旧会话反复点连接/重启。
2. 新对话实测仍 `90001` → 读 `bridge.log` 确认连接层通 → 转账号/网关层（拿 user UUID 找支持）。
3. **读 proxy 日志务必区分进程 PID 与业务错误码**（行首 `[数字]` 多为 PID）。
4. **curl 托管 MCP 必须带 `/<uuid>/mcp` 路径**，根路径 502 是误导，勿据此判后端故障。
5. 零编造铁律：`exists` 未经验证源（pkulaw/元典）实返回的，绝不手写案例元数据入库；T502 未收录走 INFO 移交不阻断。
