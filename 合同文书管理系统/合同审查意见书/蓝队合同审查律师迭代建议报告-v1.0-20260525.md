## 二、10大维度升级建议

### 2.1 维度升级总览

| 维度 | 现状 | 升级方向 | 核心增量 |
|------|------|----------|----------|
| D01 主体信息 | 基础字段核验 | **主体穿透审查** | 关联关系识别、实际控制人追溯、资质有效性动态验证 |
| D02 金额数据 | 格式与计算核验 | **资金链路审查** | 资金流向合规性、税务影响评估、跨境支付风险 |
| D03 标点符号 | 格式规范检查 | **文义精确性审查** | 标点影响文义的识别、歧义标点预警 |
| D04 版式排版 | 格式规范检查 | **结构逻辑审查** | 条款逻辑层级、交叉引用一致性、定义条款完备性 |
| D05 页码标注 | 页码完整/连续 | **文档完整性审查** | 附件与正文对应、引用文件完整性 |
| D06 法律依据 | 法条引用核验 | **法律适用深度审查** | 法条时效性动态验证、类案裁判规则匹配、司法解释适用 |
| D07 行文表述 | 口语化/冗余检查 | **语义风险审查** | 模糊表述量化评分、语义歧义自动标注、条款漏洞识别 |
| D08 管辖法院 | 管辖有效性核验 | **争议解决策略审查** | 管辖选择策略优化、仲裁vs诉讼优劣分析、执行便利性评估 |
| D09 联系方式 | 准确性核验 | **送达可行性审查** | 送达方案完整性、多渠道送达冗余设计、变更通知机制 |
| D10 实质内容 | 风险点识别 | **交易结构审查** | 商业合理性验证、交易闭环分析、履约能力评估 |

### 2.2 重点维度升级方案

#### D01 主体信息 → 主体穿透审查

**现状**：检查名称、身份证号、统一社会信用代码格式

**升级方案**：

```
新增规则：
  D01-R01: 关联关系识别 — 同一自然人在多方法定代表人/董事任职 → 利益冲突预警
  D01-R02: 实际控制人追溯 — 股权穿透至实际控制人，识别隐名代理风险
  D01-R03: 资质有效性动态验证 — 通过知识库检索目标主体的行政许可有效期
  D01-R04: 主体变更预警 — 合同存续期内法定代表人/股东变更可能性评估
  D01-R05: 境外主体特殊审查 — 外商投资准入限制、外汇合规、境外送达可行性
```

**挂载知识库**：
- 企业信用信息公示规则（ima/LawKB）
- 外商投资负面清单（实时检索）

#### D06 法律依据 → 法律适用深度审查

**现状**：核验法条引用是否存在、是否现行有效

**升级方案**：

```
新增规则：
  D06-R01: 法条时效性动态验证 — 通过知识库+实时检索验证法条是否已被修订/废止
  D06-R02: 类案裁判规则匹配 — 关键条款自动匹配最高院指导案例/公报案例裁判要旨
  D06-R03: 司法解释适用性 — 识别应适用但未引用的司法解释
  D06-R04: 地方法院审判指引 — 根据管辖法院匹配地方高院/中院审判指引
  D06-R05: 法律适用冲突 — 新法与旧法、特别法与一般法的适用优先级判断
```

**挂载知识库**：
- 法规全文库（ima「律师职业进阶」知识库中的法规文件）
- 类案裁判规则库（LawKB/红队出庭律师仓库/常用法律法规库）
- 实时检索（WebSearch → 最高人民法院官网、北大法宝）

#### D07 行文表述 → 语义风险审查

**现状**：检查口语化表述、冗余表述

**升级方案**：

```
新增规则：
  D07-R01: 模糊表述量化评分 — "合理""适当""重大"等模糊词标注 + 风险评分
  D07-R02: 语义歧义自动标注 — 同一合同内同一术语不同定义的识别
  D07-R03: 条款漏洞识别 — 通过知识库规则比对，识别常见遗漏条款
  D07-R04: 权利义务对称性检查 — 甲方义务 vs 乙方义务的不对称预警
  D07-R05: 免责条款效力预判 — 格式条款提示义务、加重对方责任条款效力评估
```

**挂载知识库**：
- 模糊表述风险案例库（从114条文本监察官案例库中提取D07相关条目）
- 条款漏洞模板库（按合同类型分类的必备条款清单）

#### D10 实质内容 → 交易结构审查

**现状**：风险点识别、事实依据核验

**升级方案**：

```
新增规则：
  D10-R01: 商业合理性验证 — 交易对价是否公允、交易目的是否合法
  D10-R02: 交易闭环分析 — 合同是否覆盖交易全周期（缔约→履行→变更→终止→争议）
  D10-R03: 履约能力评估 — 对方资信状况、历史履约记录
  D10-R04: 合同联带风险 — 本合同与其他合同/交易的关联风险
  D10-R05: 公益合规特殊审查 — 募捐合规、资金使用合规、信息公开义务（《慈善法》专项）
```

### 3.3 规则库整合方案

**步骤1：去重合并**

```
合并策略：
1. 以 dimension_rules.json 为基准（61条维度规则）
2. 将 risk_rules.json 中不重叠的规则迁入 contract_rules/ 对应文件
3. 将 extended_risks.json 拆分为 contract_rules/ + risk_library/
4. 删除 合同风险规则库.md 中的重复条目，保留Obsidian格式知识卡片
```

**步骤2：规则ID统一**

```
规则ID编码规范（v10.0）：
  格式：[类型]-[维度]-[序号]
  
  类型前缀：
    DIM-  维度规则（10维度通用）
    CTL-  合同类型规则
    IND-  行业专项规则
    RSK-  风险案例规则
    
  示例：
    DIM-D01-001   主体名称一致性
    CTL-SALE-001  买卖合同-标的物交付条款
    IND-CHR-001   慈善组织-募捐合规
    RSK-HIGH-001  高风险案例-乙方主体不一致
```

**步骤3：动态规则加载**

```
加载策略（替代一次性加载893KB）：
1. 识别合同类型 → 仅加载对应 contract_rules/xxx.json
2. 识别行业属性 → 叠加 industry_rules/xxx.json  
3. 10维度扫描 → 加载 core_rules/dimension_rules.json
4. 高风险触发 → 按需加载 risk_library/ 中相关案例

预估加载量：从893KB降至 ~50KB/次
```

### 3.4 风险库建设方案

**目标**：从"规则列表"升级为"风险知识图谱"

```
风险知识图谱结构：

风险节点（RiskNode）：
  - risk_id: 唯一标识
  - risk_name: 风险名称
  - dimension: 所属维度
  - severity: 风险等级（0-100）
  - trigger_condition: 触发条件（自然语言 + 正则模式）
  - legal_basis: 法律依据列表
  - precedent_cases: 关联判例列表
  - remediation: 修改建议
  - related_risks: 关联风险ID列表
  
风险关系（RiskEdge）：
  - 互斥关系：两个风险不会同时出现
  - 因果关系：一个风险触发另一个风险
  - 缓解关系：修改A可缓解B
  - 升级关系：A未修改将升级为B
```

**数据来源**：

| 来源 | 内容 | 融合方式 |
|------|------|----------|
| 现有132条risk_rules | 规则定义+触发条件 | 直接迁移 |
| 114条文本监察官案例 | 错误案例+修正方案 | 提取为RiskNode |
| 16份审查意见书 | 实际发现的风险 | 提取+泛化 |
| 红队反向质疑规则库(27KB) | 攻击视角风险 | 转化为防御规则 |
| 实时检索（WebSearch） | 新法新规新判例 | 定期增量更新 |

## 四、知识库挂载与智能检索

### 4.1 当前知识库架构

```
知识库现状：
├── LawKB (本地Obsidian)          ← 审查时无法实时检索
│   ├── 规则库/合同风险规则库.md
│   ├── 蓝队律师合同审查/
│   ├── 红队律师合同审查库/
│   ├── 文本监察官系统/
│   ├── 合同审查意见书/ (16份)
│   └── ... (14个一级目录)
├── ima知识库 (云端)              ← 可通过API检索
│   ├── 律师职业进阶 (kb_id: 5Qm8a0...)
│   ├── 律师成长与职业进阶
│   └── ...
└── 腾讯文档 (协作平台)           ← 可通过MCP操作
    └── 合同文档、修订版合同
```

**核心问题**：审查执行时，LawKB作为纯本地Markdown仓库，无法被智能体实时检索；ima知识库可检索但内容不全。

### 4.2 知识库挂载方案

#### 方案A：三层挂载架构（推荐）

```
三层挂载架构：

Layer 1 - 内置规则层（技能本地，ms级访问）
  ├── config/rule_engine/         # 规则引擎（见3.2节）
  └── config/contract_type_features.json
  
Layer 2 - 知识库检索层（ima API，秒级访问）
  ├── 律师职业进阶                 # 法规全文、审查意见书、知识卡片
  ├── 合同审查规则库（新建）        # 从LawKB迁移的规则知识卡片
  └── 类案裁判规则库（新建）        # 指导案例、公报案例裁判要旨
  
Layer 3 - 实时检索层（WebSearch，10秒级）
  ├── 最高人民法院官网             # 最新司法解释
  ├── 北大法宝/威科先行           # 法条时效性验证
  └── 国家企业信用信息公示系统     # 主体资质动态验证
```

#### 方案B：LawKB → ima 同步管道

```
同步策略：
1. 将LawKB中的规则库、案例库内容以知识卡片形式同步到ima
2. 每次审查时通过ima API的search_knowledge_base检索
3. LawKB继续作为本地编辑和Obsidian笔记使用
4. 新增内容通过自动化任务定期同步

具体执行：
  Step 1: 将LawKB/规则库/ → ima「合同审查规则库」
  Step 2: 将LawKB/蓝队律师合同审查/ → ima「合同审查规则库」
  Step 3: 将LawKB/合同审查意见书/ → ima「律师职业进阶」
  Step 4: 将LawKB/文本监察官系统/ → ima「文本监察官案例库」（新建）
```

### 4.3 智能检索集成方案

```
审查流程中的知识库检索触发点：

第0阶段（背调）：
  → 检索ima：合同相对方历史审查记录
  → 检索WebSearch：对方主体资质、涉诉情况

第一阶段（文本提取）：
  → 无需检索

第二阶段（审查推理）：
  → 检索ima：同类合同的历史风险案例
  → 检索ima：相关法规和司法解释
  → 检索WebSearch：法条时效性验证（D06升级）
  → 检索WebSearch：对方主体资质动态验证（D01升级）

第三阶段（报告生成）：
  → 检索ima：同类审查意见书模板和措辞
  → 检索LawKB：文本监察官案例库匹配

第四阶段（结果交付）：
  → 自动存入ima知识库
  → 自动更新LawKB规则库（如发现新风险模式）
```

### 4.4 检索增强审查（RAG-Review）架构

```
RAG-Review Pipeline：

  合同文本
    │
    ▼
  [合同类型识别] ──→ 触发专项规则加载
    │
    ▼
  [10维度扫描] ──→ 发现风险点
    │
    ▼
  [风险点 → 检索查询生成]
    │              │
    ▼              ▼
  [ima知识库]   [WebSearch]
    │              │
    ▼              ▼
  [检索结果融合与去重]
    │
    ▼
  [风险点+法律依据+类案支撑 → 审查报告]
```

### 5.3 自适应审查策略

```
自适应审查策略矩阵：

  ┌─────────────────┬──────────┬──────────┬──────────┐
  │                 │ 简单合同  │ 标准合同  │ 复杂合同  │
  ├─────────────────┼──────────┼──────────┼──────────┤
  │ 风险等级低      │ 快速扫描  │ 标准审查  │ 深度审查  │
  │                 │ (10维度)  │ (10+专项) │ (全部维度) │
  ├─────────────────┼──────────┼──────────┼──────────┤
  │ 风险等级中      │ 标准审查  │ 深度审查  │ 深度+检索 │
  │                 │ (10+专项) │ (全部维度) │ (+RAG)   │
  ├─────────────────┼──────────┼──────────┼──────────┤
  │ 风险等级高      │ 深度审查  │ 深度+检索 │ 深度+检索 │
  │                 │ (全部维度) │ (+RAG)   │ (+红队对抗)│
  └─────────────────┴──────────┴──────────┴──────────┘

  合同复杂度判定因素：
    - 合同页数/条款数
    - 涉及金额
    - 合同类型（买卖<服务<技术<金融）
    - 跨境/跨法域因素
    - 公益合规要求
```

### 5.4 审查记忆与学习机制

```
审查记忆体系：

1. 案例记忆（Case Memory）
   - 每次审查结果自动提取为RiskNode，写入risk_library/
   - 新增风险模式自动生成规则草案，经人工确认后入规则库
   
2. 主体记忆（Entity Memory）
   - 合同相对方的历次审查记录
   - 对方常用条款倾向、谈判习惯
   - 对方履约记录（如有）
   
3. 条款记忆（Clause Memory）
   - 常见条款的风险分布统计
   - 按合同类型统计的高频风险条款
   - 条款修改成功率（修改建议被采纳的比例）

4. 反馈记忆（Feedback Memory）
   - 用户对审查结果的满意度反馈
   - 修改建议的采纳/拒绝记录
   - 误报/漏报案例的纠正记录
```

### 7.2 性能优化

```
优化目标：
  - 技能加载时间：< 5秒（当前 ~10秒，因893KB extended_risks.json）
  - 审查执行时间：< 3分钟（标准合同）
  - 知识库检索延迟：< 5秒（ima API）
  
优化措施：
  1. 规则按需加载（动态规则引擎，见3.3节步骤3）
  2. legal_document_review.py(205KB) 拆分为模块
  3. 缓存高频检索结果（法规时效性、类案裁判要旨）
```

### 7.3 版本管理规范

```
版本号规范（语义化版本）：
  MAJOR.MINOR.PATCH
  
  MAJOR: 架构变更（如v9→v10多智能体架构）
  MINOR: 规则库新增/维度升级
  PATCH: Bug修复/排版修正

规则库独立版本号：
  rule_engine/v2.3.1
  
变更日志：
  每次规则变更需记录：
  - 变更规则ID
  - 变更类型（新增/修改/删除/合并）
  - 变更原因
  - 影响范围
```

### 7.4 测试与验证

```
测试体系：

1. 回归测试集
   - 从16份历史审查意见书中提取测试用例
   - 每次规则变更后运行回归测试
   - 确保新规则不破坏已有审查结果

2. 对抗测试
   - 故意植入已知风险的合同样本
   - 验证规则检出率（目标 >= 95%）
   - 验证误报率（目标 <= 10%）

3. 红蓝对抗验证
   - 蓝队审查结果 → 红队攻击验证
   - 红队发现的漏洞 → 反哺蓝队规则库
```
