# 小德慈善组织合规管理系统 — 轨道1 改造方案 v2.0

> **决策人**：老强　**决策日期**：2026-09-12
> **一句话结论**：CMS 主线定为「**慈善组织合规管理模板**（轨道1）」；**轨道2 定为「基层医院合规管理模板」**（2026-09-12 由原「通用企业合规模板包」换轨，通用企业口径价值不大已废弃）；核心动作是**接线层**——把制度、审批流、字段表三类资产全部挂上 CMS 可消费的 ID 与法条依据。**两轨不得互相稀释。**

## 一、为什么这么定（诊断复盘）

### 1.1 原有三份文档的真实定位

| 文档 | 实际口径 | 与小德的冲突 |
|---|---|---|
| 制度清单文件（29 项） | 通用企业／大国企（首席合规官、董事会、合规管理委员会） | 慈善组织主体是**理事会／监事会／秘书长** |
| 审批流设计图（7 流程） | 销售／采购合同，四级会签 | 慈善组织核心是**募捐、资助、关联交易、信息公开** |
| 字段配置表（8 表） | 含税／不含税／税率／预付款 | 慈善组织关注**募捐成本、捐赠财产用途、受益人类别、公开募捐资格** |

**最刺眼的一条**：慈善合规在原文中仅列为「重点领域专项制度补充包」**第 29 项《公益捐赠合规政策》⭐ 视业务需要**——
即小德最核心、最能卖出溢价的能力，被降格为**末位可选项**。

### 1.2 已搭建 CMS 的真实形态（2026-09-12 实测）

| 层 | 实测内容 |
|---|---|
| SKILL 层 | `~/.workbuddy/skills/小德合规管理系统/SKILL.md`，**仅 1 个文件**，无脚本／模板／自动化 |
| 制品库 | `~/Documents/LawKB/小德合规管理系统/`：方案设计 10 份／落地报告 7 份／经验卡 **25** 张／HTML 交付件 2 份 |
| 商业化 | 年度顾问包 A ¥2.98万 / B ¥5.98万 / C ¥12.8万（⚠️ 与报价单口径冲突，待裁决） |

> **结论：已搭建的 CMS 是「知识与门禁层」，不是 IT 业务系统。三份新文档是「表单与流程层」。**
> 本方案的任务 = **把这两层焊起来**，而不是二选一。

## 二、双轨架构（最终定位）

```
                    小德合规管理系统（CMS）
                            │
        ┌───────────────────┴───────────────────┐
        │                                       │
   【轨道1 · 主线】                        【轨道2 · 并行】
   慈善组织合规管理模板                   基层医院合规管理模板
        │                                       │
   治理主体：理事会/监事会/秘书长          治理主体：院长/医务科/医疗质量管理委员会
   依据：慈善法 + 基金会管理条例等           依据：医师法 + 医疗纠纷预防和处理条例等
   对象：基金会/慈善会/社会服务机构          对象：社区中心/乡镇卫生院/一级二级医院
   档位：A 档 / B 档（溢价来源）            档位：⚠️ 待裁决（建议 ≥B 档）
   弹药：慈法合规 2 张 🔴                   弹药：医院合规 13 + 纠纷章卡 10 = 23 张 🟢
   法源：2 部 🔴                            法源：约 10 部 🟢
        │                                       │
   16 领域可售卖清单 ← 护城河              医疗纠纷章卡 16 章体系 ← 护城河
   139 条内规（厚德基金会）
        │
   ⛔ 已废弃：原通用企业口径三份文档（价值不大，不再对外交付）
```

> 🚩 **铁律：两个轨道不得互相稀释。**
> **「不稀释」≠「不互哺」** —— 稀释（价值拉平：资产白送／定价拉平／口径串味／法条混引）**禁止**；
> 互哺（方法论迁移）**允许**，但须标 `cross_track_ref`。隔离细则见《运维备忘录》§1.4。
> 16 领域可售卖清单 + 139 条内规 + LTI 门禁 = 慈善轨溢价来源；医院轨 23 张卡 + 医事法源 = 独立溢价。
> 绝不用低价轨把高价值轨拉平。

## 三、接线层设计（本次改造最高价值）

> **核心思路**：让表单系统成为 CMS 的「执行层」，CMS 成为表单的「大脑」。
> 三份文档从"孤立的设计稿"变成"可被 CMS 检索、可被 LTI 校验、可回写经验卡"的活资产。

### 3.1 制度清单接线规范

每项制度必须补三个字段：

| 字段 | 含义 | 取值域 |
|---|---|---|
| `cms_domain` | 六域归属 | 制度／流程／运营／财务／人资／税务 |
| `source_skill` | 承载技能 | `小德慈善合规中枢` / `医院合规与纠纷处理` / `合同文书管理系统(L0)` / `数据合规审查` / `税务合规审查` |
| `card_id` | 对应经验卡 | `慈法合规/经验卡片-xx-xx` 等；无卡时填 `CARD-TODO` |

### 3.2 审批流接线规范

每个控制节点必须补三项：

| 项 | 要求 |
|---|---|
| **法条依据** | 必须来自本地法律法规库；本地缺失 → 标 `statute_text_pending` + ⚠️ |
| **对应制度条款** | 指向 3.1 制度清单的具体制度 + 条款号 |
| **对应经验卡 ID** | 指向 `card_id`；无卡填 `CARD-TODO` |

### 3.3 字段表接线规范

每张表新增三个字段（通用，除纯配置表）：

| 新增字段 | 类型 | 作用 |
|---|---|---|
| `合规依据` | 多行文本 | 填写该记录所依据的法条／制度条款 |
| `经验卡ID回写` | 文本 | 沉淀时回填 `card_id`，形成"表单 → 卡库"反哺闭环 |
| `LTI校验状态` | 下拉 | 未校验／校验中／通过／REJECT |

> 💡 **`LTI校验状态` 是这套系统相对普通低代码模板的唯一护城河**——别人做不出来，因为别人没有 LTI 文本监控器。
