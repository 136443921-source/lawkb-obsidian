# 专项方案：R115 案例真实性补强 与 工程化最小改造

> 日期：2026-09-15
> 背景：承接《市场对标优劣势分析-2026-09-15》中"最值得借鉴市面的两点"——补 R115 案例真实性 + 工程化最小改造。
> 实证来源：实读 `LTI文本监控器/references/main.py`（781–801 行）、`yuandian_verify.py`（655–774 行）。

## 0. 前置判断（先给结论，不绕弯）

**一句话**：两个都该做，但优先级不同——**R115/T502 补强是 P0（直接护住文书质量，且代码框架已 80% 就绪，只差"接通+喂数据"）；工程化最小改造是 P2（当前单人本地使用不紧急，仅"对外交付/降复用门槛"时才硬需求）。**

| 项 | 现状真相（实读代码） | 紧迫度 | 工作量 |
|---|---|---|---|
| R115 案例真实性 | 已演进为 **T502**，框架在但**三缺口休眠** | 🔴 P0 | 小（1 脚本 + 1 默认参数 + 充值） |
| 工程化最小改造 | LTI 有局部日志，全系统无统一审计/备份登记 | 🟡 P2 | 中（审计层 + README + 隔离预留） |

**重要事实纠正**：memory 里写的"R115 只堵越界不堵伪造"是 **2026-08-30 的旧编号**；代码已演进为 **T502**（`wrap_output` 781–801 行 + `yuandian_verify.build_case_annotation`），且已实现"缓存确证不存在→CRITICAL→REJECT"的存在性堵截。**现在的真问题不是"没做"，而是"做好了没接通、没喂数据"**——这反而让补强极低成本。

## 方案 A：R115/T502 案例真实性补强（P0）

### A.1 三缺口诊断（基于实读）

| 缺口 | 代码现状 | 后果 |
|---|---|---|
| **① 默认静默** | `wrap_output` 的 `case_verify` 参数默认 `None` → `if case_verify is not None` 不成立 → T502 整段不执行 | 绝大多数调用方（文书技能/红蓝复核）不传该参，T502 **从不生效** |
| **② 缓存无自动回查** | `record_case_verification()` 只能手动写；**无"扫描案例→查元典→回填"脚本** | `case_verify_cache.json` 近乎空 → 所有案例落 `case_unverified`（INFO 不阻断）→ "编造→REJECT" 几乎永远触发不了 |
| **③ 元典余额 0** | `yuandian_get_user_balance` 实测 `pointBalance:0` | 在线回查前提断了；但**法随 fasui-caselibrary 免费通道可兜底** |

> 提取能力已就绪：`extract_case_requests()`（655–676 行）已支持案号 + 指导案例号正则提取；`build_case_annotation`（741–774 行）状态机 `case_fabricated/case_unverified/静默` 完整。**只差"接通"和"喂数"。**

### A.2 改造三件套

**A.2.1 强制接通（1 行级改动，零风险）**
- `main.py` `wrap_output` 默认参数由 `case_verify: dict = None` 改为 `case_verify: dict = None` 并在函数体首部：
  ```python
  if case_verify is None:
      try:
          from yuandian_verify import load_case_cache
          case_verify = load_case_cache()   # 默认接入缓存；空缓存→仍报 case_unverified，不误杀
      except Exception:
          case_verify = {}
  ```
- 效果：所有调用方**零改造**即获得 T502 防护；缓存空时只 INFO 移交，不阻断（向后兼容）。

**A.2.2 自动回查脚本 `case_verify_backfill.py`（新建，核心交付）**
- 流程：扫 `LawKB` 在办案卷 + 近期文书 → `extract_case_requests()` 提取案例 → 逐条调 **法随 fasui-caselibrary**（免费优先）→ 失败/缺失再调 **元典 `rh_case_details`**（传 `ah` 案号，`type` 选 ptal/qwal）→ 存在记 `exists=True`、查无记 `exists=False` → `record_case_verification()` 写缓存。
- 量化成本：元典案例回查 ~20–30 积分/次；单案卷引用 5–10 案例 → 100–300 积分/案。**优先法随免费通道，元典仅补差**，预计充值 **500–1000 积分**即可覆盖常用案例库。
- 幂等：以规范化案号为键，已核验（含 exists=False）跳过；写前自动 `.bak` 备份（六-B 铁律）。
- 门禁：脚本跑完须 `python -c "import yuandian_verify; ..."` 回归——真案例静默、编造案号 REJECT，二者都验证通过才收口。

**A.2.3 元典余额前提（运维动作，非代码）**
- 路径：open.chineselaw.com → 控制台「我的积分」→ 充值中心（前轮已查证）。
- 兜底：法随 fasui-caselibrary 已连接则优先免费通道，元典余额仅作补充，**不阻塞 A.2.2 启动**。

### A.3 接入点清单（改后自动覆盖，无需逐个改）
文书草拟/红蓝复核/模拟法庭产出等所有经 `wrap_output` 的输出，因 A.2.1 默认接通，**一次性全量生效**。

### A.4 验证（收口标准）
- [ ] 编造案号（如不存在的 `(2026)黔0330民初99999号`）→ T502 CRITICAL → REJECT ✅
- [ ] 真实案号（如 6658 号）→ 静默通过 ✅
- [ ] 缓存空时 → 仅 INFO 移交，不阻断 ✅
- [ ] 元典余额 0 但法随通 → 回查仍可行 ✅

### A.5 风险与降级
- 元典/法随均不可达 → 退回 `case_unverified` INFO（不阻断，宁漏勿误，与现状一致）。
- 案号正则漏提（如"某高院(2023)某民终某号"非标准格式）→ 漏提部分不核验，靠人工 + 红蓝复核兜底。

### B.2 改造三件套（务实，不做 SOC2）

**B.2.1 统一审计日志层 `audit_log.py`（新建，复用 LTI 容错思路）**
- 落 `~/.workbuddy/logs/audit/audit_YYYYMMDD.jsonl`，字段：`ts/caller/action/object/result/duration_ms`。
- 所有技能/自动化写前动作统一调用 `audit_write(caller, action, object)`；全函数 try/except 吞异常，审计失败绝不阻断业务。

**B.2.2 写前备份登记（固化六-B）**
- 新增 `pre_write_backup(path)`：cp 到 `/tmp/lti_bak_时间戳/` 并写一行到 `backup_manifest.jsonl`（原路径+备份路径+时间），使"备份过"可查、可回滚。

**B.2.3 运维 README + 角色隔离预留**

- 角色隔离：本地单人场景**暂不做**；若对外（助手/客户）交付，在 `audit_log` 加 `role` 字段 + `~/.workbuddy/access/` 简单 token 校验（预留接口，不实现）。

### B.3 明确不做（边界，避免 scope creep）

### 二、关键事实（落地中发现）

- **缓存非空白**：`case_verify_cache.json` 已有 **12 条 `exists=True` 真实类案**（元典 2026-09-06 核验过，含 6658 自案号；detail 详尽可信；**无编造案号被误标 True 的危险条目**）。默认接通后：这 12 条静默、其余未收录案例走 `case_unverified → INFO` 移交（不阻断）。
- **INFO 噪音提示**：默认接通后，引用未收录案号的输出会冒一条 `[T502] 案例存在性待核验` INFO（不阻断），属方案"A.4 收口标准"预期行为。降噪路径：元典充值后跑 `--scan` 拿待回查清单 → 对话内调 `rh_case_details(ah=案号)` 核验 → `--inject` 回填，常用案例全收录后噪音趋零。若老强认为 INFO 仍不可接受，可删 `build_case_annotation` 的 `elif case_unverified` 分支改为完全静默（REJECT 命门不受影响）。
- **Edit 工具异常**：本次发现 Edit 工具对 `/Users/chenyouqiang/.workbuddy/` 下部分文件写入不稳定（返回 Success 但实际未落盘/部分落盘），已改用 Python 脚本精确替换绕过。**后续改 `.workbuddy` 下代码优先用 Python 脚本或 Bash 写文件**。
