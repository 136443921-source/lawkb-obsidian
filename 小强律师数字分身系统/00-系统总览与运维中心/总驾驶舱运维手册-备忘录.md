## 一、总则与对标说明

总驾驶舱对标 Harvey Command Center 的核心理念：**把分散的法律 AI 子系统收敛到一个统一的运维指挥面**，做到"一眼总览、分级响应、合规为前提、变更可回滚"。

| Harvey Command Center 维度 | 本系统落地方式 |
|---|---|
| 统一指挥面（Single Pane of Glass） | 门户统一入口 + 九屏统一作战地图（评分导航）+ C1–C9 分屏导航 |
| 服务级别与责任人（SLA & Ownership） | 每屏设敏感度分级、刷新频率、负责人；详见第三章 |
| 可观测性（Observability） | 六维评分模型（0–100）+ 周自动化实算总维度评分 |
| 事件分级与响应（Incident Severity） | P0–P3 四级，配值守自动化与升级路径 |
| 变更门禁（Change Gating） | 六-B 铁律：备份 / dry-run / 幂等 / 回滚，写入型动作强制门禁 |
| 合规优先（Compliance-First） | 严禁外发清单 + 对外唯一脱敏出口（白皮书）；法律数据零外泄为硬性指标 |
| 审计可追溯（Auditability） | 每次变更先备份到 `/tmp` 时间戳目录，动作记工作日志与飞轮 LOG |

**核心原则**：总驾驶舱是"只读观察面 + 轻量导航"，本身不持有业务数据；所有数据由九屏各自的源（本地知识库 / 连接器 / 部署副本）生产，门户只做内嵌与跳转。

## 四、可观测性：六维评分体系

**六维定义**：数据新鲜度 / 覆盖完备度 / 运行健康度 / 产出有效性 / 安全合规度 / 自动化程度。

## 六、事件响应 Runbook

### 6.1 通用升级路径

```
P0/P1 触发
  → 先确认影响面（curl 抽查门户/评分卡/涉事分屏 HTTP 状态）
  → 若为部署误伤：用最近 /tmp 备份回滚到上一稳定版本，重部署
  → 若为数据源失效：隔离该分屏标签（rbac.js 暂摘）、其余保持可用
  → 30min 内无法自恢复 → 上报老强，标注"待人工"
  → 事后写工作日志 + 飞轮 LOG，复盘进"事件卡"
```

### 6.2 常见事件处置

- **门户首页 404 / 非 200**：检查 `cockpit-portal-map` 部署是否成功；用 `workbuddy_sites_deploy --updateExistingApp appId=wbapp_Q3LunDxyzTuacaQi1h4zrm` 重发。
- **某分屏标签点不开（404）**：99% 是 URL 漂移或旧死链回潮。先核对 `rbac.js` 的 `sites` 与 C1–C9 页 `SCREENS` 对齐（见第十章 SOP-02）。
- **评分卡出现 NaN / 总分漂移 > 1 分**：跑 `scan_scorecard.py --apply` 前必 `--json` 预览；NaN 多为某分屏数据源返回非预期结构，定位 `P_*` 路径常量。
- **决策思维树空白**：`cards=null` 表明源 `Desktop/决策思维树.html` 内嵌数据未更新或路径变更，触发 `刷新决策树.js` 重扫 `04-LOG/决策日志/`。

## 七、变更管理（六-B 铁律 + 红线）

所有写入型动作（改 rbac.js / index.html、重部署、刷新数据源、自动化改动）**强制走门禁**：

1. **先排查**：确认改动范围与影响面，不动未核实项。
2. **先备份**：改前 `cp -n <源> /tmp/<名>_$(date +%Y%m%d_%H%M%S).<ext>`。
3. **dry-run**：默认只算不写（如 `scan_scorecard.py` 默认 dry-run）；部署前先在本地校验。
4. **幂等可重跑**：脚本须可重复执行不产生副作用，写入前比对"是否已是目标态"。
5. **再写入**：确认非误报/非误伤后落盘；跨 workspace 操作尤须锁定 appId，防误伤他站（2026-09-12 曾因 `updateExistingApp` 跨 workspace 误伤 LTI 站点）。
6. **回滚就绪**：保留备份，失败时 1 条命令还原。

**红线**：
