# 卡库统一调度与一人公司机制联结方案 · v1.0

> 背景：知识飞轮系统经 WF-028 卡库接线，已将 **698 张（二次补挂）+ 1 张（非标 rule_id 兜底，R-HG-医疗合规-疗效承诺禁止）= 699 张**规则卡注入 9 个消费技能 `SKILL.md` 检索指令段。挂载完成，但"挂了之后怎么统一调度、怎么纳入一人公司资产治理"尚缺机制。本方案给出三层联动设计。

> ⚠️ **【数据更正声明 · 2026-10-07】** 本方案初稿称"挂载完成"。经全量注册表 `card_route_registry.yaml`（2503 张 SSOT）三重实测修正后，**真实挂载率 91.4%（2289/2503），非此前表述的近 100%**。此前"99.92%"为三处测量假象叠加（R-前缀正则漏判 / 技能目录名取错 / 元技能引用注水），已逐一定位实测推翻。真实待办：**214 缺口（系统性 ~8.6% 均匀分布）+ 6 冲突 + 9 错挂**，且「法律检索助手」兜底过宽。详见同目录 `卡库统一调度-消费技能与域覆盖复盘-v1.0.md`（Task #7 复盘结论 + 方案 A/B/C）。

**当前痛点**：挂载是"声明式"——技能被告知"可检索这些 rule_id"，但缺三样东西：
1. **统一路由注册表**：9 个 SKILL.md 段各自隐式存 rule_id，无一张显式 SSOT 让任意席位解析 `rule_id → 技能 → 卡正文`。
2. **消费可观测性**：哪些卡真被技能用、哪些沉睡（usage=0），无遥测。
3. **与一人公司资产治理联结**：卡是核心数字资产，却未纳入资产运维官 SSOT 登记册 / 可视化监控屏。

## 二、总体架构（三层联动）

```
┌─────────────────────────────────────────────────────────────┐
│  一人公司管理层（单 CEO 老强）                                  │
│   资产运维官(SSOT登记册) ←→ 可视化监控运维官(9655驾驶舱屏)      │
└───────────────┬───────────────────────────┬──────────────────┘
                │ 登记/监控                    │ 调度/编排
┌───────────────▼───────────────────────────▼──────────────────┐
│  分身系统调度总线（seat-orchestrator 主任编排引擎）             │
│   任务 → 域识别 → 查 卡库路由注册表 → 派 seat → 拉卡消费         │
└───────────────┬───────────────────────────┬──────────────────┘
                │ 路由查询                     │ 消费回写
┌───────────────▼───────────────────────────▼──────────────────┐
│  卡库路由注册表 card_route_registry.yaml（SSOT·卡库DNS）        │
│   rule_id → 域路径 → 对口技能 → 检索指令 → 挂载时间 → 版本/状态  │
└───────────────┬───────────────────────────┬──────────────────┘
                │ 反向抽取                     │ 一致性校验
┌───────────────▼───────────────────────────▼──────────────────┐
│  9 个技能 SKILL.md 检索指令段（WF-028 挂载落点）                 │
│   + 知识飞轮系统 2508 张活跃卡（卡片宇宙）                       │
└─────────────────────────────────────────────────────────────┘
```

## 三、第一层：卡库路由注册表（统一调度中枢 · SSOT）

**动作**：把散落在 9 个 SKILL.md 段的 rule_id 提升为**一张显式注册表** `card_route_registry.yaml`，作为分身系统的"卡库 DNS"。

字段设计：
```yaml
version: 1
generated: 2026-10-07
rules:
  - rule_id: R-JG-007
    domain: 06-沉淀/建设工程域库
    skill: 判决书分析助手
    card_file: R-JG-007-装饰装修合同的定性与法律适用二分.md
    mounted_at: 2026-10-07
    status: active        # active / deprecated / conflict
    usage_count: 0         # 由 05-调用 聚合回填
    last_used: null
  # ……699 条
```

**生成方式**：脚本反向抽取 9 个 SKILL.md 的 `| R- | 域路径 | 卡文件 |` 表 + 域→技能映射，落地为 yaml（复用 `/tmp/supplement_wire2.py` 的 DEDICATED 映射逻辑，新增导出步骤）。**幂等**：重生成仅更新 `usage_count/last_used/status`，不破坏手写段。

**价值**：挂载与消费解耦；新增卡只改注册表 + 对应 SKILL.md 段；避免 9 文件各自漂移；任何 seat/agent 解析 rule_id 查表即得，无需各自 grep。

## 四、第二层：分身系统调度总线（统一调度）

**seat-orchestrator（主任编排引擎）** 作为 dispatcher，新增一条 SOP：
1. 接到任务 → 提取案由/域标签（如"医疗损害责任纠纷"→ 人伤法域）。
2. 查 `card_route_registry.yaml` → 定位对口 seat（技能）。
3. 派 seat 执行，seat 按 rule_id 在知识飞轮系统定位卡正文、回溯消费。
4. seat 调用卡时，**回写消费轨迹**到 `05-调用/<域>调用记录/`（已是现成体系）→ 注册表 `usage_count++ / last_used=今日`。

**卡消费协议**：每条调用记录含 `rule_id + 消费技能 + 案件 + 回溯结论`，与现有 WF-028 第五步实战验证记录同构。注册表 `usage` 字段定期（日/周）从 `05-调用` 聚合回填。

## 五、第三层：与一人公司机制联结

复用分身系统**已有的卡规模监控基座**（不另起炉灶）：
- `00-系统总览与运维中心/card_scale_baseline.json`（卡规模基线）
- `00-系统总览与运维中心/count_rules.py`（rule_id 计数器）
- `00-系统总览与运维中心/card_scale_drift_report.json`（漂移报告）

**资产运维官（Digital Asset Ops Officer）**：
- 把 `card_route_registry.yaml` 登记为数字资产 SSOT 登记册的一项（"知识飞轮卡库·已挂载 699"）。
- 职责：编目、健康监控、漂移追杀——卡文件被删/改名 → 注册表 `status=conflict` 告警；注册表与 SKILL.md 段 diff → 告警。

**可视化监控运维官（9655 驾驶舱）**：
- 新增一屏"卡库挂载健康"：挂载率、各技能卡数、沉睡卡（usage=0 超 N 天）、冲突卡（同 rule_id 多技能）、漂移数。
- 数据源自注册表 + card_scale_drift_report.json。

**调度纳入一人公司节奏**：
- 沿用现有 `04-LOG` / 月度快照机制，把"卡库调度健康"纳入周/月报（资产运维官出数、主任编排引擎出调度摘要）。

## 七、铁律护栏（沿用老强规则）

- **否定型结论实测**：沉睡卡/冲突卡判定靠 `05-调用` 真实 usage 与注册表 diff，**不凭记忆/回显**下结论。
- **六-B 备份**：注册表重生成前 `cp -n` 备份旧版；改前先 dry-run。
- **防漂移**：注册表与 9 段定期一致性校验，diff 告警（沿用 card_scale_drift 机制）。
- **裁决项二次核验**：本方案为提案，落地各步（尤其 seat SOP 改动、监控屏新增）待老强定夺后实施，未定夺不出文件。

## 八、价值小结

- 挂载从"挂了不管"升级为**可观测、可调度、可治理的活资产**。
- 一人公司单 CEO 经资产运维官 + 9655 监控屏，**一眼掌握全部卡资产健康**（挂载率/沉睡/冲突/漂移）。
- 与现有基座（card_scale_* / count_rules / seat / 资产运维官 / 可视化监控运维官）零冲突衔接，增量建设。

## 九、待老强定夺项

1. 注册表落点：放 `00-系统总览与运维中心/` 还是 `10-律所数字分身中台/`？

3. 沉睡卡阈值 N 天（建议 30 天）与处置策略（降级/补调用/删注册表项）？
