# Docling 缺口评估（pdf-dual 双路解析的"另一路"）

> 评估日期：2026-10-31 23:37–23:55
> 结论口径：**只做可行性 + 成本评估，未下载、未安装**（除已有的空壳 venv 外，磁盘未变动）
> 评估对象：`pdf-dual-parse-markdown-ingest` 的 Docling 主解析通道

---

## 一、结论先说

**不建议现在装。** 三个理由，按分量排：

1. **装完也跑不通**——`pdf-dual` 的 Docling 通道有 **3 处 Windows 硬编码**，macOS 上必然翻车（比 MinerU 那个 API 问题更硬）。
2. **模型下载要绕**——HuggingFace 直连 **8 秒超时**，必须走 `hf-mirror.com`（实测 200/0.6s）才能装上，否则会重复 10-30 那次"下载中断"。
3. **收益与现有能力重叠**——页码核验已有 `pymupdf 1.27.2.3` 的零依赖方案（Phase 1.5 本来就这么设计）；MinerU 扫描件实测字符相似度 **99.6%**。

**建议走方案 A**（用 pymupdf 补 `document_map`，不装 Docling）；确有复杂表格扫描件需求再考虑 B。

---

## 二、三条硬证据

### 证据 1：Docling 通道在 macOS 上有 3 处 Windows 硬编码

| 位置 | 代码 | macOS 后果 |
|---|---|---|
| `scripts/paths.py:278` | `SERVE_EXE = DOCLING_HOME / 'docling-serve.exe'` | 硬拼 `.exe`；macOS 的可执行文件叫 `docling-serve`，永远找不到 |
| `scripts/serve_guard.py:84` | `subprocess.run(['taskkill','/F','/IM','docling-serve.exe'])` | macOS 无 `taskkill` |
| `scripts/docling_serve_batch.py:146,149` | 硬编码 `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe` | 路径不存在 |

实测旁证：`doctor.py --serve` 已直接报 `docling-serve FAIL ValueError: creationflags is only supported on Windows platforms`（`subprocess` 的 Windows 专属参数）。

⇒ 这与 MinerU 那个"参数改名 + 协议错位"是**同一性质的问题**：上游按 Windows 写死。修得动，但要再打一轮平台补丁（3 处），且每次重装技能都要重打。

### 证据 2：模型必须走 HF 镜像

| 目标 | 结果 |
|---|---|
| `https://huggingface.co` | ❌ **8 s 连接超时**（curl 28） |
| `https://hf-mirror.com` | ✅ HTTP 200，0.6 s |

Docling 的版面/表格模型默认从 HF 拉。不设 `HF_ENDPOINT=https://hf-mirror.com` 就会卡在下载——这正是 10-30 那次"docling 阶段 33 分钟零写入"的最可能成因（当时未定位到这一层）。

### 证据 3：收益与现有能力重叠

| 需求 | 现有方案 | Docling 能多给什么 |
|---|---|---|
| 权威物理页码 | `pymupdf 1.27.2.3` 逐页渲染 + 首行标题识别 → `document_map`（Phase 1.5 既定设计，零额外依赖） | 更省事，但结论同源 |
| 正文转写 | MinerU CLI：文字层 PDF 16/16 字段、扫描件 99.6% | 阅读顺序/表格结构可能更好 |
| 表格 | MinerU 输出保留为 MD 表格 | Docling 的 TableFormer 对复杂表更强 |
| 交叉校验 | 单引擎 + 人工复核告警点 | 双引擎差异比对（理论价值最高的一项） |

**真正只有 Docling 能补的**：复杂表格（财务报表、鉴定意见附表）的结构化，以及双引擎差异比对。普通案卷（起诉状/合同/判决书）用不上。

## 四、成本估算

> 标注"估算"的为推算值，未实测下载。

| 方案 | 磁盘增量 | 代码改造 | 估时 | 风险 |
|---|---|---|---|---|
| **A 不装**（pymupdf 补页码核验） | **0** | 无（写 1 个脚本） | 30–45 min | 低 |
| **B 只装 Docling CLI**（做对照，不接 pdf-dual） | 估算 0.6–1.1 GB | 无 | 40–60 min | 中（HF 镜像必须配对） |
| **C 全接双路**（装 + 打 3 处平台补丁 + 全链路验证） | 估算 0.6–1.1 GB | **3 处 Windows 硬编码** | 1.5–2.5 h | 高（重装即失效） |

**磁盘细账（方案 B/C）**

- 若装进**现有 `venvs/mineru`**（共享 torch 626 MB + transformers 115 MB）：docling 本体及依赖估算 300–500 MB + 模型 300–600 MB（HF 镜像，未实测）→ **合计约 0.6–1.1 GB**
- 若装在**独立的 `venvs/docling`**：还要再下 torch 626 MB + transformers 115 MB → 约 1.3–1.8 GB（但可先删掉那 995 MB 空壳，实际净增接近）

## 五、三个方案，我推荐 A

### 方案 A（推荐）：不装 Docling，用 pymupdf 补 `document_map`

- 做法：pymupdf 逐页渲染 → 识别每页首行标题/关键字段 → 与 MinerU 输出交叉比对 → 写 `metadata.json` 的 `document_map`，供 Phase 1.5 引用坐标使用。
- 收益：把"页码可信"这件事做实，且**零依赖、零维护**（pymupdf 已在盘）。
- 局限：不做双引擎差异比对；复杂表格结构化仍靠 MinerU。

### 方案 B（备选）：只装 Docling CLI 做对照，不接 pdf-dual

- 适用：确有大量复杂表格扫描件（如鉴定意见附表、财务报表）。
- 做法：装进 `venvs/mineru` 共享 torch，先删 995 MB 空壳；`HF_ENDPOINT=https://hf-mirror.com`；只用 `docling` CLI 单文件试跑，**不动 pdf-dual 代码**。
- 好处：拿到 Docling 能力，但不背上游补丁的维护债。

### 方案 C（不推荐，除非明确要双路）：全接双路

- 需改 3 处 Windows 硬编码 + 打 MinerU 那轮补丁一起维护，每次技能重装都要重打。
- 收益仅"双引擎差异比对"，而当前 99.6% 的准确率下，这项收益很薄。

## 六、若你决定装（方案 B/C 通用步骤）

```bash
# 1) 先回收空壳（删前请确认没有其它工具在用）
du -sh ~/pdf-docai/venvs/docling     # 995M

# 2) 走 HF 镜像（关键，否则必卡）
export HF_ENDPOINT=https://hf-mirror.com

# 3) 优先装进已有 mineru venv，共享 torch（省 740MB）
~/pdf-docai/venvs/mineru/bin/pip install -i https://mirrors.aliyun.com/pypi/simple \
  --resume-retries 40 docling==2.145.0

# 4) 验收
~/pdf-docai/venvs/mineru/bin/python -c "import docling;print(docling.__version__)"
```

> 镜像经验复用：**清华源在本机反复中断，阿里云 + `--resume-retries 40` 一次过**（10-30 装 MinerU 时验证过）。别再用清华源。
