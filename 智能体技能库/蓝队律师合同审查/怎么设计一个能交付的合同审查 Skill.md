 # 怎么设计一个能交付的红队律师合同审查 Skill

## **1.法律AI的风险在提交**
    - **风险节点**：法律AI的风险不在于生成内容，而在于将生成的内容从草稿区提交给客户、业务、合伙人或法院的那一刻，责任随之变化。
    - **核心观点**：法律人需要关注的是如何将AI生成或辅助生成的内容从草稿区提交出去，并确保其质量和责任边界。
## 2.**合同审查Skill的设计**
    
    - **插件系统**：一个真实可用的合同Skill应像一套小型插件系统，包含入口、路由、专项插件、反向质疑、Hooks、交付门禁、审计日志和回炉机制。
    - **分诊系统**：合同审查不应是一个大而全的超级Skill，而应是一个入口Skill，先进行分诊，判断合同的类型和审查需求。
## 3.**Submission Gate（交付前总闸）**
    
    - **重要性**：Submission Gate是交付前的总闸，确保范围、来源、复核、降级和责任边界都已被显式处理过。
    - **门禁内容**：包括Scope Check、Source Check、Reverse Challenge Check、Specialist Check、Human Review Check、Output Form Check和Disclosure Check。
## 4.**反向质疑（Reverse Challenge）**
    
    - **目的**：反向质疑不是唱反调，而是为了防止确认偏误和单边论证，确保AI在交付前多想一层。
    - **具体问题**：包括对方律师的反驳、谈判筹码、行业惯例、交易效率、举证难度、遗漏附件和客户问题等。
## 5.**插件化工作流**
    
    - **入口Skill**：调度一组插件，根据合同类型和审查需求进入专项审查路径。
    - **插件示例**：包括Intake Router、Entity Check、Prompt Injection Scan、Contract Type Router、Clause Specialist、Quant Overlay、Reverse Challenge、Comment Writer、Summary Writer、Opinion Writer、Flowchart Builder和Submission Gate。
## 6. 责任控制
    - **插件化价值**：插件化不是为了炫技，而是为了控制责任，确保每个专项问题由专门的插件处理，避免通用Skill什么都管但不深入。
    - **分工与边界**：律师事务所分团队的原因在于不同领域的专业性，AI工作流也应如此，通用Skill应知道何时将问题交出去。
## 7.**提交前的机制**

- **Submission Gate的重要性**：AI时代，真正的风险在提交，Submission Gate是一张交付前检查表，确保每一步都经过严格审查。
    - **检查表内容**：包括材料脱敏、审查立场、合同类型识别、专项插件调用、重大风险来源绑定、反向质疑完成、人工复核事项单列、外部检索披露降级情况、输出区分批注、概要、意见、流程图和说明AI参与范围等。
## 8.**Skill的规模与价值**
    
    - **三档规模**：玩具级（一个SKILL.md）、工作流级（入口Skill加5到8个references加2到3个脚本加几份测试样例）、产品级（入口Skill加专项插件加外部检索加量化叠加加反向质疑加Submission Gate加审计日志加eval样例）。
    - **价值所在**：真正值钱的部分在于路由表、专项插件、反向质疑清单、Submission Gate和审计日志，而不是单一的SKILL.md文件。
## 8.**工具与资源**
    
    - **工具**：包括Claude Code / Codex装机、法律Skill写法、脱敏工作流、MCP接入、合同审查、案卷整理和人工复核清单。
    - **社群**：法律AI工作流训练场，每周一个任务，一份材料，一套参考路径，把“收藏教程”变成“真的跑通”。

BUYUN FADIANSkillRouterSubmission我是怎么设计一个能交付的合同审查 Skill 的法律 AI 的风险，不在生成。在提交。故事是这样的。我这几天一直在改上一篇稿子。改到后面，我发现这篇真正想讲的，其实不是 SkillCreator。

而是另一件事。法律 AI 的风险，不在生成。在提交。你什么时候把一个 AI 生成或辅助生成的东西，从草稿区拿出来，发给客户，发给业务，发给合伙人，甚至发给法院？

这一刻，责任就变了。所以这篇你只需要拿走三样东西。

一张插件路由表,一套反向质疑清单。一张 Submission Checklist。这三样东西，决定一个合同 Skill 是玩具，还是一套能进入真实法律工作流的东西。

[ THESIS ]法律 AI 的风险，不在生成。真正发生责任变化的节点，是把草稿提交出去。SkillCreator 当然有用。它可以帮你生成第一版 SKILL.md。但它不能替你决定，这个 Skill 的规模、路由、门禁和责任边界。

这才是法律人真正要手写的部分。我说的规模，不是字数长。

而是 Scale。一个真实可用的合同 Skill，不应该只是一份 SKILL.md。它应该更像一套小型插件系统。有入口。有路由。有专项插件。有反向质疑。有 Hooks。有 Submission 前的交付门禁。有审计日志。有失败后回炉的机制。这才是我现在真正想写的东西。

说实话，我也是这次重新看自己自用的合同审查 Skill，才意识到这件事。我以前会说，法律 Skill 的关键是让 AI 知道什么时候停。现在我觉得还要再补一句。法律 Skill 的关键，是让 AI 在停下来之前，知道自己该把哪些问题交给谁。这就不是单文件 Skill 了。这是插件化的工作流。

[ 01 ]不是一个文件，而是一套分诊系统先看一个最普通的 Skill 生成器会给你什么。大概是这样

```
name: contract-reviewdescription: 审查合同，识别风险并提出修改建议。 workflow:1. 阅读合同2. 提取关键条款3. 识别风险4. 提出修改建议5. 输出审查报告
```

这东西不能说没用。它可以当草稿。但它离真实合同审查还很远。

因为真实合同审查不是一条直线。它更像一个分叉很多的交通路口。用户说「帮我看一下合同」，这句话背后至少有 6 种可能。是签约前谈判？是履约过程中排雷？是对方已经违约之后，看能不能解除？是两版合同对比？是投资条款？是租赁？是 NDA？是带对赌、反稀释、清算优先、Earn-out 的融资文件？你看，问题一下子就变了。

所以我现在不会把 contract-review 写成一个大而全的超级 Skill。我会把它写成一个入口。一个入口 Skill。它自己不急着审。它先分诊

```
contract-review/├── SKILL.md                  # 入口，不直接吞掉所有合同├── references/│   ├── checklist.md           # 四层审查清单│   ├── language.md            # 批注语言风格│   ├── summary.md             # 合同概要模板│   ├── opinion.md             # 综合意见模板│   ├── flowchart.md           # 业务流程图规则│   └── specialist-routing.md  # 专项插件路由├── scripts/│   ├── pre_scan.py            # 隐藏指令扫描│   ├── brief_loader.py        # 场景 brief 硬加载│   ├── review_auditor.py      # 交付前审计│   └── submission_gate.py     # Submission 门禁└── evals/    ├── supplier_side_case.md    ├── buyer_side_case.md    └── missing_background_case.md
```

这才像一个能长大的东西。不是一个文件。是一组可以互相调用、互相拦截、互相复核的部件。回到我之前那篇法院文章给我的启发。那篇写得不算爆。但里面有一个判断，我现在觉得非常重要。我当时写过一个判断，法院敢用 AI，不是因为模型更强，而是因为流程更硬。这个判断不是说律师工作和法院工作一样。我的意思是，司法 AI 的很多公开实践都在提醒我们，同一个原则很重要。AI 可以进流程。但不能绕过关键节点。它可以跑。但每到关键节点，人要确认。这个东西放到合同 Skill 里，就是 Submission。我这里说的 Submission，不一定是向法院提交文件。也包括律师把审查意见发给客户之前，法务把意见发给业务之前，团队把合同风险提交给决策者之前。凡是输出要从工作区流出去，都应该经过 Submission 门禁。换成人话说，Submission Gate 不是免责声明。它是交付前质量控制、责任边界确认、未核验事项披露。

这一步太重要了。很多 AI 法律工具最危险的地方，不是中间写错。是它把半成品包装成成品。

[ 02 ]Submission Gate，交付前的总闸。所以我的合同 Skill 里，Submission 前至少要过这几道门。

```
Submission Gate 1. Scope Check   是否披露了审查范围、立场、材料限制？ 2. Source Check   每个重大风险是否绑定原条款、事实来源或外部核查来源？ 3. Reverse Challenge Check   是否生成过反向质疑清单？ 4. Specialist Check   是否识别过需要专项插件处理的条款？ 5. Human Review Check   哪些结论必须由人复核？是否单独列出？ 6. Output Form Check   批注、概要、综合意见、流程图是否各司其职？ 7. Disclosure Check   是否说明 AI 参与范围、未核验事项和降级情况？
```

过了这道门，不等于结论一定正确。它只说明一件事，范围、来源、复核、降级和责任边界，都已经被显式处理过。这一层，才是和普通 Skill 教程拉开差距的地方。普通 Skill 教程会告诉你，输出前加一句「请检查」。但真实法律工作里，「请检查」不够。要变成门禁。没过，就不能提交。我现在越来越觉得，法律 Skill 的 Hooks，不应该只理解成技术上的自动触发。

它更像法律工作流里的刹车片。如果说 Submission Gate 是出门前的总闸，Hooks 就是每个关键节点的强制刹车点。

甚至可以说，是职业习惯的插件化。比如一个合同审查 Skill，至少应该有这些 Hooks。

|---|---|---|
|Hook|触发节点|拦截什么|
|立场 Hook|实质审查前|没有我方立场，不进入风险判断|
|脱敏 Hook|读取材料前|材料疑似含真实主体、签章、账号，先停|
|隐藏指令 Hook|文档解析前|合同里藏着「忽略上文」这类指令，先标红|
|路由 Hook|合同分类后|投资、租赁、NDA、对赌等场景，进入专项插件|
|来源 Hook|风险输出前|没有原条款或事实来源，不出重大风险|
|反向质疑 Hook|综合意见前|只生成支持性结论，没有反驳清单，打回|
|Submission Hook|文件交付前|没有范围披露、人工复核清单、审计记录，不交付|

这里面我最想展开的，是反向质疑 Hook。因为这件事和法院那篇文章是接上的。法院工作里最怕的一件事，是 AI 沿着一个初步判断一路搭桥。你觉得被告有责任，AI 就帮你找一堆被告有责任的理由。你觉得合同对乙方不利，AI 就帮你写一堆对乙方不利的理由。听起来很聪明。其实很危险。法律工作最需要的，往往不是让 AI 支持你。而是让 AI 质疑你。

[ 03 ]反向质疑，不是唱反调所以在合同 Skill 里，我会强制加一个 Reverse Challenge。不是输出完之后随口说一句「以上供参考」。而是在综合意见之前，专门让它反过来问。这不是为了唱反调。是为了防止确认偏误和单边论证。

```
Reverse Challenge 1. 如果我是对方律师，我会怎么反驳这份审查意见？2. 哪些风险其实只是谈判筹码，不应写成重大风险？3. 哪些结论依赖交易背景，单看合同文本无法成立？4. 哪些条款看起来不利，但在行业惯例里可能合理？5. 哪些修改建议会破坏交易效率，导致对方无法接受？6. 如果进入争议，哪些风险很难举证？7. 有没有遗漏附件、报价单、SOW、验收标准、数据处理协议？8. 哪些问题应该问客户，而不是让 AI 自己判断？
```

这才是法律 AI 真正该做的事。不是只把话写得更像律师。而是逼你在交付前多想一层。我举个很小的例子。技术服务合同里经常会有一句话，乙方应按甲方要求完成系统开发。普通 AI 会说，建议明确交付标准。稍微好一点的 AI 会说，缺少验收标准，对乙方不利。但更好的合同 Skill，应该继续反问。甲方要求有没有在附件 SOW 里？双方有没有报价单？项目是不是敏捷开发，本来就不可能一次性写死全部需求？乙方是按人天收费，还是按成果交付收费？验收失败有没有补救期？如果把交付标准写得过死，会不会反而让交易谈不下去？你看，风险不是一句「对乙方不利」就结束了。真正有价值的是把它拆成，文本风险，交易风险，证据风险，谈判风险。这就进入插件化了。我现在理解的合同 Skill，不是一个大模型一次性读完合同，然后吐出报告。

[ 04 ]入口 Skill 调度一组插件它应该是一个入口，调度一组插件。这里的 Router，不是为了显得技术味更浓。它就是法律工作里的分诊台，先判断这份合同该进入哪条专项审查路径。大概像这样。

|---|---|---|
|插件|处理什么|什么时候启动|
|Intake Router|立场、合同类型、审查阶段|用户说「帮我看合同」之后|
|Entity Check|主体真实性、签约权限、外部风险|读正文之前|
|Prompt Injection Scan|隐藏文本、恶意指令、异常对象|解析文档之前|
|Contract Type Router|投资、租赁、NDA、服务、采购、SaaS 等分类|读完正文之后|
|Clause Specialist|对赌、反稀释、清算优先、数据处理、反垄断等专项条款|命中特定条款时|
|Quant Overlay|违约金、估值、退出瀑布、Earn-out、Cap/Basket 等量化问题|风险涉及经济测算时|
|Reverse Challenge|对方视角、反驳清单、证据缺口|综合意见前|
|Comment Writer|Word 批注，只挂到具体词句|风险确认后|
|Summary Writer|客观合同概要|批注之后|
|Opinion Writer|综合审查意见|风险和反向质疑之后|
|Flowchart Builder|业务流程图|交易结构复杂时|
|Submission Gate|交付前审计、披露、留痕|输出文件之前|

这张表才是我想给读者看的东西。也不是所有合同都要移交专项插件。只有命中独立领域知识、独立算法，或者独立动作类型的时候，才应该移交。比如对赌、反稀释、清算优先，不是普通服务合同审查能随口带过去的东西。量化叠加也一样。违约金、估值、退出瀑布、Earn-out、Cap/Basket 这些计算，只能辅助谈判、风险分级和经济后果判断，不能替代法律效力判断，更不能替代律师判断。

这不是普通 prompt。也不是普通 Skill。它已经接近一个可交付的合同审查工作流框架。这也是为什么我不太想单卖一个「合同审查 Skill」。如果只卖一个 SKILL.md，别人打开一看，可能会觉得，就这？里面无非是审查步骤，输出格式，注意事项。但真正值钱的部分，往往不在那一个文件里。它在路由表里。在专项插件里。在反向质疑清单里。在 Submission Gate 里。在审计日志里。在你一次次用真实场景打磨出来的失败样例里。这也是我为什么觉得，法律 AI 练功房不能做成「提示词合集」。提示词合集卖 19.9 都有人觉得贵。因为它确实很容易被复制。

但如果你交付的是一套工作流训练场，价值就不是一段提示词了。

它变成了，读者跟着你一起理解，一个法律任务怎么拆，拆完之后怎么跑，跑到哪里必须停，哪里需要插件，哪里需要人判断，哪里不能交给 AI。所以这个项目不是在卖一个 Skill 文件。它是在做早期训练场。如果真的按这个方向做下去，里面交付的东西不可能只是几份 prompt。合同审查会有一套。案卷整理会有一套。法律研究会有一套。文书写作会有一套。每一套都不是单个 Skill。都是入口 Skill + 专项插件 + Hooks + Submission Gate + 练习样例。这也是我为什么一直说，它更像「练功房」，不是提示词货架。说到合同 Skill 的规模，我现在会把它分成三档。

第一档，玩具级。一个 SKILL.md。里面写触发条件、工作流、输出格式、边界声明。它适合学习 Skill 的基本写法。也适合做 demo。但不要拿它当正式合同审查工作流。

第二档，工作流级。一个入口 Skill，加 5 到 8 个 references，加 2 到 3 个脚本，加几份测试样例。它能做到立场确认，四层审查，批注、概要、意见、流程图，交付前人工复核。这已经能训练一个法律人怎么把 AI 放进合同审查流程里。

第三档，产品级。一个入口 Skill，加专项插件，加外部检索，加量化叠加，加反向质疑，加 Submission Gate，加审计日志，加 eval 样例。它不是为了让 AI 看起来更厉害。它是为了让每一次输出都可解释，可追溯，可复核，可回炉。我现在真正想做的是第三档。哪怕先做得很小。也要从第三档的方向设计。因为只有这样，才不会被普通 Skill 教程卷掉。普通教程教你写一个 Skill。我想拆的是，一个法律 Skill 怎么长成一套工作流。这里面还有一个很容易被忽略的点。插件化不是为了炫技。是为了控制责任。比如合同里出现对赌条款。

你不能让通用合同审查 Skill 随口说几句「建议注意履约承诺」就完事。它应该把这一段交给对赌条款插件。如果涉及估值、触发概率、回购价格、业绩补偿，还要叠加量化插件。如果出现反稀释、清算优先、退出瀑布，就应该进入 cap table 或投资条款插件。如果出现数据处理、跨境传输、DPA，就应该进入数据合规插件。

如果出现反垄断、外商投资、ODI、行业审批，就应该进入监管路径插件。这就是分工。也是边界。一个 Skill 什么都想管，最后就会什么都管不深。律师事务所为什么要分团队？投融资、劳动、知识产权、数据合规、争议解决，本来就不是一套脑子。AI 工作流也一样。你不能让一个通用 Skill 假装自己什么都懂。它应该知道，什么时候该把问题交出去。这就是插件化最重要的价值。

[ 05 ]提交前，才是真正的风险点再回到 Submission。我觉得这个词以后在法律 AI 工作流里会越来越重要。因为 AI 时代，真正的风险不在生成。生成太容易了。真正的风险在提交。你什么时候把一个东西从草稿区拿出来，发给客户，发给业务，发给合伙人，甚至发给法院？这一刻，才是责任发生变化的地方。所以我现在会把 Submission Gate 当成合同 Skill 的最后一道门。它不是免责声明。它是一张交付前检查表。这张表可以直接拿走。

```
Submission Checklist 材料是否脱敏？审查立场是否明确？合同类型是否识别？专项插件是否调用？重大风险是否绑定来源？反向质疑是否完成？人工复核事项是否单列？外部检索是否披露降级情况？输出是否区分批注、概要、意见、流程图？是否说明本次审查不构成个案法律意见？
```

这张表，读者今天就可以拿走。哪怕你不用我的 Skill，也可以把它放进自己的合同审查流程里。说真的，这才是这篇文章应该给出去的干货。不是一段更好的 prompt。而是一套更硬的提交前机制。最后再回到 SkillCreator。我现在不是反对它。恰恰相反，我会更愿意用它。因为当你把架构想清楚之后，生成器很适合帮你起草第一版。它可以帮你快速生成入口文件。可以帮你整理 references。可以帮你把某个专项插件的说明先写出来。可以帮你生成 eval 样例的雏形。但它不能替你决定，这个合同 Skill 的规模应该是什么。它不能替你决定，哪些问题应该进入专项插件。它不能替你决定，Submission 前必须拦什么。它也不能替你决定，哪些结论必须被反向质疑。这些东西，才是法律人的工作。也是法律 AI 练功房真正要练的东西。

下一篇我可能会继续拆一个更具体的问题。

比如，一篇法律 AI 文章里，哪些段落必须人写，哪些段落可以交给 AI 写。因为写作也是一样。AI 可以帮你生成。但能不能提交，还是另一回事。
