## 二、scripts/update_frontmatter.py：一颗未拔的雷

### 2.1 结构性缺陷（四个，任一即可致灾）

1. **无 scope 限制**：`os.walk(LAWKB_ROOT)` 扫全库，**天然包含** `法律法规库/`
2. **直接覆写**：第 192-193 行 `open(file_path, "w")` + `f.write(new_content)`
3. **销毁注释**：第 99-100 行 `yaml.dump(new_fm)` **重建整个 frontmatter → 原 fm 内所有 `#` 注释被永久丢弃**
4. **无备份 / 无 dry-run / 无防覆盖复检**：与六-B 铁律完全相悖

### 2.2 实测污染面

- 法律法规库残留脚本专属字段：**40 张**
- 字段命中频次：`source` 40 / `maturity` 29 / `status` 27 / `importance` 26 / `difficulty` 25 / `related` 24 / `review_interval` 23 / `last_review` 22
- 运行指纹报告自述：「✅ 已更新：**362 个文件**」，其中原材料仓 **33 条**
- 报告文件自相矛盾：fm `updated: 2026-09-23T15:53` 而正文仍写「更新时间 2026-06-27 19:21:55」——恰是脚本扫到报告自身、**只换 fm 块不换正文**的指纹

## 六、方法论沉淀（供后续复用）

1. **「否定性排除」也要给判据**：不能只说"不是脚本写的"，必须给出可复核的反证（updated 未刷新即最经济的一条）
2. **脚本污染用「专属字段」识别**：`update_frontmatter.py` 会补 `maturity/difficulty/importance/status/review_interval/last_review/related`，这些字段不出现在原生 schema，是天然指纹
3. **`yaml.dump` 重建有固定长相**：空值写成 `key:`、列表用 `  - xxx`、新增键追加在原顺序尾部——看一眼格式即可定性
4. **报告文件是最好的运行指纹**：批量脚本通常留报告/日志，其 mtime 可直接判定「最后一次运行时间」
5. **git 可用性必须实地验，不能凭印象**：本次推翻了「原材料仓盘上 vs HEAD 差异 0」的既有印象（实际 25 个未提交差异，且污染已进 HEAD）
