## 一、总则

### 一 · 立法目的

1. 为法条银行（`~/Documents/LawKB/法条银行/`）建立**系统性内部控制**，使「增 / 查 / 改 / 核填 / 归档」五类动作**有章可循、有据可查、有权可溯**。
2. 保障起草方在引用法条时，随时能拿&#x5230;**「现行有效 · 版本双证一致 · 可回溯」**&#x7684;本地法条，防止版本漂移与疑本外流。
3. 把本轮已验证的行之有效的治理实践（G1/G2/G3 三档、R-3 授权粒度、备份回滚、零残留核验、六维成熟度）**固化成长效机制**，不因人因时失效。

### 二 · 适用范围

本制度适用于法条银行子系统的**全部治理动作与消费行为**，包括：

| 适用对象 | 具体范围                                          |
| ---- | --------------------------------------------- |
| 治理方  | 法条银行行长（守库执行 A 岗）、数字资产中台运维协同                   |
| 消费方  | 业务中台各起草智能体（引用本地法条）                            |
| 监督方  | LTI 文本监控器（交付前置门禁）、老强（抽检与拍板）                   |
| 库内范围 | 100 张在库卡片、`_archive/`、`法律资讯周报/`、`银行治理层/`、覆盖台账 |
| 动作范围 | 建卡、核填回填、改库（元数据/版本）、归档、批量处置、台账维护、审计            |

> 排除项：`银行治理层/` 下的 persona / 心智备忘录 / Schema 规范等**治理文档**非 statute 卡，不纳入卡层面合规率分母；台账、报告、方案按各自规范管。

### 三 · 五项基本原则（做事底线，五条不得突破）

| 原则           | 含义                                                                                                        | 违规后果         |
| ------------ | --------------------------------------------------------------------------------------------------------- | ------------ |
| **① 权威源唯一**  | 本地法条银行是法条引证的唯一权威源；命中不到走 pkulaw / 元典 / qcc 核填，**永不凭记忆灌条文正文**（引总册 §六）                                       | 条文失真，回滚 + 复盘 |
| **② 双证不可妥协** | `source_verify` 须 pkulaw / qcc **远程指纹** ↔ **本地末条施行日期**一致，才标 `现行有效`；否则 `待核验` + `statute_text_pending:true` | 疑本禁引，追责      |
| **③ 元数据一致**  | 全库收敛为 RULE-038 **两型**（A 型权威法规卡 / B 型资讯案例卡），sxx 严格用枚举值（括号注释即违规）                                            | 不合规，不计入合规率   |
| **④ 留痕可溯**   | 凡写入必备份、凡批量必 dry-run、凡处置必留痕（版本冲突只移 `_archive` **不删**）                                                      | 数据不可溯，记过     |
| **⑤ 零残留**    | 批量处置后须核验「无残留」（预期产物全部到位、无孤儿、无双份 frontmatter、无失联字段）                                                         | 视为未闭环，重跑     |
| **⑥ 主源唯一**  | **法条银行为法条唯一主源**，一切自动化法条更新以法条银行为唯一落点（**见 §七 铁律 FR-MAIN**）；`LawKB/法律法规库/` 冻结为**只读原材料仓**，禁止批量写入 | 违反即流程缺陷，回滚+复盘 |

## 三、建库与卡片管理（准入控制）

### 一 · 卡片两型（RULE-038）

| 型                  | 适用                     | 强制字段                                                                                          |
| ------------------ | ---------------------- | --------------------------------------------------------------------------------------------- |
| **A 型 · 权威法规卡**    | 法律法规 / 司法解释 / 规章等可引证法条 | `type: statute` + `sxx`（枚举精确值）+ `doc_no` + `source_verify`（以「双证一致」开头）+ `statute_text_pending` |
| **B 型 · 资讯 / 案例卡** | 资讯、案例、会议纪要             | `type: digest｜case` + `source` + `status`                                                     |

> 字段骨架以 `_Schema规范_v1.0.md` 为准；中文键（制定机关 / 发文字号 / 施行日期）、`type: 法律法规源文件`、近裸卡（仅 created/updated）**均属 drift，发现即治**（见 §四 FR-07/08）。

### 二 · 命名规范（强制）

`<法规全称>（<发文字号>）[·<版本指纹>][·<节选范围>].md`

- 禁止：无发文字号、无版本指纹、纯描述性命名。
- 示例：`中华人民共和国慈善法（主席令第XX号）·2023修正.md`、`……（主席令第XX号）·节选·事故责任与赔偿专题.md`
  > ⚠️ 示例中的「主席令第XX号」为**占位符**。**真实发文字号（发文字号 / 主席令号）一律以 pkulaw 或官方公布令号为准，严禁凭记忆套用**（FR-01、FR-17）。

### 三 · 建卡准入六项检查（建卡前逐项打勾）

1. 命名合规（含发文字号 / 版本指纹 / 节选范围）
2. frontmatter 符合两型且 sxx 为枚举精确值
3. 双证一致（pkulaw / qcc 远程指纹 ↔ 本地末条施行日期）
4. 节选卡已标 `scope: 节选·<专题>`，且不与全文卡混淆
5. 已登记入 `_本地法条银行_覆盖台账.md`
6. 域归属正确（11 域体系，含「地方性法规·贵州」）

### 四 · 归档与版本处置

- 发现旧版（如慈善法 2016 版）→ 现行版另存 `·<版本指纹>` 置顶；旧版移 `法条银行/_archive/` **不删**，frontmatter 标 `superseded_by`。
- 公众号转载（`mp.weixin.qq.com`）仅作内容备份，文件名标 `·内容备份·禁条号级引用`，`statute_text_pending: true`，**禁止条号级引用**。

## 四、风险控制（核心章节）

### 一 · 风险清单与控制措施（RCL）

> 编号 `FR-xx`（法条银行风险）。三级：高（即刻停做并报）/ 中（当轮处置）/ 低（排期整改）。

| 编号        | 风险点                                                  | 等级 | 控制措施（执行落点）                                                                                         | 责任岗       | 触发处置                   |
| --------- | ---------------------------------------------------- | -- | -------------------------------------------------------------------------------------------------- | --------- | ---------------------- |
| **FR-01** | **凭记忆灌条文正文**                                         | 高  | 条文须 pkulaw 主源 verbatim 回填（pkulaw ＞ 元典 ＞ 本地核准表，**绝不降级记忆**）；未核填标 `statute_text_pending:true`，不得引为文档源 | 行长        | 立即回滚，复盘记过（总册 §六）       |
| **FR-02** | **双证不一致 / 版本漂移**                                     | 高  | 远程指纹 ↔ 本地末条施行日期比对；不符即 `sxx:待核验` + `statute_text_pending:true`，并回写覆盖台账                              | 行长        | 暂停引用，标的卡禁用             |
| **FR-03** | **删 / 批量改写未报批（R-3）**                                 | 高  | 删 / 批量改写一律交老强拍板；执行前置：`cp -n` 备份至 `/tmp/时间戳` + dry-run + 安全扫描 + 确认非误报                               | 行长        | 立即中止，回滚（总册 §一 / §五）    |

### 二 · 风险控制三条硬闸门

内控 effectiveness 取决于三条闸门是否同时关得住：

```
【闸门一 · 写入闸门】一切写入 / 批量动作
   先排查确认非误报 → 安全扫描 → dry-run → 破坏性预检五条
   （引用预检 / cp 备份 / dry-run / 安全扫描 / 确认非误报）
   → 零残留核验 → 回写台账 → 复盘
   ⛔禁止：跳过 dry-run、凭记忆静默覆盖、未备份直接写

【闸门二 · 引用闸门】一切法条引用
   本地源引证（命中本地 → 引本地；命中不到 → 标 statute_text_pending）
   + 疑本禁引（statute_text_pending:true 一律不得引用）
   + 禁凭记忆（pkulaw 主源，绝不降级记忆）
   + 节选 / 全文口径一致

【闸门三 · 版本闸门】一切版本与存档
   双证不一致 → 标待核验，禁当现行有效用
   旧版发现 → 现行版另存顶置，旧版移 _archive 不删 + superseded_by
   公众号源 → 禁条号级引用
```

### 三 · 备份与回滚（FR-04 / FR-15 控制细则）

| 层级      | 触发              | 落点                                     | 核验方式              |
| ------- | --------------- | -------------------------------------- | ----------------- |
| ① 整库预备份 | 批量处置前           | `/tmp/<业务>_pre_<时间戳>/`                 | `du -sh` + 目录清单比对 |
| ② 逐张备份  | 单源文件重建          | `/tmp/schema_remed_bak_<时间戳>/`（逐文件 cp） | 文件数 = 处置数         |
| ③ 版本备份  | 关键节点（制度发布、规范改版） | 外部通道 + `/tmp`                          | 可还原性抽验            |

**回滚触发**：FR-01/02/03/04/05/10 任一命中 → 立即停止后续动作 → 从备份还原 → 双重校验（字节 + 内容）→ 记入整改台账。

## 五、审计事项（核心章节）

### 二 · 审计指标与合格线（以实库扫描为唯一取数来源）

### 三 · 审计方法与工具（防假审计）

| 方法 | 要点 | 防的是什么 |
|---|---|---|
| **鲁棒扫描** | 取含 `type:` 的块解析，**禁用首块扫描器**（首块扫描读不到「桩+未闭合」卡真实 schema） | 防漏报隐形 A 型卡 |
| **台账对账** | 实库 frontmatter（权威） ↔ 覆盖台账逐行比对 | 防台账滞后、防虚报合规 |
| **幂等复跑** | 回填 / 修复后重跑，比较差异，0 变更即达成幂等 | 防重复写、防隐性漂移 |
| **零残留核验** | 预期产物数 / 目录清单 / 关键字段比对 | 防处置未闭环 |
| **双副本 grep 核验** | 两副本关键字段（maturity_score / status）逐字比对 | 防中枢漂移 |
| **脚本取数，禁凭记忆** | 指标一律由脚本实测，不引用记忆值 | 防假数据 |

> **审计纪律三条**：① 取数必须来自实库脚本，不得凭记忆填；② 基线变了必须重新实测，不得沿用旧值；③ 审计报告须写明实测口径与时间。
>
> **⚠️ D5 合规率有「宽 / 严」两口径，混用即失真**（2026-09-25 补注）：
> - **宽口径**＝两型合规卡 ÷ 实库总卡（**含 `待核验` 疑本**）→ 实测 **97/102 = 95.1%**；
> - **严口径**＝同上去掉 4 张 `待核验` 疑本（疑本不计合规）→ 实测 **93/102 = 91.2%**（＝ `governor_maturity.py` 判定值）。
> - 两者均 ≥ 90% 合格线，**引用时必须标注口径**；对外出件与起草方推荐位判定一律**取严口径**。

### 四 · 审计流程（五步闭环）

```
① 立项与范围   → 定审计类型 / 范围 / 指标 / 取数方式
② 实盘取数     → 脚本全量扫描 + 台账对账（不凭记忆）
③ 比对定级     → 逐项对合格线，缺陷定 P0 / P1 / P2
④ 报告与授权   → 出审计报告；涉 R-3（批量改写单源）须老强拍板
⑤ 整改与复核   → 备份 → dry-run → 执行 → 零残留核验 → 回写台账 → 复盘
```

### 五 · 缺陷分级与整改时限

| 等级 | 判定 | 整改时限 | 处置 |
|---|---|---|---|
| **P0** | 权威源失真、疑本外流、数据丢失风险、未批批量改写 | **≤ 24 小时** | 立即停机处置 + 报老强 + 复盘 |
| **P1** | schema 漂移、台账滞后、版本标记错误 | **≤ 本轮（7 天）** | 进整改台账，闭环后重扫核验 |
| **P2** | 命名不规范、标注缺失、可延后优化 | ≤ 30 天 | 排期整改，不影响引用合规 |

### 六 · 审计输出（三件套）

1. **审计报告**：按《G3 库级审计对账报告》体例——基线表 + 对账表 + 缺陷表 + 闭环记录 + 成熟度刷新页。
2. **整改台账**：缺陷编号 / 定级 / 责任人 / 时限 / 处置 / 复核人 / 复核日期 / 零残留结论。
3. **成熟度记录**：`governor_maturity.py` 实测刷新结果（六维 D1–D6、M1–M5、双副本零漂移核验）。

## 七、附则

### 铁律 FR-MAIN · 法条唯一主源（老强 2026-09-27 拍板 · **优先级高于本章其它条款**）

> **背景（事故由来）**：`LawKB/` 下同时存在「法条银行」与「法律法规库」两套法条副本。实测 66 个共有文件中 **63 个已分叉**（仅 3 个字节相同），且原材料仓侧大量卡片**正文自称「现行有效」却在 frontmatter 无 `sxx` 佐证**（2026-09-27 实测 23 张），无从判定版本，一旦被自动化引用即为**静默误标**风险。P0 实例：`法律法规库/通用法律法规/中华人民共和国网络安全法（主席令第53号）·关键条文回填版.md`——正文载「时效性：现行有效」，实为 2016 版（2017-06-01 施行），已于 2026-01-01 被主席令第61号修正版取代。

**FR-MAIN 六条（逐条强制，违反即流程缺陷）**：

| # | 铁律 | 具体要求 |
|---|---|---|
| **1** | **法条银行 = 法条唯一主源** | **所有自动化、流程、智能体的法条「新建 / 更新 / 版本替换 / 时效性修正」，一律以 `LawKB/法条银行/` 为**唯一写入落点**。任何其它目录不得作为法条主源承接自动化的法条写入。 |
| **2** | **法律法规库冻结为原材料仓** | 冻结 = ①**禁止任何自动化批量写入或改写**（含改 frontmatter、批量打标、就地定级）；②**只读**，仅用于历史沿革查证与人工溯源；③ 确需处置既有问题时，**只补标记、不改内容**，且须单文件留痕（FR-02 不静默覆盖 / FR-10 只标不删）。 |
| **3** | **禁止原地定级** | 原材料仓的卡片**一律不得标注为 `现行有效`**。正文已有的「现行有效」主张视为**待核验陈述**，frontmatter `sxx` 一律记 `待核验`。升级为 `现行有效` 只能经下述第 4 条回流路径。 |
| **4** | **回流路径唯一** | 原材料仓 → 法条银行，唯一通道＝**G1 核填**：① `qcc-legal` / `pkulaw` / 元典 **主源实拉**（禁止 WebSearch 直采入库，引总册 §六）；② 过 **LTI 五维门禁**（REJECT=0）；③ 建成后回写法条银行，**不反向回写**原材料仓。 |
| **5** | **禁止双源并行演化** | 两库同名法条须「一处演化、一处归档」。原材料仓的既有副本**不再同步更新**，只在法条银行侧持续维护；两库差异属**预期状态**，审计时记「原材料仓分叉」而非缺陷。 |
| **6** | **写入前须确认落点** | 任何写入型动作在动手前，须在报告中声明「本动作写入落点＝法条银行 / 原材料仓（只读）」；误写原材料仓的，立即回滚并在当轮报告中披露。 |

> **本铁律的自动化落点**：`每日知识摄入`（v1.28 起增设 FR-MAIN 纪律段）、`LawKB 法条与法理一致性月度巡检`、`存量卡质量巡检（法条待回源 + 死链）`、`LawKB周度维护任务` 等一切涉及法条写入的自动化，执行时**先确认落点是否法条银行**。
> **例外留痕**：2026-09-27 对原材料仓侧网络安全法 P0 卡的处置（补 `sxx: 已废止` + `superseded_by`，不删文件、不改正文）与 23 张批量 `sxx: 待核验` 补标，系按老强指令的**例外处置**，均在 `comments` 字段留痕，不构成反向先例。
