# WF-102 · 资产复盘双口径对撞铁律（官方脚本跑完对撞）

> **一句话**：**资产复盘报告不得由单一口径产出。** 本席（D1–D5）复盘与官方脚本（M1–M6）对撞通过后，报告方可交付。
> **来源**：2026-10-15/16 首轮全量复盘事故——官方 `asset_ops_maturity.py` 跑完（耗时 50 分钟）后，发现初版报告存在 3 处**口径错**（复用率 74.8%→39.5%、"下调30.4分"错误对比、"实体交付物未落地"表述过当），全部写得很自信、全部无数据伪造。
> **立规人**：老强 2026-10-16 拍板「固化为资产运维官复盘的标准动作」。

---

## 一、为什么必须双口径（血泪依据）

首轮复盘 3 个错误的共同特征：

| # | 初版错误 | 性质 | 为何单口径查不出 |
|---|---|---|---|
| 1 | 复用率 74.8%（分母取"实体 .md 文件"=0） | **口径错** | 本席自己的脚本自洽；只有官方脚本用 json rule_id 口径才暴露 |
| 2 | 官方 96.4 与本席 66「下调 30.4 分」 | **维度误比** | 两个分数各自成立，需知道对方测什么才能发现不可相减 |
| 3 | 「规则包实体交付物未落地」 | **表述过当** | 需读官方脚本 `pkg_rule_ids()` 实现才知 json 内数据完整 |

**核心教训**：
> **单口径复盘会产出高置信度的错误数字。**
> 三个错全是"口径错"、不是"数据错"——**没有一处编造，但交付出去就是错的**。
> 交叉对撞不是"复核一遍"，是**换一个测量体系重测同一对象**。

## 二、两套口径的测量范围对照（必读，防混用）

| | 本席 D1–D5 评分卡 | 官方脚本 M1–M6 |
|---|---|---|
| **测什么** | **资产经营纪律**：账记不记得住 | **商业化就绪度**：包做得好不好 |
| D1/M1 | D1 编目覆盖率（9 大类登记率，含空库检出） | M1 域库封装覆盖率（已封装域库/域库数） |
| D2 | 告警及时性（漂移能否识别、P0 有无漏报） | — **不测** |
| D3/M2/M5 | 规则包质量（结构+实体+计费+核验） | M2 计费口径一致 / M5 包内一致 |
| D4 | 交付闭环（真实采用反馈） | — **不测** |
| D5 | **回写与漂移控制（记载=实测）** | — **不测**（脚本只读包、不读登记册） |
| M3 | — **不测** | 跨域复用（⚠️ 已于 2026-10-16 由饱和打分改为复用率计分，见下） |
| M4 | 并入 D3 扣分项 | 法源核验（待核验源占比） |
| M6 | — 不测 | 规则库归库（撞号/backup残留） |

**关键盲区（务必记住）**：
- 官方脚本 **完全不读 `asset_registry.json`** → 其 P0/P1 数组为空，**不代表无漂移**，只代表它看不见账实差。
- 官方 M3 打分公式 **2026-10-16 已修正**（老强拍板）：
  - **旧口径（已废）**：`min(100, reused/50×100)`，**饱和打分**——复用 50 张即满分，814 张与 50 张同得 100 分，无区分度。这是 2026-10-15 首轮复盘的踩坑点之一。
  - **新口径（现行）**：`reuse_pct = reused / total_rules_indexed × 100`，**按复用率计分、无主观阈值**。当前实测 814/2059 = **39.5 分**。
  - **连带影响**：M3 得分 100 → 39.5，成熟度指数 96.4 → **87.3**（✅ 2026-10-16 脚本重跑实测确认，与独立复算值一致；仍判优秀，但分数变诚实）。
  - 若报告仍见 M3=100，须注明系**旧口径残留**。

## 三、标准动作（强制执行）

```
FUNCTION 资产复盘(资产域):
  ① 编目：确认目标域在登记册内（不在 → 本轮先补登）
  ② 本席复盘：跑 asset_monitor.py + registry_consistency_check.py → D1–D5 评分卡
  ③ 官方对撞：跑 asset_ops_maturity.py（⚠️ 慢盘约 50 分钟，须 run_in_background 后台等）
       若未跑完 → 报告必须标注「官方口径未对撞」并置为草稿态，不得交付
  ④ 差异裁决：逐项比对 D1–D5 与 M1–M6
       · 同向一致 → 记入报告
       · 冲突/单边 → 先查「测量范围差异」再判「谁错」
           - 差异来自范围（对方不测此项）→ 两分并列，禁相减
           - 差异来自口径（同一对象两种算法）→ 双口径各算一次，取口径正确者并留痕
  ⑤ 三维门禁全绿方可交付：
       · 双口径结论并存且已说明不可相减
       · 全部数字带口径键（来源/算法/排除项）
       · 差异项已写入「口径更正记录」章节
  ⑥ 回写：中枢 PROJ 卡 + 登记册 + 经验卡
  【终止】③④⑤ 全过 + 三处回写
```

### 硬约束

1. **官方脚本未跑完，报告不出**。可先出草稿，但必须标注「官方口径未对撞·待确认」。
2. **两个分数并列呈现，禁止相减**（`96.4 − 68 = 28.4` 这类表述一律不得出现）。
3. **官方 M3 已按复用率计分**（2026-10-16 起）；若见 M3=100 须注明系旧口径饱和打分残留。
4. **发现口径错必须回改已交付报告**，并在报告内立「修订记录」章节（不得静默覆盖）。
5. 官方脚本口径与本席口径**均可疑时，取第三方实体文件（`find`/`du`）仲裁**。

## 四、慢盘执行约束（50 分钟的跑法）

- `asset_ops_maturity.py` 在 LawKB 慢盘上实测 **50 分钟**（2026-10-15 23:51 → 2026-10-16 00:41）。
- **必须 `run_in_background` 后台执行**，不得前台阻塞；前台跑会被 SIGTERM 且拿不到输出。
- 跑前先做六-B 备份；跑后读 `/tmp/maturity_out.txt` + 落盘的 `asset_maturity_report.json/.md` 双向确认。
- 脚本输出重定向到文件时，前台 `cat` 可能读到 0 字节——**以 `wc -c` 确认非空再读**。
- 已知待修：脚本无 mtime 增量缓存（同 D7 红线方案），P1 排期中。
