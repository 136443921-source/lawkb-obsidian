# WF-047 · 治理席位（律所主任/管理合伙人）心智训练流水线

> **一句话**：给数字分身系统补一个「管家」角色——**不办案、不参审、不判胜负，只对系统整体效能负责**；并把它的训练做成可观测的成长曲线。

---

## 一、何时用

当系统出现「有人打仗、没人管家」的症状时：

| 症状 | 判据 |
|---|---|
| 自动化僵尸堆积 | PAUSED 占比 > 10%，且无人记录暂停原因 |
| 监控类半盲 | 看板/监控类自动化被暂停 → 出问题无人报警 |
| 调度撞车 | 同一时段并发 ≥ 5 个自动化 |
| 训练资源错配 | 各角色成熟度各刷各的，无横向对比与倾斜 |

**实证**：2026-09-15 全量体检，69 条自动化中 10 条 PAUSED（存活率 85.5%），其中 **6 条是监控看板**；周一 9:00 档 8 个并发。

---

## 二、六步流水线

| 步 | 动作 | 产物 |
|---|---|---|
| 1 | **席位勘定**——先与 QC 总闸切边界，否则必打架 | 边界表 + 红线 |
| 2 | **建治理六层栈 G0–G5**（平行对位于业务栈 L0–L5） | 心智栈表 + 四条信条 |
| 3 | **职责域建模**——每项职责写成「输入→步骤→产出→判据」算法 | D1–D7 心智算法 |
| 4 | **实证诊断**——全量实测，病灶带角色前缀 | M1–M9 病灶表 |
| 5 | **建备忘录 + 追踪脚本 + 周刷新** | 活文档三件套 |
| 6 | **跑首轮实战并回写** | 首条成长记录 |

---

## 三、与 QC 总闸的边界（最关键，第 1 步必做）

| | ⚖️ QC-Controller | 🏛️ 治理席位 |
|---|---|---|
| 范围 | 单场庭审内 | 跨场次 / 跨技能 / 跨自动化 |
| 尺度 | 实时分钟级 | 日 / 周 / 月 / 季 |
| 权力 | 战术否决权 | 战略处置权 |
| 对人 | 只盯产出物 | **盯人**（谁退步了） |

> **红线**：治理席位**不得推翻 QC 单场裁决**；QC **不得评价跨场趋势**。
> 唯一交集：**QC 出数据，治理席位出结论。**
> 类比：QC = 当值审判长，治理席位 = 律所主任 + 技术负责人。

---

## 四、归因三分法（本流水线最有价值的方法论）

```
发现问题 → 先归类，再开处方：
  能力问题 → 处方【加练】
  结构问题 → 处方【改造】
  数据问题 → 处方【补数据】
  ROI 末位 → 处方【下线】
```

> ⚠️ **开错药方 = 白训一轮**。实证：M8（埋点覆盖率低）初判为「能力问题：执行不认真」，
> 实际根因是**结构上没有强制埋点门禁**——派角色「认真点」没用，得加门禁。
> **归因时先问一句：这个现象背后，有没有强制机制在支撑？**

## 五、成熟度五维（治理角色定制）

| 维度 | 权重 | 算法 |
|---|---|---|
| P1 治理场次 | 20 | `min(n/8, 1) * 20` |
| P2 产出留痕率 | 25 | 带 output 字段记录数 / n * 25 |
| P3 身份留痕率 | 15 | 带 `mp` / `managing_partner` 字段记录数 / n * 15 |
| P4 职责域覆盖 | 20 | `min(覆盖域数/5, 1) * 20` |
| P5 病灶修复率 | 20 | `fix_done / fix_total * 20` |

**等级阶梯（治理版）**：M1 萌芽（结论靠印象）→ M2 成型（能盘点但处方不可操作）→ M3 熟练（结论挂实测数）→ M4 精熟（能识别静默失败）→ M5 教练级（训练飞轮自运转）

**采集源**：`知识飞轮系统/05-调用/治理席位调用记录/*.md` + `协同效果日志.md`
**脚本**：`~/.workbuddy/skills/_common/scripts/mp_maturity.py`（`--refresh` / `--report` / `--dry-run` / `--fix-done N`）

## 六、本次新踩的坑（重要）

### 坑 A：**成熟度五维与职责域编号撞车**（新，未见于既有踩坑表）

- **现象**：既有多角色（红/蓝/书记员）的成熟度五维固定叫 **D1–D5**；而治理席位的七项职责也习惯编号 **D1–D7**。两套 D 编号并存，文档中「D3」到底指「系统运维职责」还是「身份留痕维度」完全分不清。
- **根因**：跨角色复制模板时，**只改了内容没改编号命名空间**。模板里 D = Dimension（维度），新角色里 D = Domain（域），缩写撞车。
- **解法**：**治理席位成熟度五维改名为 P1–P5（Performance）**，职责域保留 D1–D7，病灶用 M1–M9（Managing，与蓝队 F / 红队 R / 书记员 CK 前缀互不冲突）。并在备忘录顶部加**「编号区分声明」**区块。
- **推广铁律**：**给新角色做心智模型时，先规划编号命名空间再写内容**——成熟度维度 / 职责域 / 病灶 / 能力项，四类编号必须前缀互斥。

### 坑 B：**冷启动单场记录把留痕类维度刷满，分数虚高**

- **现象**：首轮仅 1 场记录，P2 产出留痕 25/25、P3 身份留痕 15/15 双满分 → 总分 50 看似「M3 熟练」，但真实只跑了 1 场。
- **解法**（沿用踩坑 #14 拆口径思路，不改分母）：在脚本里加**动态口径提示**——当 `0 < n < 3` 时自动输出「留痕类满分属冷启动自证，真实能力分（P1+P4+P5）= X / 60」。
- **要点**：**让脚本自己说清楚分数的成色**，别指望读文档的人自己去拆。

### 坑 C：**新角色的第一批分来自「结构」而非「能力」**

- 治理席位开局就能拿满 P2/P3（只要记录写规范），但这是**留痕治理分**，不是治理能力分。
- 与书记员冷启动（踩坑 #15）同理：**先拿结构分、再拿能力分**，全程标注哪些分是留痕、哪些是真实能力。

## 七、执行前铁律

1. **先备份再动手** —— 改任何技能/自动化前 `cp` 到 `/tmp` 时间戳目录
2. **批量前先 dry-run** —— 脚本先 `--dry-run` 预览
3. **改完确认幂等** —— 重复跑一次结果应一致
4. **中文 md 校验一律用 ripgrep** —— macOS BSD grep 对中文 md 会假阴性（踩坑 #7）
5. **只改两个标记区块** —— 区块外手工内容零改动
6. **卷宗喂料前先脱敏** —— 个案隐私不入卡库
