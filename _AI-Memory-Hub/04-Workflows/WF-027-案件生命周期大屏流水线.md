# WF-027 · 案件生命周期大屏流水线

> 案件全程驾驶舱的**状态可视化与对外沟通**运维手册。
> 与「案件全生命周期·编排器」（七阶段 SOP + G0–G7 门禁，管"怎么做案"）分工：
> **编排器管流程，本流水线管状态展示与对外简报。**

## 一、适用场景
- 多案并发，需一眼掌握各案进度 / KPI / 期限榜 / 风险态势（大屏）。
- 需给当事人或客户发**脱敏**进度简报 / 当事人进度页。
- 跨设备 / 跨 AI 同步案件状态（LawKB 主本 ↔ 桌面副本双写）。

## 二、五大铁律
1. **状态是数据不是散文**——`case-state.json` 是唯一事实源；md 案件笔记由它派生展示，绝不可反向从散文解析状态。
2. **内外双管线隔离**——内部大屏读全量 payload；对外简报**只**读 `publicView` 白名单五字段；两条管线不共用渲染函数。
3. **脱敏闸门必须实测**——每次生成对外 / 公网产物，必须跑红线词扫描，PASS 才准外发。**零泄漏才算过。**
4. **先备份再动手**——改门户、覆盖大屏前一律先备份带时间戳副本。
5. **法条不凭记忆**——期限 `basis` 中条文序号若未核验，标注"交付前须经 LTI 核验"，不得进正式文书。

## 三、单一事实源
```
/Users/chenyouqiang/Documents/LawKB/案件生命周期管理系统/<案件夹>/case-state.json
```

### case-state.json Schema 关键字段（v1）
- **基础**：`schema` / `caseId`（内部编号，脱敏替换为 CASE-0x）/ `caseNo` / `title` / `court` / `judge` / `procedure` / `partyRole` / `counselRole`（代书须写明，避免身份误述）/ `client[]` / `status`
- **stage**：`current` 阶段号 + `code` + `name` + `enteredAt` + `note`
  - 七阶段：①接案建档 ②检索研究 ③文书起草 ④庭审查庭 ⑤客户协作 ⑥程序执行 ⑦风控归档
- **gates**：`G0`–`G7` 状态门禁（pass / active / warn / fail / todo / waived）
- **deadlines**：`id` / `name` / `due`（触发型 / 持续类填 null）/ `type` / `level`(P0\|P1\|P2) / `state` / `basis` / `note`
- **timeline** / **nextActions** / **risks**
- **stance**：`blue` 态势分 + `trend` + `reason`（拨动原因一句话）
- **publicView**：对外白名单**仅此五字段**——`stageText` / `done[]` / `next` / `clientTodo[]` / `contact`
- **updatedAt** / **source**（事实一律取自桌面真卷 + 案件笔记实地核实，不凭记忆）

## 四、常用命令
```bash
PY=/Users/chenyouqiang/.workbuddy/binaries/python/versions/3.13.12/bin/python3
cd <工作区>/case-lifecycle

$PY scripts/scan_cases.py --dry-run          # 只看扫描结果，不写文件

$PY scripts/scan_cases.py --only=6658        # 单案模式（逗号可多案）
$PY scripts/scan_cases.py --only=6658 --redact   # 单案脱敏版（供公网）

$PY scripts/sync_case_state.py              # 扫描前必跑：LawKB↔桌面 双写同步 + 冲突报警
$PY scripts/send_client_brief.py --case 6658            # 生成待发送文本
$PY scripts/send_client_brief.py --case 6658 --check    # 检查企业微信通道
```

## 五、接入新案件（四步）
1. 在 LawKB 案件夹建 `case-state.json`，照 schema 填写（事实从桌面真卷实地核实）。
2. `--dry-run` 验证 JSON 可解析、阶段与门禁填写完整。
3. 正式扫描，检查大屏 KPI 与期限榜是否正确。
4. **若案件涉及新自然人，必须同步登记 `scan_cases.py` 的 `REDACT_NAMES` 表**，否则脱敏版会泄漏姓名。

## 六、脱敏闸门（每次外发前必跑）
- **红线字段**：当事人 / 法官 / 律师姓名、案号序号、身份证号、统一社会信用代码、本地绝对路径。任一命中即 FAIL，禁止外发。
- **替换顺序坑**：`_redact_str` 必须**先**跑案号正则 `(民初|民终|民再|刑初)\d+号 → \1****号`，**再**跑 caseId 替换。顺序反了会把 `(2026)黔0330民初6658号` 改成 `民初CASE-01号`，案号序号反而暴露格式。

## 七、双写同步（P1-1 · 打通执行动线）
- `scripts/sync_case_state.py` 双向同步，LawKB 与桌面各一份，以 hash 基线判定谁改了：
  - 桌面缺失 → 从 LawKB 拉副本（首跑建双写）
  - 仅 LawKB 改 → 推送桌面；仅桌面改 → 拉回 LawKB
  - **两边都改 → 字段级冲突报警，不自动覆盖，等人工裁决**（退出码 1）
- 新增案件须在 `MAP` 注册桌面夹映射，否则 sync 跳过。
- 基线文件 `.sync_baseline.json` 记录上次同步 hash，**勿手删**（删了触发整批重同步，但不丢数据）。

## 八、产出
| 命令 | 大屏 | 桌面副本 | 对外简报 | 当事人进度页 |
|---|---|---|---|---|
| 默认 | 全量 | ✓ | ✓ | ✓ |
| `--only` | 全量 | ✓ | 仅该案 | 仅该案 |
| `--redact` | 脱敏 | ✗ | ✗ | ✗（案号抹去后对当事人无意义） |

- **当事人进度页**（可公网）：移动端优先、深色自适应，数据只取 `publicView` 五字段；发布前必跑泄漏扫描。
- **企业微信外发**：`msg` 域常因企业成员 >10 人受限 → 用**群机器人 webhook** 绕过（无需管理员权限），内容仍是 `publicView` 白名单；通道未通时降级 `--case 6658` 生成 `out/待发送-6658.txt` 手动转发。

- 门户为公网站点，全量大屏含真实案号与当事人姓名，**发布前必须 `--redact` 脱敏版，或经用户明确确认**。
