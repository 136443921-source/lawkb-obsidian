# 连接器故障四亚型分层诊断与处置流水线

> 适用：WorkBuddy 连接器（pkulaw / 元典 / ima / qq-mail / 公益 / 微云 等托管 HTTP MCP）"连着却调不通 / 调不通但显示连着"的故障排查。
> 详细权威版见技能 `workbuddy-connector-enabled-gate` v4.1.1；本卡为跨会话召回用的浓缩版。

## 适用场景
- 连接器在 `connector-status` 显示 connected，但工具调用报 401 / Bearer missing / 未连接 / 90001 / 402 / 403。
- 用户说"已重新连接"却仍用不了（工具列表里根本没有 `mcp__xxx__*`）。
- 批量连接器同时掉线（疑似平台级迁移事故）。

## 一句话口诀（先分层再归类）
> **先看错误体带不带 `requestId`/`timestamp`** —— 带 = **亚型D 业务层**（服务端配额/权限/点数，翻 enabled 与重新授权都无效，去充值或核对账号）；不带、报 401/未连接才归连接层 A/B/C。
> 再查 `id ∈ connectors` 吗？**不在 = 亚型C**（条目缺失，翻 enabled 无效，须 UI 完整"连接/信任/启用"注册）；在则看 enabled：**false = 亚型A**（翻 true 即可）；**true 却缺 token = 亚型B**（假连接，走 UI 重新授权补令牌）。

## 诊断步骤（只读，不写盘、不碰令牌）
1. **定位活跃 config**：`find ~/.workbuddy/connectors -name connector-states.json` → 取 mtime 最新的 UUID 目录那份（version 4，AES-256-GCM 加密令牌）。
2. **判定四亚型**（python 只读，禁打印令牌密文）：
   - `id ∈ connectors`? 否 → 亚型C。
   - `enabled`? false → 亚型A；true → 查 `id ∈ headerOverrides`：在=健康，不在=**亚型B 假连接**。
3. **判业务层（亚型D）**：错误体含 `requestId`/`timestamp` → 服务端已处理，是配额/权限/点数问题，连接层操作无效。
4. **查迁移根因**：config 若 `mcpSecurityMigrated/headerOverridesBearerStripped/staleManagedAuthHeadersPurged` 全 True → 安全迁移**批量清令牌**（多个 `enabled=true` 受管 MCP 同时缺令牌），按批量处置，勿当单点。
5. **查 proxy 健康**：读 `~/.workbuddy/mcp-aluris-proxy/bridge.log`（pkulaw 走 `https://aluris.top/mcp`），若全 `Proxy established successfully` → proxy 正常，POST 瞬时错误是会话噪音，重启可清。
6. **查工具索引热加载**：本会话 `ToolSearch`/deferred 索引查不到该连接器个体工具 → "工具索引不热加载"会话假象，须**重启 + 开新对话**核验，别在旧会话判成败。

## 亚型D 实战：pkulaw 90001（2026-09-21 实测）
- 返回体：`{"code":"90001","message":"Unclassified Authentication Failure","description":"Error while checking remaining points for user: a4204ed9-..."}`。
- 根因：`description` 明写校验用户剩余点数失败 = **北法宝账号侧点数/套餐/绑定**问题，非连接层、非 token 过期。"Unclassified" 是法宝网关未分类兜底码，勿见 90001 就判"重新授权"。
- 分层处置：**①** 去北大法宝后台核 WorkBuddy 绑定账号 `a4204ed9-...` 点数是否耗尽/到期；**②** 若已充值仍 90001 → 高度警惕**账号绑定错配**（充值的北法宝账号 ≠ 绑定的 `a4204ed9-...`），重连时必须登录"已充值的那个"账号；**③** 主源挂期间法条核验改走副源（元典 `rh_ft_search` 等可用接口），不能用的标 `statute_text_pending`，**严禁降级到模型记忆**。

## 处置（责任归属）
| 步骤 | 动作 | 责任方 |
|---|---|---|
| ① | 重启 WorkBuddy 重建 proxy session | 用户（系统操作） |
| ② | 开新对话再测（绕工具索引不热加载） | 用户 |
| ③ | 亚型B：`enabled=true 缺令牌` → UI「解绑后重新连接」（=老版本"重新授权"，按钮名因版本而异）补令牌 | 用户（UI，AI 不代点） |
| ④ | 亚型A：`enabled=false` → UI 拨启用开关 / 翻 true | 用户（UI） |
| ⑤ | 亚型C：条目缺失 → UI 完整"连接/信任/启用"注册 | 用户（UI） |
| ⑥ | 亚型D：账号侧点数/绑定 → 去服务商后台或核对充值账号 | 用户（浏览器） |

> ⚠️ **关键纠偏**：「解绑后重新连接」只修亚型B（本地令牌），**不修亚型D（9001 等账号侧错误）**。90001 若仍在属预期，说明账号侧未解，勿误判重连无效。

## 红线（本环境）
- **不代点 UI**：重启 / 解绑重连 / 拨开关 均由用户亲手处置，AI 不代点、不静默翻写 enabled。
- **不打印令牌明文**：`headerOverrides` 为 AES-256-GCM 加密，且 `.credentials.v3.json` 的 `mcpOAuth[id].accessToken` 实测全是 3 字节占位值（非真实 token），AI 无法复现私有加密、不能凭空造 OAuth，亚型B 必须走 UI 重新授权。
- 个案卷宗（当事人隐私/证件号）不入中枢，只沉淀方法论。
