# 🔴 RULE-060 · 中枢唯一事实源（SSOT）与单向派发铁律

> **老强 2026-11-06 裁决原话**：「以后所有的标准要以中枢为准，小强律师数字分身系统的技能版本、规则要以中枢为唯一事实源，**中枢一变其它才能变**。这个应该成为系统的铁律。不然还是会发生漂移的问题。」

## 一句话铁律

**`LawKB/_AI-Memory-Hub/` 是小强律师数字分身系统一切「标准」的唯一事实源；下游只能派生、不能自定义。任何版本/维度/阈值/门禁规则的变更，必须中枢先落盘，下游才允许跟着改；禁止反向操作。**

---

## 一、适用范围（三类对象，全覆盖）

| 类别 | 具体内容 | 下游示例（均为派生产物） |
|---|---|---|
| ① 版本号 | skill release version、QC spec version、脚本自报版本、手册「当前版本」 | `SKILL.md` frontmatter、`main.py` docstring、运维手册顶部、用户使用手册 |
| ② 规则标准 | 维度定义、维度数量、阈值、规则码、REJECT/WARN 判定、门禁步骤 | `lti_dimensions_v9.json`、`lti_qc9.py`、`WF-002`、各 QC 报告模板 |
| ③ 引用声明 | 挂载声明、技能分工声明、索引主题列、经验卡/复盘里的「系统现行为 X」断言 | 席位 `SKILL.md` 挂载段、`_索引.md`、飞轮经验卡、交付报告 |

**不适用**（属制品自身事实，非「标准」）：案件事实、当事人信息、个案 `case-state.json`、原始证据材料、法律条文正文。

## 二、SSOT 登记值（本卡即登记处 · 改标准先改这里）

> ⚠️ **一个 SSOT，两个版本字段**——不是「两个事实源」。两个字段同属中枢，分属两个不同制品，**禁止互相覆盖、禁止合并成一个版本号**。

| 字段 | 登记值 | 制品 | 载体（下游执行副本） | 维度/模块体系 |
|---|---|---|---|---|
| `runtime_version` | **v4.11.1** | LTI 文本监控器（skill / 代码运行时） | `SKILL.md` frontmatter `version`、`references/main.py` docstring 首行 | 六模块 R/L/C/T/P + charity + personalization，形式层校验，入口 `wrap_output()` |
| `qc_spec_version` | **v4.9.3** | LTI 九维文本质检维度规范（工作流） | `04-Workflows/WF-002-法条LTI五维QC门禁.md`、`lti_dimensions_v9.json`、`lti_qc9.py` | 九维 R/L/C/T/P/S/V/W/E，含人工确认维 L206/S704/E1004 |

**判定依据（防再漂移）**：`lti_qc9.py:24` 明写「依赖：仅 Python 标准库」、`:42`「内嵌以保证脚本自包含可跑」——它**不 import `main.py`**；两侧规则码亦不同（skill 侧 R101-R116/C301-C308/PF-001/T504；spec 侧 L201-L206/S701-S704/R-fb001）。故二者是同一 SSOT 下的两条独立制品线，不是同一版本号的两个写法。

**交付门禁（唯一口径）**：A 层 `REJECT=0` **且** B 层 `REJECT=0`，双闸门；任一未过不得对外交付。禁止简称「五维 QC」——五维（R/L/C/T/P）只是 B 层基座，现行 B 层为九维。

## 三、🔴 单向派发顺序（缺一步即视为未完成）

```
① 中枢先改   → 改本卡登记值 / WF-002 / 中枢索引，写 updated + 版本演进记录
② 生成变更单 → 列出「旧值→新值」+ 全部下游受影响文件清单（引用预检：多路径+多命名变体）
③ 备份       → cp -n 到 /tmp/时间戳/，回显回滚命令；批量改同一文件用单进程 Python（RULE-045/046）
④ 派发下游   → 按变更单逐文件改；禁止静默覆盖权威数据；禁止凭记忆填值
⑤ 回读验证   → 读内容确认改动落地（禁以时间戳判定，RULE-007）＋跑漂移检测脚本＋残留扫描＋写日志
```

**顺序不可逆**：③④ 不得早于 ①；发现下游先改了，**一律判为漂移**，须回滚下游、从 ① 重走。

## 四、⛔ 反向禁止（六条）

1. **禁止下游先改后补中枢**——这是 2026-10-09 / 2026-11-06 两次漂移的共同根因。
2. **禁止凭记忆或旧文档填写**版本、维度、阈值（承 WF-002:102「维度/配置真源铁律」）。
3. **禁止把机器可读副本当独立真源**：`lti_dimensions_v9.json` 是中枢派生的**执行副本**，其 `version` 必须等于本卡 `qc_spec_version`；不得单方面改它再回头改文档。
4. **禁止在下游文档/挂载声明里写死版本号**：改为引用本卡 ID（写死＝埋下下次漂移种子）。
5. **禁止为「命名一致」重命名已有卡片文件**：`WF-002-法条LTI五维QC门禁` 全名被 **36 处双链 / 33 文件**引用（2026-11-06 Grep count 实测），改名即全断。文件名遗留由「文件名遗留声明 + `aliases` + 索引主题列」消解，不动文件名。
6. **禁止静默覆盖**：冲突须留痕，旧值标 `superseded`/`历史` 并保留可追溯链（承 `冲突仲裁规则.md`）。

## 六、下游写法规范（根治「写死即漂移」）

| 场景 | ✅ 允许 | ❌ 禁止 |
|---|---|---|
| 手册 / 文档 | 「版本口径以中枢 `RULE-060` / `WF-002` 登记为准」 | 「LTI v4.8.x 五维门禁」「当前版本 v4.10.3」 |
| 挂载声明 | 引用 `RULE-060` + 写清 A/B 双闸门 | 写死 `v4.9.3 九维` 作为唯一事实（升版即过期） |
| 制品自报元数据 | `SKILL.md` frontmatter `version`、脚本 `__version__` **允许存在**，但值须等于本卡登记值，且变更须由 ① 发起 | 自行 bump 版本后不回中枢 |
| 历史沿革 | 明确标「历史版本（vX，已废弃）」并保留原文 | 把历史陈述与「当前状态」混排不标注 |

**挂载声明标准模板（P1 及后续所有挂载必用）**：

```
LTI 口径引用规则（以中枢 RULE-060 为唯一事实源）：
1. 运行时版本：见 RULE-060 §二 runtime_version；六模块形式层，入口 wrap_output()。
2. 文书 QC 维度/版本/阈值：见 RULE-060 §二 qc_spec_version 及 WF-002；
   机器可读副本 lti_dimensions_v9.json 为派生执行副本，不得自定义。
3. 引用维度/版本/阈值前先读中枢，不得凭旧文档（v4.8.x 五维 / v4.0 三模块）填写；
   两字段分属不同制品，禁止互相覆盖或合并成一个版本号。
4. 交付门禁 = A 层 REJECT=0 + B 层 REJECT=0 双闸门；任一未过不得对外交付。
5. 本声明不写死版本号；中枢一变，此处随派发流程刷新。
```

## 七、漂移检测（机制，不靠人记得）

- 脚本：`_AI-Memory-Hub/99-脚本/check_ssot_version_drift.py`
- 读本卡 §二登记值 → 核验 `lti_dimensions_v9.json.version`、WF-002 frontmatter、`lti_qc9.py` 自报版本、`SKILL.md` frontmatter、`main.py` 自报版本 → 扫描下游**写死的旧口径**（`v4.8.x`/`五维 QC`/`v4.10.3`/`三模块` 等）→ 输出漂移清单
- 触发时机：① 每次派发完成后（步骤⑤必跑）；② 挂载声明新增/变更时；③ 交付前口径复核
- 退出码：`0` 全清 ｜ `1` 有漂移（须按派发顺序修复，不得就地硬改）
