# ⚖️ 诉讼信息中枢挂载铁律

> **定位一句话**：「诉讼信息中枢系统」是诉讼**程序信息**（送达/开庭/期限/法院联系人）的
> **唯一采集入口 + 计算器 + 提醒器**；它**不是**期限真值源，也**不是**法律判断者。
>
> **挂载对象**：🔵 蓝队诉讼律师（PROJ-001，定策席）+ 🔵-A 蓝队律师助理（PROJ-003，供料席）。
> 本卡为二者共用的接线规则，**不新设第五席**，不改 `RULE-BLUE-DISAMBIG` 四席架构。

---

## 一、为什么必须挂载（不挂载会出什么事）

程序信息在本体系里原本是**三条互不相通的通道**：

| 通道 | 载体 | 缺口 |
|---|---|---|
| 人的眼睛 | 老强看短信/照片 → 口头或笔记转述 | 无结构化落点，易漏、易记错日期 |
| 案件实体 | `case-state.json` 的 `deadlines[]` / `timeline[]` | 只存结论，**不存送达原始凭证** |
| 提醒 | 日历 / 备忘录 | 与上二者无写回回路，改了不同步 |

后果实证（6658 案 P0）：`d3 一审判决上诉期` 长期 `due: null`，卡在「送达日期未核」。
**判决 2026-09-29 落款，送达日无从技术性坐实，生效日与上诉时效全悬空。**
这不是律师不勤，是**没有采集口**——凭肉眼与回忆无法坐实 `dt_cjsj` 级证据。

中枢正好补这个口：`zxfw` 送达记录的 `dt_cjsj` 字段是**目前唯一可技术坐实送达日的来源**。

## 二、五条硬约束（违反即返工）

### 1. 单一入口：程序信息一律先过中枢

凡属以下任一形态，**先走中枢再谈其他**，禁止凭肉眼从短信/照片里手抄日期入卷：

- 法院送达短信（含链接）、送达平台链接（zxfw / gdems / jysd / 湖北 / SFDW）
- 传票、出庭通知、应诉通知书、受理通知书、举证通知、缴费通知
- 判决书、裁定书（**含"冻结/查封/扣押"字样者强制走保全期限流程**）
- 纸质文书照片 / 扫描件

> 例外：老强明确说「这次我只要你看一眼、不归档」→ 可只做解析不做归档，但**仍须走中枢解析**，
> 不得改用肉眼+口述（否则送达日无凭证）。

### 2. 🔴 期限真值不让渡（本卡最重要一条）

作战室总纲第 0 条：`case-state.json` 是阶段/门禁/**期限**的唯一可信源。本卡不得架空它。

```
中枢算出日期  →  procedure-facts（候选值，带原始送达凭证）
      ↓ 经 🔵 蓝队诉讼律师 复核起算点与法律依据
写入 case-state.deadlines[]  →  truth（真值）
      ↓
日历/桌面MD/邮件提醒  =  真值的提醒副本（不得反证真值）
```

**三条推论**：

- **中枢的日历事件不是期限依据**。—— 提醒漏建、错建、时区偏移，都不影响期限本身；反之日历显示某日截止，也不能证明期限就是该日。
- **两处不一致时以 `case-state` 为准**，并**当场报告冲突**（写明：中枢算出 X、case-state 记 Y、依据分别是什么），**不得自行取舍**。
- **禁止双写**。—— 不许「中枢写一份、case-state 写一份、两边各算各的」。中枢只写自己的 `archive/` 与案卷文件，**不直接改 `case-state.json`**。

### 3. 确认权归律师，助理不代点

中枢自身设了两道「必须律师确认」的硬门禁：**归档确认**（同名同姓误归风险）、**提醒创建确认**。
叠加 `RULE-BLUE-DISAMBIG` 第 3 条（助理不定策、不决定提交哪些材料），得出：

| 动作 | 🔵-A 助理 | 🔵 诉讼律师 | 老强 |
|---|---|---|---|
| 触发中枢、转述解析结果 | ✅ 可做 | ✅ 可做 | ✅ |
| **点「确认归档」到既有案卷** | ⛔ **禁** | ✅ 应做 | ✅ 可推翻 |
| **点「确认创建提醒」** | ⛔ **禁** | ✅ 应做 | ✅ 可改时间 |
| 判断期限起算点/是否争期限 | ⛔ 禁 | ✅ 专属 | ✅ 拍板 |
| 写入 `case-state.deadlines[]` | ⛔ 禁 | ✅ 专属 | ✅ 授权 |

> 助理只能把「待确认清单」递上去，**手指不许落在确认键上**。这是本卡最容易被越界的一处。

### 4. 期限条文必核，规则库只给天数不给效力

`deadline-rules.json` 只提供**天数与提醒节奏**，**不提供条文效力**。
任何对外文书或期限主张所引条号，仍须走 LTI / pkulaw / 元典核验；未核标 `statute_text_pending`，**不得引为期限依据**。

> 实证：6658 `d3` 的 basis 原文即写着「条文序号交付前须经 LTI 核验」——这条纪律不因接入中枢而放松。

### 5. 混案识别：匹配到 ≠ 归档到

6658 与 6660 涉**同一实际买受人**，且当事人姓名高度重叠（刘九零、刘维同时为两案被告）。
中枢按**案号**匹配是可靠的，按**当事人姓名**匹配在本体系内**不可靠**。

- 命中依据若只有姓名 → **视为未匹配**，须人工按案号复核；
- 一案多份文书、一批多次送达 → 按送达批次建子目录，不得混批；
- 跨案相同的法院/法官/书记员**不构成同案证据**（同一法官承办多案是常态）。

### 三之二、规则库可达性修复（2026-10-29 第二、三轮 · 期限规则链路整体打通）

> 起因：老强授权修「preservation_* 前置 + fee_payment 一字之改」。
> 实际排查发现**真正的病根不是顺序**，而是更底层的一处：`tags` 从来没被传进去。

#### ① tags 恒为空 —— 真正的病根（已修）

`create_all_reminders` 调用提醒脚本时，第 5 个参数（tags）**写死为空字符串**，`doc_title` 根本没传：

```python
# 修前
deadline_script, 'setup', case_no, case_type, doc_type, '', sent_at, court
```

于是 `match_rule` 里 `all_text = ' '.join([]) + ' ' + ''` ≡ 一个空格，**任何带 tags 的规则都不可能命中**。
这解释了为什么保全、上诉、再审、管辖异议全都哑火——不是顺序问题，是**没喂数据**。

**修法（两处）**：
- `parse_pdfs` 从正文提取特征词写入 `doc_info['tags']`
  （词表：冻结／银行存款／查封／不动产／扣押／管辖权异议／再审／生效／民事／刑事／行政）
- `create_all_reminders` 改用 `--json` 模式传 `tags` + `doc_title`

**实测（7 种文书全通）**：

| 文书 | 类型 | 提取 tags | 命中规则 |
|---|---|---|---|
| 冻结裁定 | 裁定书 | 冻结·银行存款·民事 | `preservation_freeze` 365日 |
| 查封裁定 | 裁定书 | 查封·不动产·民事 | `preservation_seal` 1095日 |
| 一审判决 | 判决书 | 民事 | `appeal_civil_judgment` 15日 |
| 驳回起诉裁定 | 裁定书 | 民事 | `appeal_civil_ruling` 10日 |
| 上诉状 | 上诉状 | 民事 | `defense_deadline_appeal` 15日 |
| 举证通知书 | 举证通知书 | — | `evidence_deadline` 15日 |
| 受理案件通知书 | 受理案件通知书 | — | `fee_payment` 7日 |

#### ② 顺序抢匹配（已全部修复 · 4 条专用规则前置）

`rules` 数组最终顺序：**前 4 条为专用规则，先于宽泛的 `appeal_*`**
（1 preservation_freeze → 2 preservation_seal → 3 jurisdiction_appeal → 4 retrial_deadline → 5–8 appeal_* → …）。

**实测（13 样本全通过）**：

| 文书 | 命中 | 说明 |
|---|---|---|
| 冻结裁定 | `preservation_freeze` 365日 | 已前置 |
| 查封裁定 | `preservation_seal` 1095日 | 已前置 |
| 管辖权异议裁定（「对管辖权提出的异议」） | `jurisdiction_appeal` 10日 | 已前置；截止 2026-11-08（周日）→ 自动顺延 11-09 ✅ |
| 二审终审判决（「本判决为终审判决」） | `retrial_deadline` 180日 | 已前置 |
| 一审判决（含「本判决生效后十日内履行」） | `appeal_civil_judgment` 15日 | **未误判再审** ✅ |
| 普通裁定（驳回起诉） | `appeal_civil_ruling` 10日 | 未被专用规则误抢 ✅ |

> 本轮两处**必须配套**的修正，否则前置会引入更大误判：
>
> **① `retrial_deadline` 的 tags 收窄**：`['生效','再审']` → `['终审','再审']`。
> 因 `match_rule` 是**任一命中**，而「生效」在判决书中极常见（「本判决生效后十日内履行」），
> 前置后会把**一审判决书**误判成「申请再审 180 日」。收窄后语义反而更正确：
> **一审判决 → 15 日上诉；二审/终审判决 → 180 日再审**。
>
> **② 管辖权异议表述归一化**：裁定书原文多写「对管辖权提出的异议」，并非连续的「管辖权异议」四字，
> 词表直匹配会漏。已在 `parse_pdfs` 加组合条件（含「管辖权」且含「异议」→ 归一为 `管辖权异议`）。
> ⚠️ 此项是**端到端测试才暴露**的——手工传 tags 的测试会掩盖它。

#### ③ 类型取值不一致（部分修）

| 规则 | 原值 | 现状 |
|---|---|---|
| `fee_payment` | `受理通知书` | ✅ 已改 `受理案件通知书` |
| `defense_deadline` | `起诉状` | ❌ 仍不可达（代码不产出该类型） |
| `enforcement_deadline` | `生效法律文书` | ❌ 仍不可达（代码不产出该类型） |

#### ④ 保全到期日 off-by-one（已修）

原代码 `deadline_dt = received + 期限`，而 `references/保全期限计算.md` 明定
**到期日 = 裁定日期 + 期限 − 1日**（示例：2026-05-27 裁定 → 2027-05-26 到期）。
差 1 天会使最后一条兜底提醒落在到期日之后。

已改为**仅对 `preservation_*` 生效**的 −1，其他期限不动：
`2026-10-29` 裁定冻结 → 截止 `2027-10-28` ✅（答辩期 15 日仍为 `2026-11-13`，未受影响）。

#### ⑤ 邮件收件人仍是占位符（未修 · 待老强确认）

`config/user-preferences.json` **不存在**（目录里只有 `.example`），dry-run 显示邮件发往
`YOUR_QQ_EMAIL@qq.com`。三条提醒渠道中「QQ 邮件（微信送达）」当前**空转**。

> 不擅自代填邮箱：填错会把案件信息发到错误地址，属隐私事故。待老强确认后一键补。

### 归档落点（老强 2026-10-29 拍板 · 缺口 G0 闭环）

中枢原生要求 10 个固定子目录，与 6658 桌面案夹扁平编号结构冲突。**采用独立归档子目录**：

```
{案夹}/01_法院送达文书_中枢归档/{批次}_YYYYMMDD送达/
```

既有 `00_-12_` 编号文件、`庭审十件套_6658_定版/` **一律不动**。
写入 `config/case-root.json` 的 `archive_policy: subfolder_isolated`。

> **G1 是当下最痛的一条**：6658 正处二审，而这正是中枢唯一算不出的期限。

## 四、推翻信号

- 中枢再次升级补齐公告送达/二审审限/涉外答辩期（G1b/G1c/G3/G4）→ 本卡第三节相应行作废并重写。
- 若 `deadline-rules.json` 改用 tags 区分境内外当事人 → G1b 作废。
- 老强决定让中枢直接写 `case-state.json`（放弃"候选值→律师复核"两段式）→ 第 2 条失效，须重议。
