# 📜 共享记忆协议 v1.0

**生效日**：2026-09-14 ｜ **制定人**：老强 ｜ **守约方**：本机及将来所有接入的 AI 助手

---

## 第一条 唯一事实源

1.1 本中枢（Obsidian LawKB / `_AI-Memory-Hub/`）是**永久记忆的唯一最终事实源**。

1.2 下列位置**降级为辅助缓存**，不得作为跨平台权威依据：
- WorkBuddy：`~/.workbuddy/MEMORY.md`、`~/.workbuddy/projects/*/memory/`、会话上下文
- Claude Code：`~/.claude/` 下的会话与 `projects/` 记忆
- Codex：`~/.codex/sessions/`
- Gemini：`~/.gemini/tmp/`
- 任何聊天记录、临时 prompt、当场对话

1.3 **冲突即让位**：缓存与中枢不一致时，无条件以中枢 `status: active` 且 `updated` 最新者为准。若中枢缺该条目，才允许缓存临时顶替，并**必须**在本次会话写回中枢补录。

---

## 第二条 任务前必读（Read-Before-Act）

2.1 任何 AI 在开始实质性工作前，必须完成下列装载：

```
必读：
  00-全局规则/共享记忆协议-v1.0.md       ← 本协议
  00-全局规则/字段-Schema.md             ← 写入格式
  01-用户偏好/_索引.md                   ← 老强怎么说话、怎么交付
  02-当前项目/_活跃项目.md               ← 当前在办事项
按需：
  03-决策档案/_近期决策.md               ← 近 30 天决策（涉及该项目时）
  04-每日日志/<昨天>.md                  ← 最近发生

一键完成：99-脚本/read_hub.py --brief
```

2.2 例外：纯寒暄、一句话查词、明确被告知"不用查记忆"的任务可跳过。

2.3 **违反后果**：等于失忆状态开工，产出的交付物视为草稿，不得直接交付客户。

---

## 第三条 任务后必写（Write-After-Act）

3.1 实质性工作结束后，必须提炼下列五类新增事实并写回中枢：

| 类型 | 落盘目录 | 触发信号举例 |
|---|---|---|
| `rule` | `00-全局规则/` | "以后都要…" "这条铁律…" "禁止…" |
| `preference` | `01-用户偏好/` | "我喜欢…" "别用…" "改成四个，以后按这个来" |
| `project-fact` | `02-当前项目/` | 案号进展、案件阶段、项目状态变化 |
| `decision` | `03-决策档案/` | "就这么定了" "选A" "为什么不选B" |
| `workflow` | `03-决策档案/` | 某流程跑通了/踩坑了、脚本用法 |

3.2 写回流程必须是：**`--dry-run` 先看拟写入内容 → 确认无误 → 去掉 dry-run 执行**。

3.3 写回时**必须**同步更新对应目录的 `_索引.md`，否则下次读不到。

3.4 **个案卷宗禁止入库**：当事人姓名、身份证、银行卡、证据原件内容一律不入中枢；只允许提炼"方法论 / 工作流事实 / 通用规则"。

## 第四条 每日复盘（01:00 + 08:00 补跑）

4.1 每日 01:00 自动复盘前一天全部素材；若机器休眠未跑成，08:00 幂等补跑。

4.2 扫描素材源（四类，老强 2026-09-14 选定全开）：

| # | 素材源 | 路径 |
|---|---|---|
| 1 | WorkBuddy 会话与项目日志 | `~/.workbuddy/projects/` |
| 2 | LawKB 库内日期日志 | `LawKB/.workbuddy/memory/*.md` |
| 3 | 现有 automation 运行报告 | `~/.workbuddy/automations/`、`LawKB/logs/` |
| 4 | 桌面办案系统本地交付物 | `~/Desktop/小强律师办案系统/`（**仅提炼方法论**） |

> 注：素材源 2 已于 2026-09-14 降级为**只读归档**，复盘时可读取提炼，但不得回写。

4.3 复盘三步走：**去重 → 解冲突（走漏斗） → 淘汰过期**。

4.4 淘汰标准（任一即归档）：
- `status: deprecated` 且 `updated` > 90 天
- `status: superseded` 且被替代已 > 30 天
- 项目已 `closed` 的 `project-fact` 且 > 60 天未更新

4.5 产出：`04-每日日志/YYYY-MM-DD.md`（复盘记录）+ 在 `04-每日日志/_哨兵.md` 追加一行已复盘日期（幂等标记，防止次日重复执行）。

## 第五条 可移植性

5.1 中枢内容**必须是纯 Markdown + YAML frontmatter**，不得依赖某平台专有语法，保证 git 拉到任何设备都可读。

5.2 任何设备上的 AI，只要能读写本文件树，即为合规接入方，**无需改造中枢**。

## 第六条 中枢 git 提交统一走 backfill.py 安全通道

6.1 任何 AI 对本中枢（`_AI-Memory-Hub/`）执行 git 提交（add / commit / push origin main）时，**一律经 `99-脚本/hub-card-backfill/backfill.py` 的 `_run_git()` 安全重试通道**，禁止手敲 `git push`。

6.2 链路分工：`write_back.py` 仅负责本地落盘 + 索引更新（走 index_guard 门禁），**本身不含 git push**；git 提交由 backfill.py 统一承担。故「写回中枢」= `write_back.py` 落盘 + `backfill.py` 安全推送，二者配合、不重叠。backfill.py 提供两种模式：**补卡主入口即 `--card <卡路径>`**（自动插索引 + 删待沉淀 + git 推送一条龙，受 hub-card-backfill 技能驱动）；**非卡片的通用提交走 `--files <文件...>`**（仅 `git add` / `commit` / `push` 指定文件，统一经 `_run_git()` 安全通道，如改协议 / 规则文件 / 索引 meta）。凡对中枢的 git 提交，二选一，均禁手敲 `git push`。

6.3 安全理由：backfill.py 内置 `index.lock` 安全重试——捕获锁阻塞后，先用 `pgrep -fl git` 精确判定是否有真实 git 进程持有锁，有则 ABORT（不盲删），无持有者才清锁重试。比手敲 `git push` 稳，可规避并发会话 git 中断导致的 `index.lock` 僵死（2026-09-14 第 5/6 轮实测）。

6.4 详细约定见偏好卡 **PREF-006**（「中枢 git 提交统一走 backfill.py」）。
