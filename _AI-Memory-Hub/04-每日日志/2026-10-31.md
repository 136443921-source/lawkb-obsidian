## 一、MinerU 现状：引擎可用、接线坏了

**一句话**：CLI 通道 15 页判决书 39 秒、关键字段 16/16；`mineru-api` 通道**从未打通**——10-30 那次"实跑成功"用的是 CLI，故障被掩盖。

### 安装（✅）
MinerU 4.1.2 / Python 3.12.16 / `~/pdf-docai/venvs/mineru`；7 个控制台命令齐全；模型 2 套（torch 套件 853 MB + GGUF VLM 1.2 GB）；磁盘合计 **4.5 GB**；Docling **未装** ⇒ `pdf-dual` 的"双路解析"在本机实际是单路。

### 故障根因（两层，第二层才是要害）
1. **启动参数废弃**：`pdf-dual/scripts/mineru_serve.py:187` 传 `--allow-local-source`（standard 档另加 `--no-flash`），MinerU 4.1.2 两者皆无 → 服务启动即退 → 桥接层空等 300 s 超时。
2. **来源协议错位**：4.1.2 API 只接受 `source: upload | url`（`mineru/parser/api_server.py`: `Literal["upload","url"]` + `_validate_source_policy`），本机客户端先发 `local` 再降级 `inline`，两者均非法 → `unsupported_source`。**改参数名也救不回来。**
   - `--allow-http-source` 不能用：那是放开明文 URL，与"卷宗不出网"原则相悖。

### 已修（只动本地增量层，不动上游）
- `case-file-review/scripts/ocr_local.py`：新增 `--engine cli|api`，**默认 cli**；`--check` 报引擎与 kit 路径；metadata 加引擎标识。
- `LOCAL-OCR-ADAPTER.md`：补「2026-10-31 重要变更」整节（现象／两层根因／实测表／口径提醒）。
- 未改 `pdf-dual` 本体（上游包，重装即覆盖）。
- 备份：`/tmp/pdfdual-backup-20261031-232037/`。

## 二、方法论沉淀

- **"跑通过"要区分哪条通道**：同一能力存在 CLI / API 两条路时，一次成功不能证明另一条通；复盘的第一个动作应是**分通道各跑一次**。
- **改上游还是改增量层**：上游技能包的文件（`mineru_serve.py`）改了会被重装覆盖，修复应落在本地增量层（`ocr_local.py`、`LOCAL-OCR-ADAPTER.md`），并把上游缺陷写成文档事实。

### ② 批量解析（去重复加载模型）

多文件合并为一次 `mineru-kit parse` 调用；同名文件退回逐件；批量失败/产出 0 自动逐件；漏掉的单件补跑；`._batch` 用完即删；metadata 增 `batch`/`batch_seconds`，批量命中文件 `seconds=null`。

**A/B 实测（3 个单页 PDF）**：逐件 **72 s** → 批量 **25 s**，省 65%。边界：同名冲突正确退回逐件（50.3 s，2/2 OK）；单文件 25.4 s OK。
