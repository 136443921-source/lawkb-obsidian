# ⚖️ 一人公司中台分层 · 独立「法律服务中台」收口"咨询+文书"两条营收线

## 背景

- "法律咨询域内全入口"（`legal-consult-router` + 需求**拷问**前置门禁 grill-me-legal-preprocessor）已接入并实测通过，统一接待所有法律诉求、先做意图澄清再五问分诊派发。
- 问题：该入口（及由此跑出的咨询、文书两类业务）应归入一人公司哪个中台？

## 候选方案

- **A｜新建法律服务中台（收口"咨询+文书"两条营收线）** ← 拍板
  - 利：业务/资产/监督三层职责清晰，入口归属无歧义，未来扩容（如加执行/执行异议业务线）有容器。
  - 弊：多一个中台需维护边界，但仅组织划分、不增系统负担。
- **B｜不新建，挂进数字分身系统"业务层"**，与数字资产中台并列
  - 弊：与数字资产中台同壳易混，长期仍要拆。
- **C｜入口归前台（客户触点层）**
  - 弊：router/拷问门是内部编排层非 UI 触点，硬塞前台打乱分层。
- 数字资产中台（资产运维官管）＝"供"非"产"，错配；后台（合规/LTI/9655 监控）＝监督非生产，错配。

## 结论（选项 A）

一人公司中台层**独立成「法律服务中台」**，与数字资产中台并列同属中台层：

- **法律服务中台**＝ 收口"咨询 + 文书"两条营收线（业务生产/交付层）。
- **数字资产中台**＝ 专职供给（模板/规则包/知识卡 SSOT，资产运维官管）。

> 📝 **命名沿革**：本方案草拟阶段曾以"业务运营中台"作类目描述（见选项 A 原拟名），2026-09-24 定名"法律服务中台"并全中枢收敛，不再使用"业务运营中台"称谓，以避免与四中台之"运营中台"部门混淆。

## 分层模型

- 前台：客户触点/获客（企微 Claw 渠道、公众号）。
- 中台：法律服务中台（咨询线 + 文书线）｜ 数字资产中台（SSOT 供给）。
- 后台：合规/LTI/9655 监控（风控与质量门禁）。

## 入口在中台内的角色与两条业务线

- 入口定位＝**统一接待分诊台**：router 接所有诉求 → 拷问门澄清意图 → 五问分诊 → 派发。
- 咨询线：分诊到各专项技能（人损/医疗/合同/慈善合规…）→ 出法律意见、备忘录。
- 文书线：分诊到文书生产链（docx 交付流水线 / 红蓝复核 / 非诉文书复核）→ 代写交付。
- 上下游：文书线从数字资产中台**取**模板/规则包/知识卡，形成"中台消费、中台供给"闭环；入口在法律服务中台，资产在数字资产中台，不重叠。
