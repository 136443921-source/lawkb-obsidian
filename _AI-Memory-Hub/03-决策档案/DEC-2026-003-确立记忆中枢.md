# ⚖️ 决策：共享记忆中枢架构

## 考虑了哪些选项

- **A. 新建顶层 `_AI-Memory-Hub/`**（LawKB 库根）：可见、可渲染、可检索、可 git 同步
- **B. 就地升级现有 `LawKB/.workbuddy/memory/`**：零迁移风险，但隐藏目录在 Obsidian 里不可见、不可检索
- **C. 另起独立 vault**：干净，但脱离知识飞轮体系，且要多维护一条 git 通道

## 选了什么 & 为什么

选 **A**。因为必须为频次（Obsidian 不渲染隐藏目录）+ git 同步通道复用 + 与知识飞轮同库互通。

## 配套的四项选择（同日确认）

| 议题 | 选择 |
|---|---|
| AI 接入范围 | **WorkBuddy + 预铺 Claude/Codex/Gemini/Cursor 全局规则文件**（本机虽未安装，将来装上即生效） |
| 凌晨复盘执行方式 | **01:00 定时 + 08:00 幂等补跑**（解决 Mac 凌晨休眠） |
| 复盘素材源 | **四类全开**：WorkBuddy 会话项目日志 / LawKB 库内日期日志 / automation 运行报告 / 桌面办案系统（仅提炼方法论） |

## 否了什么 & 为什么

- 否定 B：`.workbuddy` 是隐藏目录，Obsidian 默认不渲染，等于"写进去看不见"，违背"可人工检视"的初衷。
- 否定 C：脱离 LawKB 会造成第二套知识体系，重蹈 historical 上 `xiaoqianglawkb` 与 `LawKB` 双库分裂的覆辙。

## 什么信号会推翻这条决策

> 当出现下列任一情形时，本决策作废，需重新评估：
> 1. LawKB 的 git 自动同步**连续 7 天失败**且未能修复 → 跨设备共享失效，需换通道；
> 2. `_AI-Memory-Hub/` 条目数超过 **500** 导致 read_hub 装载过慢 → 需拆分索引或改分级装载；
> 3. 老强明确要求改用其它记忆方案。
