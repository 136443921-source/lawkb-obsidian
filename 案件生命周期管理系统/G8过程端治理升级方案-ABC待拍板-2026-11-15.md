# G8 过程端治理升级方案（A/B/C 待拍板）

> **一句话结论**：四周补丁去重后是 6 项机制、指向同一个缺口——G8 只会"挡输出"不会"盯过程"。**推荐 C（分阶段）**：巡检侧本周先上止血字段（零门禁改动、可撤销），门禁本体升级作为第二阶段立项，等你一次性拍板。

---

## 一、问题与证据（可证伪）

1. **业务挂账未闭环**：R2（审计约定书主体信息）死线 09-20 逾期约 **56 天**、R6（航合事故表态稿）距事故 **75 天**仍无正文、R7（面瘫协议）仍 **v2 未签署**。三项经第46周二次核验（读笔记/case-state + find 反查补正版/表态稿/签署版），非误报。
2. **治理建议自身挂账**：第42/43/44/45 周开出的四张补丁卡，截至 11-15 实测 `gate-config.md` 第41行 G8 仍「非诉合规·触发式」、第73行强制步骤仍是 v2 五项「红蓝复核＋合规专项体检＋过 LTI＋调用留痕＋经验卡沉淀」——**四周建议零落地门禁本体**。这是"建议力≠采纳力"的递归失效。
3. **遵守边界**：本方案由巡检产出，只提方案不改配置。gate-config.md / case-state.json 本次零改动。

## 二、四周补丁溯源（原文回读，不凭记忆）

| 周次 | 来源卡（实体文件） | 原建议要点（摘自卡内"可复用处置原则/处置建议"） |
|---|---|---|
| 第42周 10-18 | 框架已锁定却永不落地的挂账陷阱 | ① **双轨触发器**：死线日 + 升级日（死线+7天自动升 P0 + 提示人工发函）；② **owner 唯一化**：单一责任人 + 验收标准；③ **闭环证据化**：以签署/补正回执/正文落盘为完成证据，周巡检只做证据核对；④ 诚实标注：不因"框架已出"降级风险 |
| 第43周 10-25 | 危机双线整改不对称性 | ⑤ **双线拆项**：危机事项拆"赔偿线/管理线"，各自唯一 owner 与死线，任一未闭环整体风险未消；⑥ **管理线"框架即草稿"**：把"成稿"而非"框架"设为 G8 闭环判据；⑦ 公信力修复计时：管理线逾期触发 P0 催办 + 人工确认外发 |
| 第44周 11-01 | G8 声明硬挡须配执行验证回执 | ⑧ **执行验证回执字段**：声明硬挡时须有人/系统回执确认挡已实际生效（出具流程挂起、sign-off 被拦截留痕）；⑨ **状态机四段化**：声明→执行→验证→闭环，仅"声明"无"回执"视为门禁未生效（red） |
| 第45周 11-09 | 周巡检挂账衰减陷阱 | ⑩ **挂账存活周数字段** + 熔断阈值：同一风险连续存活 ≥3 周未闭环 → 具名 owner + 强制外部动作（催办函经老强授权/dashboard 置顶/周会议程）+ 🔥 升级态；⑪ 闭环证据化：无补正版/签署页/挂起回执则存活周数不清零 |

**去重合并为 6 项机制（M1–M6）**：

| 机制 | 内容 | 来源 |
|---|---|---|
| **M1 死线+升级双轨** | 死线日 + 升级日（+7 天自动升 P0 并提示人工催办） | ①⑦ |
| **M2 owner 唯一化（含双线拆项）** | 单一 owner + 验收标准；危机事项拆赔偿线/管理线各自 owner 与死线 | ②⑤ |
| **M3 闭环证据化** | 以补正版/签署页/正文落盘/挂起回执为唯一完成判据；中间产物不算闭环，存活周数不清零 | ③⑥⑪ |
| **M4 执行验证回执** | 硬挡须回执证明下游出具动作被实际挂起/拦截并留痕 | ⑧ |
| **M5 挂账存活周数 + ≥3 周熔断** | 首标起计周；≥3 周未闭环升 🔥 态 + 强制外部动作 | ⑩ |
| **M6 状态机分段化** | 声明→执行→验证→闭环（→熔断）四/五段；仅声明无验证视为未生效 | ⑨ |

## 四、利弊分析（总体）

**收益**：把 G8 从"输出闸门"升级为"过程闭环闸门"，直接对标 R2/R6/R7 这类跨月挂账；四周经验卡从"只写不改"变成可执行的制度条款；下次周巡检有明确熔断判据，不再靠人工记忆天数。

**代价/风险**：① 门禁定义变更属中枢规范，须走 RULE-060 五步全链路同步（gate-config.md、运维手册 §3.3/§3.5、作战室总纲、相关镜像卡），改动面不小；② "自动升 P0/强制外部动作"若写得太硬，可能触发误报升级（需保留老强授权闸门，自动化不代发函）；③ 新增字段要给 case-state.json 的 gates schema 留扩展位，否则状态机无法承载执行回执；④ 版本号撞号需按第三节处理。

## 五、A/B/C 三方案

### 方案 A｜最小止血：只改巡检侧，不动门禁文件

- **做什么**：仅改周巡检简报模板/自动化脚本，增加「挂账存活周数 / 🔥 熔断态 / 唯一 owner / 闭环证据」四个展示字段；gate-config.md 一字不改。
- **利**：零门禁改动、零版本冲突、零 RULE-060 派发；本周即可生效；完全可撤销（改回模板即可）；不触碰 case-state schema。
- **弊**：只提升"可见性"，不产生制度强制力——硬挡仍无执行回执，下次仍靠巡检自律；R2/R6/R7 若老强不盯，会继续挂账；四周补丁的 M4/M6 仍悬空。
- **适合**：想快速止血、暂不动核心规范的场景。

### 方案 B｜一步到位：升级门禁本体（gate-config.md → 1.7.0 / 体系 v2.2）

- **做什么**：在 gate-config.md 第三节 G8 强制步骤表增补 M1–M6 六项；状态机增"执行验证回执/存活周数"字段；frontmatter 1.6.0→1.7.0 + 变更日志；按 RULE-060 五步同步运维手册 §3.3/§3.5、作战室总纲 §3.2、镜像卡；跑 doc-consistency 自检。
- **利**：制度层根治，G8 从声明闭环变执行闭环；四周补丁一次性落地；与 G7 结案回流、数字分身系统第6条留痕铁律对齐；后续巡检有硬判据。
- **弊**：改动面最大（多文件同步）；写入前须逐文件 cp 备份 + dry-run + 引用预检；南四同步任何一处遗漏即产生版本漂移；需你明确授权"五步派发 + 写入"。
- **适合**：决心根治、愿意一次授权全链路改的场景。

### 方案 C｜分阶段（推荐）：A 立即上 + B 立项第二阶段

- **做什么**：
  - **第一阶段（本周，无需另行授权即可备妥）**：巡检侧先加四个止血字段（同 A），R2/R6/R7 立即显示存活周数与 🔥 态；不动任何门禁/状态文件。
  - **第二阶段（等你拍板后执行）**：按 B 升级门禁本体，走 RULE-060 五步同步 + doc-consistency 自检，版本号按第三节双编号处理。
- **利**：止血与治本兼顾，风险可控；第一阶段零改动、可撤销，第二阶段有明确授权边界；版本撞号问题在立项时一并解决；给老强一次拍板决定"是否+何时"上本体升级。
- **弊**：两阶段落地周期较长；若第二阶段迟迟不立项，会重演"建议挂账"（故第二阶段建议设立项死线，例如 2026-11-30 前裁定）。
- **适合**：既想立刻见效、又不愿在未确认前大规模改写规范——**推荐**。

## 六、推荐与拍板请求

**推荐 C**。理由：完全守住"AI 不擅改门禁"边界，同时把四周补丁中最容易落地的"可见性/熔断显示"先变成产品能力；门禁本体升级作为明确立项项，等你一次拍板，且用第二阶段死线（建议 11-30）防止再次挂账。

请老强拍板（回复即可，无需长文）：

1. **选哪个方案**：A / B / **C（推荐）** / 其他；
2. **若选 B 或 C 第二阶段**：是否授权我按 RULE-060 五步全链路同步（gate-config.md + 运维手册 + 作战室总纲 + 镜像卡）+ 逐文件备份后写入？
3. **第二阶段立项死线**：建议 **2026-11-30**，是否认可？（防止"治理建议再次挂账"）
