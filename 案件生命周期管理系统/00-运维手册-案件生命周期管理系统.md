# 运维手册 · 案件生命周期管理系统（CLM）v2.1.1

> **一句话定位**：小强律师数字分身系统的「案件全程驾驶舱」——把接案到结案的全周期状态，变成一份机器可读的事实源，向下游分出**内部全量大屏**（自己看）与**对外脱敏简报**（当事人看）两条独立管线；同时把「哪些智能体在哪一阶段干活、产出了什么文件」也固化进同一事实源（`meta.agents`）。
>
> **本手册回答四个问题**：系统由什么组成、智能体怎么路由、日常怎么操作、出故障怎么办。
> **本手册不回答**：案件怎么做、文书怎么写——那是 [[案件全生命周期·编排器]] 的职责；推演怎么打——那是 [[模拟法庭推演专家]] 的职责。

## 一、系统定位与四层架构

```
L1 数据层  ──  case-state.json（单一事实源 ★ 含 meta.agents 智能体路由）
                    ↓
L2 引擎层  ──  scan_cases.py（扫描 / 倒计时 / 分级 / 智能体面板渲染）
                    ↓
        ┌───────────┴───────────┐
L3 内部展示（全量）      L4 对外通道（脱敏）
   大屏 / 驾驶舱 / 智能体面板   简报 / 进度页 / 微信 / 邮件
```

**铁律：L3 与 L4 是两条独立管线，绝不共用渲染。** 内部能看到的所有东西（红蓝态势、法官预判、证据分级、底线金额、对方当事人信息、智能体挂载明细），对外一律不可见。

### 3.1 为什么必须是 JSON

案件笔记是**散文**，散文无法驱动大屏、推送与智能体路由。所以：

> **`case-state.json` 是唯一事实源。md 笔记由它派生展示，绝不可反向从散文解析状态。**

### 3.2.1 三个易混字段：`counselRole` / `appearanceRole` / `partyRole`（2026-11-02 增补）

**动因**：6658 案 `counselRole` 长期写「代书（未正式代理）」，但真实结构是**老强幕后起草、当事人刘维以「被告二＋被告一特别授权委托代理人」身份出庭并署名**。二元取值装不下三元事实，导致代理词技能按 `counselRole` 分支时把《代理词》判成《意见书》，文书名称与自称跟着错。

| 字段 | 答的是 | 6658 实例 |
|---|---|---|
| `partyRole` | 我方在诉讼中是什么身份 | 被告方 |
| `counselRole` | 律师/起草人以什么身份介入 | 代书（老强起草，未以律师身份出庭） |
| `appearanceRole` | 谁出庭、谁在文书上署名 | 刘维（被告二）兼被告一刘九零特别授权委托代理人 |

**铁律**：三者不得互相顶替。文书自称（《代理词》vs《庭后补充意见》）**跟 `appearanceRole` 走，不跟 `counselRole` 走**——因为决定文书体裁的是「谁以代理人身份向法院陈述」，不是「谁在后台起草」。

### 3.3 七阶段与十门禁（v2.1 增补 G9）

| 阶段 | 名称 | 出口门禁 |
|---|---|---|
| ① | 接案建档 | G0 收案 |
| ② | 检索研究 | G1 检索 |
| ③ | 文书起草 | G2 文书 |
| ④ | 庭审查庭 | G3 庭审 |
| ⑤ | 客户协作 | G4 客户 |
| ⑥ | 程序执行 | G5 程序 |
| ⑦ | 风控归档 | G6 风控 → G8 非诉合规 |
| — | 结案回流 | G7 结案回流 |

门禁状态取值：`pass` / `active` / `warn` / `fail` / `todo` / `waived`（未开庭等场景用 waived）。

> 门禁的**强制步骤清单**以 `案件全生命周期·门禁体系` 为准，本系统只读不改。v2.1 起门禁为 **G0–G9**（共十道）：
> **G0–G7 为阶段流转门禁**；**G8 非诉合规**（v2 新增）与 **G9 执行专项**（v2.1 新增）均为**触发式、不并入阶段流转**，未触发的案件不影响任何阶段放行。
> **G9 分两段**：**G9-a 立案前六项**（任一项不过则不写申请书）＋ **G9-b 产出后两项**。定义见 §3.5 与 §4.6。

### 3.4 `meta.agents` 字段（v2 新增 · 智能体路由落地）

`meta.agents` 是 v2 核心新增：把「哪一阶段由哪个真实智能体/连接器干活、产出了什么文件」固化进事实源，大屏据此渲染「智能体挂载」面板。

**字段说明**：
- `stage`：七阶段名（与 §3.3 对齐）
- `gate`：对应门禁（如 `G1` / `G6/G8`）
- `role`：职能（检索/文书/模拟法庭/推送…）
- `agent`：**真实承载**（解析后的连接器/技能，非逻辑名）
- `status`：已接入 / 已建 / 待配
- `artifacts`：该阶段实际产出物**真实路径**（可点击跳文件，见 §6.2）
- `note`：补充说明（如「二源互补」「邮件待配webhook」）

**当前两案均写入 11 条 `meta.agents` 记录**（含 接案三件套 / 庭审六件套 真实路径）。

### 3.5 门禁强制步骤速查（摘要，权威源见 gate-config.md）

| 门禁 | 强制步骤（缺一项即阻断） |
|---|---|
| **G0 收案** | 利益冲突审查通过 + 收案审批表完成 + 委托合同签署 + 已建档 |
| **G1 检索** | 法律检索报告已出（含相反观点+本地口径+风险）+ 类案检索报告已出 + 检索结论归档 → **接案三件套齐备** |
| **G2 文书** | 文书经蓝队+红队红蓝复核通过 + 证据目录齐备 + 质证齐备 |
| **G3 庭审** | 庭前准备清单通过 + 庭审记录已生成 + 庭后复盘已写 |
| **G4 客户** | 客户会议纪要已存 + 材料清单已交付 + 工作汇报已发（五段式） |
| **G5 程序** | 立案/保全/送达签收（签收日=期限起算）/期限无遗漏 四项全过 |

#### 4.6.1 挂载方式：适配层外置，本体零改动

| 项 | 落点 |
|---|---|
| **技能本体**（🔴 **禁改**） | `~/.workbuddy/skills/execution-docs-generator/` |
| **本机适配层** | `~/.workbuddy/skills/_local-patches/execution-docs-generator/ADAPTER.md` |

**为什么外置**：外部技能作者升级会**整体覆盖技能目录**，任何写在目录内的定制都会丢且无法追溯。故一切 override 集中在 `_local-patches/`，技能本体保持原样，随时可升级。

#### 4.6.2 适配层 override 六项（对应技能自身 P0 缺陷）

| # | 技能缺陷 | 本机 Override |
|---|---|---|

| §6 | 文末署名推广条款 | 出件时屏蔽 |

#### 4.6.3 挂载链路（顺序不得颠倒）

```
⑥-a 执行立案（触发式子分支）
  ① G9-a 立案前六项        ← 任一项不过 → 不写申请书，退回策略层
  ② 案件执行助手 出策略     ← 打不打 / 怎么打 / 财产在哪 / 惩戒节奏
  ③ 读 ADAPTER.md          ← 取 override 六项
  ④ execution-docs-generator 出件
  ⑤ 蓝队诉讼律师 体检
  ⑥ G9-b 产出后两项        ← 含 LTI REJECT=0
  ⑦ 执行案 case-state 回写
```

**为什么 G9 分两段**：八项横跨三个时点——第 1–6 项是立案前审查（主体资格不具备就不该动笔），第 7 项在文书产出后，第 8 项在立案后。合成一门挂哪一步都不对（详见 gate-config v1.6.0 说明）。

#### 4.6.4 关键约束

1. **技能本体一字不得改**——升级覆盖即失效，且无法追溯改动
2. **不占用原案 ⑥→⑦ 的 G5 结案门禁**——执行案是**独立新案**（独立案号 / 案由 / 立案 / case-state），原案照常走 G5 结案，互不干扰
3. **触发式**：未进入执行程序的案件无需检查，**不影响 G5 放行**（自动履行、和解结案、胜诉但无给付内容的案件不会走到这一步）
4. **出件不等于定稿**——律师签字前一律是草稿
5. **元典按调用计费**——非公司主体案件可跳过技能"第二问"，不必调

#### 4.6.5 维护要点

| 场景 | 动作 |
|---|---|
| 作者发布新版本 | 直接覆盖升级技能目录；**升级后必须复核 ADAPTER.md 六项 override 是否仍适用**（尤其 §1 工具名、§5 利息口径——这两项一旦失效会直接出错误文书） |
| 发现新缺陷 | 登记到 ADAPTER.md **§7「已知瑕疵」**，**不改本体** |
| 门禁检查点调整 | 只改 `gate-config.md`，ADAPTER.md 引用之，**不重复维护** |
| **改完本节或 SOP 表 5 后** | 🔴 **必跑** `python3 _AI-Memory-Hub/99-脚本/check_registry_sync.py`（规程见 **WF-132**）。§4.6 与表 5 是**同源关系**，单边改会被 TWIN 检查报出，全纳表计数与版本号不一致会被 COUNT/VLOG 报出 |
| 实战状态 | ⚠️ 截至 2026-11-02 **仍未实战**。首次真实执行立案后须回填实测记录；在此之前只算"逻辑正确"，不算"验证过" |

#### 4.6.6 适用性提示（防误用）

**不是所有案件都能用**。触发本技能前先过 **G9-a 第 2 项（申请执行人主体资格，《民事诉讼法》第 247 条）**——只有"对方当事人"才有资格申请执行。

> 实例（6658 案，2026-11-01 沙盘推演）：我方系一审被告且全案胜诉（判项为驳回原告对我方诉请），**判项给付对象是原告**，我方不具备申请执行人资格。同案的承揽尾款 68,000 元另案，我方是**定作人（付款义务方）**，属潜在被执行人，同样不适用。
> **教训**：一个写错的适用性结论，若不做沙盘推演，会一直躺到真正需要时才暴露。

## 九、故障排查手册（踩坑档案）

### 9.1 脱敏版把案号改成「民初CASE-01号」
**原因**：`caseId` 替换规则抢在案号正则之前命中。**铁律**：`_redact_str` 中必须**先**跑 `(民初|民终|民再|刑初)\d+号 → \1****号`，**再**跑 caseId 替换。

### 9.2 脱敏版仍泄漏真实姓名与本地路径
**原因**：`_path` 与 `_folder` 未处理。**解法**：脱敏预处理中 `c.pop("_path")`、`c["_folder"] = f"案件{i}"`。

### 9.3 `wecom-cli --version` 版本解析失败
**解法**：正则 `re.search(r"(\d+)\.(\d+)\.(\d+)", raw)` 提取。

### 9.4 grep 多词扫描扫不出东西（2026-10-31 二次踩坑，症状升级记录）

**原因**：BSD grep 的 BRE **不支持 `\|` 交替**——`\|` 被当字面量，「A 或 B」退化成「匹配这一整串」，返回 0 命中且 exit 1，**看起来像「查无此事」，实为模式写错**。

**实测对照（2026-10-31，对象 `LTI文本监控器/references/personalization.py`）**：

| 命令 | 命中数 |
|---|---|
| `grep -c "statutory\|_STATUTORY" f.py` | **0** |
| `grep -cE "statutory|_STATUTORY" f.py` | **7** |

**解法**：`grep -E "A|B|C"`，或逐词循环，或直接用检索工具。

🔴 **铁律（2026-11-02 立）**：**单次 grep 零命中，不构成「不存在」的证据。** 断言「零引用／未接线／不存在」前，必须换写法（`-E`、`-F`、逐词）或换工具复核第二次。本次事故：同一坑连续 3 次零命中，被误诊为「环境问题」并写进汇报——**同一个错误重复三次而没认出来，比错误本身更危险**。

### 9.5 `timeout` 命令不存在
**原因**：macOS 无 GNU coreutils。**解法**：后台运行 + `sleep` + `pkill`。

### 9.6 探测 init 二维码不能转述
**正确做法**：用户本机实时跑 `setup_wecom.sh`；或由助手前台跑 `wecom-cli init --noninteractive` 使其**阻塞**（auto-background 保活），把**当次**二维码给用户扫。

### 9.7 非交互终端子进程跨轮不保活
**解法**：不要 `(cmd &)` 挂起；让命令自然阻塞触发 auto-background。

### 9.8 探测 init 是否有副作用
**判据**：`wecom-cli msg --help` 不再报"未找到 MCP 配置缓存" + `cache status` 非空 + `~` 下出现 wecom 配置目录。已验证掐断探测**无残留进程、缓存为空、授权未变**。

### 9.9 智能体面板不显示 artifacts 路径
**现象**：面板只渲 stage/gate/role/agent/status/note，未渲染 `artifacts`。
**状态**：已知待补（§十二 P2）。`artifacts` 已存于 state，渲染层加「点开跳文件」即可。

### 9.10 LTI `PF-001` 判起诉状／答辩状／上诉状「违反格式铁律」（2026-10-31，规则盲区·已修）

**现象**：43 号《民事答辩状》过 LTI，报 `PF-001-2 编号小标题 — 违反「禁止论文化写法」`。

**根因**：老强格式铁律「禁编号小标题／禁『综上所述』」的适用对象是**庭后代理词、书面意见**；起诉状、答辩状、上诉状属**法定格式文书**，法院对其格式有规范要求，「一、二、三」分项与分节标题是法定或通行写法。**是规则把铁律无差别套到了所有文书，不是文稿写错。**

**已修（LTI v4.11.1）**：`personalization.py` 新增 `_is_statutory_form()`——文首 15 行内、独占一行的文种标题（民事/刑事/行政/执行/仲裁 + 起诉状/答辩状/上诉状/反诉状/自诉状，可带括注）即识别为法定格式文书。

**豁免口径（刻意收窄，勿扩大）**：

| 规则 | 是否豁免 | 理由 |
|---|---|---|
| PF-001-2 编号小标题 | ✅ 豁免 | 分项标题有法院格式依据 |
| PF-001-1 加粗元信息块 | ❌ 照拦 | 「**案号：…**」独立加粗块无格式依据 |
| PF-001-3 独立「法律依据：」板块 | ❌ 照拦 | 同上 |
| PF-002 双轨交付提醒 | ❌ 照发 | 与体裁无关 |

**边界**：只认**文首标题**；正文中提及「对方答辩状提出三点抗辩」不触发；「代理词／法律意见书／答辩意见」**不在**豁免名单。

**回归保护**：`references/tests/test_personalization_pf001.py`（24 项）。改 PF 规则**必跑**，它是该模块唯一回归保护。

### 9.11 LTI 输出尾部带「AI 参与说明」，不得随文书提交法院（2026-10-31 实测）

**现象**：`wrap_output()` 返回值末尾自动追加「本文件由人工智能辅助生成，仅供内部参考」+ 参与说明勾选表 + 版本 footer。43 号若整段复制即会把这段带进法院。

**解法**：正式提交件**只用文书正文**，不用 LTI 包装后的整段文本。交付前搜一遍「人工智能辅助生成」「文本监控器」确认零残留。

### 9.12 电核口头结论被标成「已坐实」，后被原件推翻（2026-10-28 → 11-02，事故）

**经过**：2026-10-28 电话核实后，`case-state.json` 写入「仅黄茂姣上诉、欧派店未上诉（**已坐实**）」，并以此覆盖了 2026-10-14 依据 37 号原件作出的「黄茂姣／欧派店二人上诉」记录。2026-11-02 复核 37 号原件（六份 PDF 逐字核验，落款 2026-10-12）确认**上诉人确为二人**，10-28 结论系误记。一审判决主文本即判「黄茂姣、欧派店判付尾款 2855 元＋受理费」，欧派店本具上诉利益——**原件与判决主文互相印证，电核结论与之相反**。

**根因**：把「口头核实」当成了「原件核验」。「已坐实」在 F 编号体系里是最高证明状态，只能由**书证原件**支撑，不能由电话记忆支撑。

**铁律（2026-11-02 立）**：

1. 电核／口述结论最高只能标 **「强佐证」**，且须注明核实方式与时间；
2. 标「已坐实」必须写明**原件名称 + 落款日**，做不到就不许用这三个字；
3. 新结论与既有原件冲突时，**先比对原件再改状态**，不得直接覆盖；
4. 更正时**保留旧结论并标注「已核正·此条结论有误」**，不得静默删除——否则下次无从判断电核的可靠边界。
